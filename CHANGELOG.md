# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- **sync**: `deepl sync pull --dry-run` previews a pull without writing anything — no target file, no `.deepl-sync.lock`. It reports how many translations would be pulled and how many existing local translations would be replaced, and `--verbose` names each key and file whose TMS value differs from the local one. `--format json` carries `replaced` and `dryRun` alongside `pulled`. Pull is the one sync command that replaces hand edits with content the CLI has no way to date, and it was the only writing sync command with no preview mode; `sync` itself and `sync resolve` both have one. The flag is also accepted on the parent (`deepl sync --dry-run pull`), matching how `sync resolve` reads it.

- **translate**: `--glossary` now applies to document translation (PDF, DOCX, PPTX, XLSX, images, and text-based files routed to the document API). It was previously accepted and then silently discarded with a "document mode does not support --glossary" warning, even though `POST /v2/document` supports glossaries. Repeating the flag works here too, with the same merge behaviour and the same API-decided conflict resolution. `--from` is required, because the API rejects a document glossary without a source language; `--translation-memory` remains unsupported for documents. Note that glossary matching is context-dependent for documents exactly as it is for text — a term applied in one sentence may be left alone in another.

- **translate**: `--glossary` is repeatable, applying up to 5 glossaries to one request via the API's `glossary_ids` parameter. Entries are merged, so terms unique to each glossary all apply. When several glossaries define the same source term, **which mapping wins is the API's choice and does not follow flag order** — verified live with two glossaries defining the same term, where the same one won in both orderings in five of six trials and the first-listed one won in the sixth, so position is not a way to override a term. The order is still sent as given and never sorted, because it is part of the cache key: reordering the flags is a different request with its own cache entry. Names and UUIDs may be mixed and are resolved independently. A single `--glossary` still goes out as `glossary_id`, leaving existing commands and their cache keys untouched; the new field is appended last in the cache key for the same reason. A 6th `--glossary` exits 6 (ValidationError) before any API call. `watch` and `sync` keep their single-glossary configuration. Verified against the live API: `POST /v2/translate` accepts `glossary_ids` as repeated form fields and resolves them in order, rejects a sixth with `A maximum of 5 glossaries can be specified per request.`, and rejects `glossary_id` and `glossary_ids` together with `Specify either glossary_id or glossary_ids, not both.` -- which is why the CLI collapses a single glossary to `glossary_id` rather than sending both. The multipart `POST /v2/document` takes one comma-joined value, since multipart does not parse repeated fields as a list. Both halves of that are now confirmed against the live API with two real single-entry glossaries: a comma-joined `glossary_ids` applies the terms from both, while sending the same two IDs as repeated multipart fields applies only the first and reports no error, so the comma-joining is required rather than merely sufficient.

- **languages**: `deepl languages --features` shows which features each language supports — formality, glossary, style rules, translation memory, tag handling and auto-detection — from the `features` matrix on `GET /v3/languages`, which the CLI previously discarded. Support no longer has to be discovered by making a request and reading the error. Which features get a column is derived from the response rather than a fixed list: a feature appears when its support differs across the languages listed, and one supported by all of them is reported once as `All listed languages also support: ...` instead of being repeated on every row (`All languages with reported features also support: ...` when the listing also carries languages the response did not describe, since the note must not speak for those). A language the response omitted reads as `no feature data` rather than as supporting nothing, and does not count towards whether a feature varies. That makes the columns differ between listings — `auto detection` appears under `--target`, where target-only variants lack it, but is uniform under `--source` — and means a newly reported feature shows up without a code change. Support is signalled by the API reporting a feature at all; `status` describes maturity, so anything short of generally available renders verbatim (`glossary (beta)`) rather than collapsing to `yes`. Works with `--format table` (one column per feature) and `--format json` (the raw matrix including each status, present only when `--features` is passed, so existing JSON consumers are unaffected). The `supportsFormality` field is unchanged for every language `GET /v3/languages` describes, which is all of them today; it now comes from the matrix rather than v2's `supports_formality` boolean, and is **omitted rather than reported as `false`** for a target the response says nothing about, since silence is not evidence that formality is absent. `--features` supersedes the `[F]` shorthand and replaces it when given. It needs an API key; without one the command warns and falls back to the registry, which carries no feature data. Note that the matrix is finer-grained than the core/regional/extended tiers: some extended languages support style rules and translation memory even though they support neither formality nor glossary.

- **cli**: `deepl correct` command (alias `c`) — spelling and grammar correction without rewording, via the Write API's `/v2/write/correct` endpoint. Supports the same input handling and workflow flags as `write` (`--check` with exit code 8, `--fix`/`--backup`, `--diff`, `--interactive`, `--output`/`--in-place`, `--format json`, `--no-cache`), but not `--style`/`--tone`, which the correct endpoint does not accept. Results are cached under a separate `correct:` namespace so corrections and rephrasings of the same text never collide.

- **http**: `NO_PROXY` / `no_proxy` are honoured, with the standard semantics — `*` for everything, a leading dot or `*.` for subdomains, and an optional `host:port` that must agree. A corporate `HTTPS_PROXY` was previously applied to every request, including one aimed at localhost.

- **auth**: `deepl auth set-key --no-verify` stores a key without validating it against the API. Validation ran before persisting, so on a network without proxy configuration both documented setup paths — `auth set-key` and `init` — failed and discarded the key; an unreachable API now also names `DEEPL_API_KEY` as the zero-network alternative.

- **ci**: `npm run check-deps` fails the build when a package imported by `src/` is missing from `dependencies`, including one declared only under `devDependencies`. It runs in CI and in the publish job, and matches package names as quoted strings so indirect loads such as `requireModule('php-parser')` count as references.

- **cli**: `t` and `w` command aliases for `translate` and `write` ([#12](https://github.com/DeepL/deepl-cli/issues/12)). The aliases appear in `--help` output and in bash/zsh/fish shell completions. `w` is deliberately assigned to `write` rather than `watch` — write is a primary API feature, watch a workflow helper.

- **ci**: Pushing a `v*` tag now creates a GitHub Release, with notes extracted from that version's CHANGELOG section and generated notes as a fallback when the section is missing. This is why the repo has 17 tags and zero Releases. The workflow does **not** publish to npm: releases are published from GitLab, which is the source of truth and mirrors to GitHub, matching the other DeepL client libraries. The tag is checked against `package.json` first, so a mislabelled tag cannot mint a Release whose title disagrees with the version it contains.

- **cli**: Global `--timeout <ms>` and `--max-retries <n>` options override the HTTP transport defaults (30000 ms, 3 retries) for a single invocation. Neither was previously configurable from the CLI.

- **translate**: `--format json` output now includes the documented `cached` boolean, so scripts can distinguish cache hits from fresh API calls.

- **cli**: Running under Node.js < 24 now fails fast with a clear one-line error (exit 6) instead of surfacing a raw `node:sqlite` ExperimentalWarning or crashing later.

### Changed

- **sync**: **the `--format json` error envelope moves from stderr to stdout, for every sync subcommand at once.** A consumer that read the failure reason off stderr stops finding it there: `deepl sync … --format json 2>err.json` now captures only human-facing warnings, and the envelope arrives where `> out.json` already captured the success payload, so one redirection handles both cases. Exit codes are unchanged and remain the failure signal. Anything branching on *the presence of* stderr output still works — warnings still go there — but anything *parsing* stderr must switch to stdout. See Fixed.

- **sync**: **`deepl sync validate` exits 8 where it exited 1 on a project whose target file cannot be read, and its `--format json` issues list gains a new check kind.** A consumer that treated exit 1 as "the CLI crashed" starts seeing the documented check-failure code with a full report attached, and a JSON consumer iterating `issues` will meet entries whose `check` is `unusable_target`, whose `key` and `file` are both the target path, and whose `source`/`translation` are empty. See Fixed.

- **sync**: **`deepl sync pull` no longer applies an exported value to a plural entry, and its counts move.** The export carries one string per key, which cannot fill a plural entry's forms; that value used to be applied nowhere while the entry's forms were emptied and the key was still counted as pulled and replaced. Such a key is now reported under a new `plural_entry` skip reason in the `(N skipped: …)` summary and in `--format json`, is not counted in `pulled` or `replaced`, and no lockfile entry is recorded for it. A consumer reconciling pull counts against the export's key list will see the difference; the export itself is requested exactly as before. See Fixed.

- **sync**: **`deepl sync status` reports a lower coverage percentage for an XLIFF project whose targets carry a review `state`, and `deepl sync` writes `state="translated"` where it used to leave the old value.** A dashboard or CI check reading `coverage` or `complete` out of that command will see an XLIFF project it called 100% drop to whatever share of its units are actually approved, and `deepl sync push` reports a lower pushed count by the same number. The written bytes change only for a target that already carried a `state` and whose translation this run replaced; a target with no `state` is written exactly as before. The `sync status` explanation of the `needsReview` count no longer describes gettext alone — it named `#, fuzzy`, `msgfmt` and "clear the msgstr" to users of a format that has none of those. `sync --frozen` still passes. See Fixed.

- **watch**: **`deepl watch` writes a nested source file to a nested output path.** Watching `docs/` with `--output out`, `docs/guide/intro.md` now lands at `out/guide/intro.es.md` where it used to land at `out/intro.es.md`. Anything reading a watch session's output by flat basename — a publish step, a `.gitignore` entry, an `--auto-commit` diff — has to follow the directory it now sits in. A file at the top of the watched directory, and a watched path that is a single file, are unchanged, so a single-directory or single-file session sees no difference. The layout is the one `deepl translate <dir> --output <dir>` has always produced. See Fixed.

- **sync**: **`deepl sync status` reports a lower coverage percentage for a PO project holding `#, fuzzy` entries**, and each locale in `--format json` gains a `needsReview` count. A dashboard or CI check reading `coverage` or `complete` out of that command will see a project it called 100% drop to whatever share of its keys are actually shippable — which is what `msgfmt` has been reporting all along. `deepl sync push` reports a new `needs_review` skip reason, so its pushed count falls by the number of fuzzy entries. Nothing is re-translated, rewritten or re-billed, and `sync --frozen` still passes. See Fixed.

- **sync**: **a project that sets `sync.max_characters` can now be refused where it previously ran**, and `deepl sync --dry-run` can now report a larger character estimate than before for the same input. Both follow from the cap and the preview finally counting repair work — keys the lockfile calls translated that the target file no longer holds — which a real run translates and bills. A pipeline whose cap was tuned against the old under-count will need it raised to the number `--dry-run` now reports, which is the number that run actually spends. `--dry-run` still exits 0 and still writes nothing. See Fixed.

- **watch**: **`deepl watch --auto-commit` now exits 6 at startup when the output directory is in no git repository.** It previously started the watcher, translated, and printed `⚠️  Not a git repository, skipping auto-commit` once per translated file while exiting 0, so a session that could never commit anything still billed every translation. The refusal names the directory and comes before the first translation, matching how a `--glossary` without a source language is refused at launch rather than once per file change. Automation that relied on the translations still being written in that case has to drop `--auto-commit`. See Fixed.

- **watch**: **a `deepl watch` session now exits 12 rather than 0 when it recorded a failure.** Ctrl+C used to end every session at exit 0 with failed translations and failed auto-commits only logged, so a script wrapping `deepl watch` could not tell a clean run from one that lost work. A session that recorded any translation error or any `--auto-commit` failure now exits **12** (`PartialFailure`), and the auto-commit failure count is printed beside the translation total. A session with no failures still exits 0. See Fixed.

- **sync**: **`deepl sync push` / `pull` exit 5 where they exited 1 when the TMS could not be reached.** A pipeline branching on exit 1 as "the CLI crashed" stops seeing an unreachable TMS there and starts seeing it under the documented retriable code, alongside the timeout it already handled. Request counts are unchanged. See Fixed.

- **sync**: **`deepl sync` exits 12 where it exited 0 on a locale whose target file it cannot read**, and writes nothing for it rather than rebuilding the file from the source. Automation that treated exit 0 as "the locale is up to date" will start failing on a project whose target file is unparseable or unreadable — which is the point: the alternative was re-billing the locale and overwriting the only copy of its translations. `deepl sync pull` reports the same condition as a new `unusable_target` skip reason in its `(N skipped: …)` summary and in `--format json`, at its existing exit code, matching how a colliding target file is already handled. See Fixed.

- **sync**: **`deepl sync` exits 12 where it exited 0 on a key it could not write into the target file.** Any automation treating that command's exit 0 as "the locale is up to date" will start failing on a project it was already shipping incomplete — which is the point: the alternative was a lockfile entry claiming a translation the file does not contain. `sync --frozen` exits 10 and `sync status` counts the key against the locale for the same reason. See Fixed.

- **sync**: **a project already missing strings from this defect recovers on its next sync that has any work to do, and re-bills them.** Measured on a `properties` project whose target file was missing a key the lockfile called `translated`: the next `deepl sync` that had a further key to translate reported `es: 2/2 keys` — the new key plus the recovered one — and wrote both. A run with nothing else to do reported `2 current`, wrote nothing, and `sync status` still said `100% (0 missing)`, because `status` and `--frozen` compare the source against the **lockfile** and never read the target file. So a project where nothing has changed since is not repaired by upgrading alone: add a string and sync, or delete the target file to have it rebuilt. See Fixed for the defect itself.

- **sync**: **two output shapes change for PO and XLIFF buckets.** `deepl sync validate` now **exits 8** on a project it previously passed at exit 0, because the check finally reads the translation (see Security) — a CI job treating that command's exit 0 as "translations are sound" will start failing on input it was already shipping broken. And `deepl sync push` now reports a lower pushed count on any PO or XLIFF bucket with keys not yet translated: those keys are skipped rather than uploaded as their own source text (see Fixed), under a new `untranslated` skip reason that appears in the `(N skipped: ...)` summary line and in `--format json`. Monolingual buckets are unaffected on both counts.

- **sync**: **`sync pull`'s lockfile and output shapes both change.** Pulled keys no longer carry `review_status` at all (see Security), so anything reading `review_status === "human_reviewed"` out of `.deepl-sync.lock` to find reviewed strings stops matching pulled entries — an absent field means "unknown", which is all the export response supports. A key with no translation in the export and none in the target file is now **absent** from the written target file rather than present holding the source string (see Fixed). `sync pull --format json` gains `replaced` and `dryRun` fields, and the text output gains a second line naming the replaced count when it is non-zero.

- **translate**: **a translation that lost one of your placeholders is now a failure rather than output.** `deepl translate` exits 5 and writes nothing where it previously printed or wrote the CLI's internal `__ Var_0 __` scaffolding at exit 0, and a directory run reports those files as failed. Anything scraping `translate` output was already receiving unusable text in this case; it now sees a non-zero exit instead. See Fixed.

- **translate/sync**: **two exit codes move for files containing an empty string value.** `deepl translate <file>` exits 0 and writes its output where it used to crash with exit 1, and `deepl sync` exits 0 where it used to exit 12 on every run forever. A rate limit part-way through a large structured file now exits 3 rather than 1, so a CI wrapper that treats 3 as retryable starts retrying it. See Fixed for the measurements.

- **sync**: **`deepl sync --force` without `--yes` now exits 6 wherever it cannot prompt**, not just under `CI=true`. Any automation that runs it from a git hook, cron job, `make` target or container entrypoint — anything with piped or closed stdin, plus `--no-input` — has to add `--yes`. See Security for why it was doing the opposite and what that cost.

- **sync**: **a validation error now fails the run.** `deepl sync` previously exited 0 with a one-line `N validation error(s)` warning while writing the corrupt translation; the key is now withheld and counted as failed, so the run exits 12 (`PartialFailure`) — or 6 with `validation.fail_on_error: true`, as before. CI that treats `deepl sync` exit 0 as "translations are complete and correct" gets the right answer for the first time; CI that ignored the warning line starts failing on input it was already mistranslating. `SyncResult.success` is `false` for the same runs. See Fixed for the measurements and for why the `fail_on_error` default was left alone.

- **hooks**: **`deepl hooks list --format json` reports a state string per hook instead of a boolean** — `"installed"`, `"modified"`, `"unverified"` or `"not-installed"` (see Security for why a boolean could not tell the truth). Scripts must gate on `state === "installed"`; a truthiness test now passes for every state, `"not-installed"` included, so it has to be replaced rather than left alone. The text output gains the same distinction, and a hook you customized by hand — which the README invites — reports `!` from then on, since its body no longer matches the hash recorded at install. `GitHooksService.list()` returns those states as well; `isInstalled()` still answers the narrower "a DeepL marker is present" question and is unchanged.

- **translate**: **`--tag-handling` requests now pin `tag_handling_version=v2`** instead of letting the API pick. The CLI previously sent the parameter only when `--tag-handling-version` was passed, so everyone else inherited the server default — which DeepL documents as moving from v1 (deprecation-bound) to v2 at an unannounced date. That flip would have changed tag-handling output with no CLI change to point at, and worse, would have gone unnoticed by the cache: a request that omits the version hashes identically before and after, so cached v1 output would have kept being served after the API started returning v2. Adopting v2 now makes that one output shift deliberate and dated, and DeepL's own docs recommend v2 for structure handling. **`--tag-handling xml`/`html` output may differ from previous releases**; pass `--tag-handling-version v1` to keep the old behaviour, which is still honoured and always wins over the default. Requests without `--tag-handling` send no version. Cached translations from earlier versions are retired on first open regardless — see the cache entry under Fixed — so no tag-handling entry can be served stale.

- **translate**: **A glossary referenced by name is checked against the requested language pair before any translation request.** Previously only translation memories did this; a glossary whose dictionaries did not cover the pair reached the API and came back as `No dictionary found for language pair EN-DE in glossary <uuid>`, naming a UUID the user never typed. It now fails locally, exit 7, naming what the glossary actually covers: `Glossary "my-terms" does not support the requested language pair` / `Glossary covers en→es; requested en→de.` This costs no extra request, because the glossary list is already fetched to resolve the name. Matching is per dictionary, so a multilingual glossary holding en→es and de→fr is not treated as covering en→fr, and when translating to several targets at once every one of them must be covered. Both sides are compared on their **base** language, because glossary dictionaries only ever name base languages while `--to` accepts regional variants: a de→en glossary covers `--to en-us`, which the API accepts, and demanding an exact match would have made glossaries unusable for every regional target — `en-us`, `en-gb`, `pt-br`, `pt-pt`, `zh-hans`, `es-419`, `fr-ca` — including the ones DeepL steers users towards over bare `en`/`pt`. The check is therefore deliberately permissive at the edges: a pair it lets through is still the API's to reject, which is much the cheaper mistake. Two deliberate exemptions: a glossary passed as a **UUID** is trusted and left to the API, matching how translation-memory resolution already behaves and giving an escape hatch if the check is ever wrong; and a glossary the API reports with no dictionaries is left alone, since that says nothing about coverage.

- **write**: **The Write API's 14 target languages are generated rather than hand-maintained**, closing the last hand-kept language list. The list and the `WriteLanguage` type were two separate hand-edited copies of the same set, either of which could fall behind `GET /v3/languages?resource=write` — the same way the translation list silently went four codes stale. `npm run generate:languages` now emits both language lists and `npm run check:languages` reports which one drifted; the type is derived from the generated list, so a language added upstream widens it on regenerate instead of needing a second edit. The generated list is byte-identical to what was there. `write`/`correct` still check the code locally and name every valid option, because at 14 of 125 languages an enumerated error beats a round trip -- but a code that is *shaped* like a language tag and simply is not in the snapshot is now sent to the API with that list as a warning, rather than refused. Nothing in CI regenerates the snapshot, so refusing outright made a language DeepL had added unreachable until someone ran the generator, with no flag to get past it. Malformed input is still rejected locally. Note the documented style/tone support table is unchanged and still maintained by hand, because it records what the API accepts rather than what its metadata claims: `resource=write` omits `writing_style` for `en`, but `--style` with `--lang en` works.

- **languages**: **The DeepL API is now the authority on which languages exist, not the CLI's bundled list.** That list was hand-maintained, so it could silently fall behind the API and make languages the API accepts unusable — which is exactly what happened to `de-CH`, `de-DE`, `fr-CA` and `fr-FR` (see Fixed). Three changes remove the failure mode rather than just correcting the data. **Validation defers to the API:** a well-formed language code the bundled list does not contain is sent to the API, which accepts or rejects it authoritatively, instead of being rejected locally. Input that is not shaped like a language tag is still rejected immediately with a pointer to `deepl languages`, so typos like `--to grman` still fail fast without a request. This covers `translate`, `sync` and language values in the config file. **The listing is API-driven:** `deepl languages` renders the union of the API response and the bundled list, so a language DeepL offers can no longer be missing from the output. **The list is generated:** `npm run generate:languages` rewrites it from `GET /v3/languages` and `npm run check:languages` fails on drift, so it is a build artifact of the API rather than something maintained by hand. The core/regional/extended tiers are derived in the same pass — glossary support separates extended from the rest, source usability separates core from regional — which reproduces the previously hand-assigned tiers exactly, so the tiers can no longer disagree with the API either. No command line changes; `--to de` and every other existing code behave as before.

- **types**: **The published `Language` union is derived from the generated language snapshot** instead of being written out by hand. It was a fourth copy of the same list and had already fallen four codes behind the snapshot it describes — `de-ch`, `de-de`, `fr-ca`, `fr-fr`, the very codes the /v3 migration added — so `const lang: Language = 'de-de'` was a compile error in the published typings while `deepl config set defaults.targetLangs de-de` succeeded at runtime and wrote a config `DeepLConfig` could not type. Neither `generate:languages` nor `check:languages` touched it. `ENTRIES` is now generated `as const satisfies readonly LanguageEntry[]` and the union derives from its codes, exactly as `WriteLanguage` already derived from `WRITE_TARGET_LANGUAGES`, so regenerating the snapshot widens both. The union only ever gains codes here, so nothing that compiled before stops compiling; runtime validation still defers to the API, which means the union describes what the CLI can name offline rather than what works.

- **languages**: **Ten display names changed to match the API**, a consequence of generating the language list rather than hand-writing it: `ckb` Central Kurdish → Kurdish (Sorani), `es-419` Spanish (Latin America) → Spanish (Latin American), `gom` Goan Konkani → Konkani, `kmr` Northern Kurdish → Kurdish (Kurmanji), `my` Myanmar (Burmese) → Burmese, `nb` Norwegian Bokmål → Norwegian (bokmål), `pam` Pampanga → Kapampangan, `st` Southern Sotho → Sesotho, `zh-hans` Chinese (Simplified) → Chinese (simplified), `zh-hant` Chinese (Traditional) → Chinese (traditional). **Only offline output changes**: with an API key configured, `deepl languages` already took names from the API and was therefore already showing these, so this makes the no-API-key output consistent with the keyed output rather than changing what keyed users saw. Language codes are unaffected, so nothing that selects a language by code has to change; only output that scrapes display names.

- **cli**: **Language codes are displayed in lowercase everywhere.** Output previously mixed three casings: `deepl languages` printed lowercase from the registry, `glossary show` and `tm list` uppercased at display time, `translate`'s table uppercased the target language, and `write`/`correct` used BCP-47 (`en-GB`, `zh-Hans`). Lowercase matches the CLI's own normalized form, the registry, what `deepl languages` teaches users to type, and the wire format `/v3/languages` moved to; uppercase followed a v2-era docs convention that v3 abandons. **Scripts scraping these values will see a casing change** — `glossary show` now reports `Source language: en` and `en → es: 5 entries`, `tm list` renders `brand-terms (en → de, fr)`, `translate --format table` labels rows `de`, and `write --format json` reports `"language": "en-us"`. Input is case-insensitive everywhere, so no command line has to change -- `voice` included, which previously demanded the exact mixed-case spelling of a regional code (`--to zh-HANS`) and rejected the lowercase form the rest of the CLI prints. `write`/`correct` also send the lowercase code as `target_lang`: the Write API accepts any casing and canonicalizes server-side (verified live on `/v2/write/rephrase` and `/v2/write/correct` — `en-gb`, `zh-hans`, and `zh-HANS` all return 200 and echo back `en-GB` / `zh-Hans`). Wire parameters that are not display are untouched: `translate` and the glossary create endpoint still send uppercase `target_lang`/`source_lang` as those endpoints document.

- **api**: Language listings migrated from the formally deprecated `GET /v2/languages` and `GET /v2/glossary-language-pairs` endpoints to `GET /v3/languages` (`resource=translate_text` / `resource=glossary`). Command output is unchanged: source/target lists derive from the v3 `usable_as_source`/`usable_as_target` flags, glossary pairs from the source×target cross-product (verified identical to the v2 pair list), and the `[F]` formality markers come from the per-language `features` matrix, which is what v2's `supports_formality` boolean became (see the Fixed entry on `pt`). A language whose features the response does not describe is left unmarked rather than marked unsupported, so the `[F]` legend cannot appear with no `[F]` beneath it.

- **tests**: A fast-check property suite (`tests/property/`) now enforces round-trip laws across all 11 format parsers — translated values survive reconstruct/extract intact, re-applying the same translations never changes the file, and an identity sync is a fixed point — plus preservation laws for the placeholder and ICU utilities. Runs are seeded-random with 200 cases per law by default (`FC_NUM_RUNS` overrides; `FC_SEED`/`FC_PATH` replay a recorded counterexample). The suite found the U+2028 TOML corruption and the `.properties` leading-space loss fixed in this release; example tests document decisions, properties enforce laws.

- **tests**: Tests that assert only inside a `catch` block now declare their assertion count, so they fail instead of passing with zero assertions when the command under test unexpectedly succeeds — the failure they exist to detect was the one they could not see. Sites that already assert on the success path are unchanged. `npm test` also refuses to run against a **stale** `dist/`, not just a missing one: the suites execute the built CLI, so a stale build reported results that did not describe the current source. A new suite checks every documented `deepl …` invocation in the README and docs against the CLI's real surface, so a command or flag that drifts out of existence fails CI rather than waiting for a reader to find it.

- **docs**: The README leads with the npm install path and marks Homebrew as pending until the tap exists. Install instructions target `@deepl/cli` (10 occurrences across `docs/SYNC.md`, four example scripts, `examples/README.md`, and the git-hook template in `src/services/git-hooks.ts`). The README installation section documents three install paths — npm (`npm install -g @deepl/cli`), from source, and Homebrew (`brew install deepl/tap/deepl`, marked pending until the tap ships) — with an explicit Node.js 24 prerequisite, replacing the `better-sqlite3` native-compilation caveat (Xcode CLT / python3-make-gcc), which no longer applies. The `TROUBLESHOOTING.md` `NODE_MODULE_VERSION` / `npm rebuild better-sqlite3` entry is replaced by accurate guidance for the one remaining cache-degradation cause (running on Node < 24). Six stale `DeepLcom` GitHub URLs now point at the `DeepL` org directly. `CONTRIBUTING.md` states the Node 24 development prerequisite, and `SECURITY.md`'s supported-versions table reflects that only 2.x is a published, supported line.

- **tests**: Removed the global manual mocks for `p-limit` and `fast-glob` (`tests/__mocks__/`). Because a manual mock for a node module is auto-applied to every suite, and `resetMocks: true` strips its implementation, `pLimit(n)` resolved to `undefined` and `fg(...)` resolved to `undefined` in all 236 suites — so no test exercised a real concurrency limit or a real glob walk, and two concurrency defects reached a release candidate undetected. The suites that need these mocked declare them explicitly with their own implementations, so nothing depended on the global versions. Added `tests/unit/concurrency-limiting.test.ts`, which asserts that `p-limit` rejects a non-positive concurrency, that peak overlap never exceeds the limit, and that `fast-glob` returns real paths — it fails if either global mock is reintroduced.

- **tests**: Suites that shell out to the bare `deepl` command now run this tree's built CLI via a PATH shim installed in jest `globalSetup`, instead of whatever `deepl` happens to be globally installed. 23 suites (392 tests) previously required a global install — absent one they all failed with `command not found`, and present one they silently tested the installed version rather than the working tree. The shim lives in the real environment before jest workers spawn (a `setupFilesAfterEnv` hook cannot do this: test code sees a copied `process.env` that child processes never inherit). CI's now-redundant `npm link` step is removed, and a new unit suite pins that `deepl` resolves to the shim and reports the tree's version.

- **tests**: `npm test` now fails fast with an actionable message when `dist/cli/index.js` is missing. `dist/` is gitignored and `npm test` does not build, yet all three test tiers execute the built CLI, so a fresh checkout previously failed hundreds of tests with errors that never mentioned the missing build.

- **tests**: Jest's haste map no longer indexes `.claude/` (via `modulePathIgnorePatterns`). A leftover agent worktree under `.claude/worktrees/` duplicated the manual mocks in `tests/__mocks__/` and made every jest run emit a `jest-haste-map: duplicate manual mock found` warning; test files in worktrees were already excluded, but module indexing was not. Verified warning-free with a worktree present.

- **BREAKING — package**: The package is now published as the scoped **`@deepl/cli`** (previously the unpublished working name `deepl-cli`). Scoped packages default to restricted visibility, so `publishConfig.access: "public"` is set explicitly — without it the publish fails. The `bin` name is unchanged: the command is still `deepl`, and scoping changes only the install string (`npm install -g @deepl/cli`). Repository, bugs, and homepage metadata now point at `github.com/DeepL/deepl-cli` directly instead of relying on the redirect from the legacy `DeepLcom` org name.

- **BREAKING — cache/runtime**: The translation cache now uses Node's built-in `node:sqlite` module instead of the `better-sqlite3` native addon, and the CLI consequently requires **Node.js >= 24** (`engines.node` is now `>=24.0.0`). Node 24 is the first release where `node:sqlite` is non-experimental; Node 18/20 lack the module entirely and Node 22 would both warn on every invocation and downgrade the bundled SQLite (3.50.4 vs 3.53.1). Existing cache databases are read in place with no migration — the on-disk format is unchanged (SQLite 3.53.2-written files verified readable, WAL mode and `user_version` stamp included). **Migration**: upgrade to Node 24 (current LTS), e.g. `nvm install 24`; no other action is needed, and the cache keeps its contents.

- **ci**: `.nvmrc` now pins Node 24, matching the CI matrix. It still read `20`, so `nvm use` handed local developers a runtime that cannot load `node:sqlite` and does not satisfy `commander`'s `engines.node >=22.12.0`.

- **build**: `npm run build` now runs a `clean` step first, removing `dist/` and `tsconfig.tsbuildinfo` before compiling. Without it, `tsc` leaves output for sources that no longer exist, so a file rename could ship stale artifacts — verified reproducible: planting a stale module under `dist/sync/` and rebuilding left both files in `npm pack` output. Removing the build-info file is required too; deleting only `dist/` makes the incremental compiler report the output as up to date and emit nothing.

- **tests**: Raised the timeout for the `watchAndSync` test block to 30s and replaced its fixed-round setup flush with a wait on an observable readiness signal. These tests intermittently exceeded the 10s default on CI runners — always as timeouts, never assertions — failing unrelated dependency PRs. Suite duration was measured to be flat across 250/25/5 flush rounds, so the historical 20 → 50 → 250 escalation could not have addressed it; the cost is runner CPU starvation (1.8s locally vs 10.8s observed on CI). The flush now also fails with the pending state rather than a bare timeout if setup genuinely stalls.

- **deps**: `commander` 14.0.3 → 15.0.0. commander 15 is ESM-only (`"type": "module"`) and requires Node >=22.12.0, so it was unmergeable until the Node 24 baseline landed. Jest's `transformIgnorePatterns` allowlist gains `commander` so ts-jest transforms it under CommonJS test execution; without that, 28 suites fail to load with `SyntaxError: Cannot use import statement outside a module`.

- **ci**: Test matrix, release workflow, and security workflow now target Node 24 (previously Node 20 and 22). Node 20 reached end-of-life in April 2026, and Node 24 is the current LTS. This aligns CI with the runtime the project is moving to; the `engines.node` range is unchanged in this entry and is bumped separately.

- **perf**: CLI startup no longer eagerly loads the HTTP client (axios) or the format-parser stack (yaml, smol-toml): the API URL constants moved to a dependency-free module, and `sync init`'s `--file-format` choices are filled lazily via a commander `preSubcommand` hook. Measured on `--version`: ~144 ms → ~80 ms median, 358 → 137 modules loaded. Help output and invalid-value errors are unchanged.

- **perf**: YAML reconstruction now indexes every string slot in a single document walk instead of calling `setIn`/`deleteIn` per key, scaling roughly linearly with file size — measured ~3.6 s → ~170 ms for a 16,000-key file. Batched deletion also fixes a correctness bug where removing several items from one sequence shifted indices mid-iteration and deleted the wrong entries.

- **batch**: Plain-text batch translation now reads, translates, and writes one API batch at a time instead of loading every file into memory up front, so memory stays proportional to a single batch rather than the whole tree. Batch grouping also measures the form-encoded body size (what the API's 128 KiB limit actually applies to) instead of raw UTF-8 bytes, so CJK-heavy batches whose percent-encoding inflates ~3x are split correctly instead of being rejected server-side.

- **sync**: Backups are written as `<file>.deepl.bak` instead of `<file>.bak`, and the stale-backup sweep considers only the `.deepl.bak` suffix — a user's own `*.bak` files are never touched again. The sweep also no longer re-creates a target file that was deleted, nor restores one over an existing file: it only ever deletes (see the Security entry below). **Migration**: `.bak` files from earlier versions are no longer swept or restored — delete leftover `<target>.bak` files manually if desired.

- **cli**: The primary human-readable reports of `sync status`, `sync validate`, `sync audit`, `sync init`, and `auth show` print to stdout, so `deepl sync status > report.txt` and `deepl auth show > key.txt` capture output instead of producing empty files. Diagnostics, warnings, and progress stay on stderr, and `--format json` stdout purity is unchanged.

- **glossary**: `create` and `show` render language codes uppercase and the creation timestamp as a locale-independent ISO string, and the create success line prints to stdout — matching the documented output instead of a locale-dependent date on stderr.

- **hooks**: The installed pre-commit hook now actually validates translations — when a `.deepl-sync.yaml` exists and the CLI is on PATH it runs `deepl sync validate` and blocks the commit on validation errors (with a `--no-verify` hint). It was previously a no-op that grepped staged files and always exited 0.

### Removed

- **sync**: **BREAKING**: `tms.auto_push`, `tms.auto_pull` and `tms.require_review` are gone from the config schema. All three were on the `tms:` allowlist and in the `tms` table in docs/SYNC.md, and **no code read any of them** — the allowlist membership was the entire reason they were tolerated, since every other unknown `tms:` field throws. Measured: a `.deepl-sync.yaml` with `require_review: [de]` passed `deepl sync validate` at exit 0 and then `deepl sync pull` replaced a hand-edited German string with the mock TMS's `"Unreviewed TMS draft"` at exit 0 — a documented safety control that did nothing and said nothing. The near-miss hint made it worse: a typo'd `auto_pushh` was answered with `Did you mean "auto_push"?`, steering the reader onto the inert key. Each now fails config load with a `ConfigError` (exit 7) that says so by name — `tms.require_review was never implemented and has been removed` — rather than as a generic unknown field, because "unknown" reads as a typo and sends the reader hunting for the right spelling of something that never existed. `require_review` is not implementable from this side: the documented export contract is a flat `{ key: value }` map with no per-entry review flag, so there is nothing to gate on; use `deepl sync pull --dry-run` to preview and review a pull instead. `auto_push`/`auto_pull` are one explicit `deepl sync push` / `deepl sync pull` away, which also keeps the credential-and-destination decision on a command someone typed — implementing `auto_push` would have made a plain `deepl sync` in a checkout you do not control ship every translated string to the `tms.server` that checkout names. `SyncTmsConfig` drops the three fields too, so a TypeScript consumer setting them stops compiling rather than being ignored at runtime.

- **cli**: **BREAKING**: The `--enable-beta-languages` flag on `translate` is gone. The API deprecated the underlying `enable_beta_languages` parameter with "has no effect" — beta languages are simply part of the regular language set now — so the flag had become a silent no-op. Scripts passing it will exit with an unknown-option error; remove the flag.

- **usage**: The dedicated "Speech-to-Text Usage" section (text output) and "Speech-to-text" row (table output) are gone, along with the `speechToTextMilliseconds*` fields they read. The API deprecated `speech_to_text_milliseconds_count`/`_limit` on `GET /v2/usage` ("Always returns 0"), so the section could only ever display zero. Voice usage remains visible in the Product Breakdown, which reads the live per-product minutes data. The Admin API's per-key `speech_to_text_milliseconds` usage limit is a different, still-current field and is unaffected.

- **repo**: The `VERSION` file and `.npmignore`. Nothing read `VERSION` — `deepl --version` reports `package.json`'s value — so it was a second, hand-edited source of truth that could only drift; use `npm version X.Y.Z --no-git-tag-version`, which updates the manifest and lockfile together. `.npmignore` was dead weight because the `files` array governs what is packed.

- **build**: Source maps and declaration maps are no longer emitted. They were already excluded from the published package, so emitting them only left dangling `sourceMappingURL` comments in the shipped files, giving library consumers unresolvable stack frames and broken go-to-definition.

- **deps**: `inquirer`, which no source file imported (see the `@inquirer/prompts` entry under Fixed).

- **deps**: `better-sqlite3` and `@types/better-sqlite3`. The production dependency tree no longer contains any native addon, removing the entire class of ABI-mismatch failures (`ERR_DLOPEN_FAILED` / `NODE_MODULE_VERSION` errors after a Node major upgrade, e.g. via `brew upgrade node`), a 1.9 MB platform-specific binary, and the C++ compilation-toolchain requirement for installs from source. The cacheless-degradation safety net remains: a runtime whose `node:sqlite` is missing (Node < 22.5.0) warns once and runs uncached rather than crashing, and never touches the cache database.

- **BREAKING — sync**: `deepl sync init --source-lang` and `--target-langs`, the deprecated aliases introduced in 1.x, are removed and now fail with `unknown option` (exit 1). Use `--source-locale` and `--target-locales`. This is the documented removal of 1.x aliases at the 2.0 cut. `deepl translate --target-lang` is unaffected — it is the API's wire name, not a deprecated alias.

### Fixed

- **sync**: **the `--format json` error envelope is machine-readable again: it moves to stdout, the stream nothing else writes to.** The envelope went to stderr, which is also where every diagnostic goes — the CLI's own warnings (the world-readable-config notice, the non-DeepL-endpoint key warning, every `Logger.warn` in a run) and anything the Node runtime emits (`(node:7016) ExperimentalWarning: SQLite is an experimental feature…`, which is exactly how three e2e tests broke on 2026-08-08: `JSON.parse(stderr)` failed at the opening `(`). A consumer capturing stderr got valid JSON only when nothing else happened to be said, and the failure path — the one case a script most needs to parse — was the one case sharing a stream. Measured before the fix: `deepl sync validate --format json` in a directory with no `.deepl-sync.yaml` and a group-readable config file wrote the mode-tightening warning **and** the envelope interleaved on stderr, with stdout empty. The envelope is the command's *result* in the failure case, so it now lands where the success payload already does; the non-zero exit code remains the failure signal, and warnings stay on stderr where they can no longer break the parse — asserted end to end with the CLI's own warning firing alongside a `JSON.parse` of the whole of stdout. `sync init`'s config-already-exists envelope, previously built inline, goes through the shared emitter and moves with it. See Changed for the migration note.

- **sync**: **`deepl sync validate` validates the rest of the project when one target file cannot be read.** A target-file parse failure propagated out of the walk and ended the whole command at exit 1 with a raw parser message (`Error: Expected double-quoted property name in JSON at position 32`, `UnknownError` in the JSON envelope) — a project with fifty locales and one corrupt file was told about the corrupt file and nothing about the other forty-nine, which is the opposite of what a validation command is for. Every other path already refuses one file and carries on. The unreadable file is now an `error`-severity issue like any other — reported under an `unusable_target` check with the file, the locale and the parser's reason, counting toward exit **8** — and every other locale and file is validated and reported alongside it. Deliberately **not** a warn-and-skip: validate exiting 0 over a file it never validated would turn CI green on an unvalidated locale, which is strictly worse than dying. A locale with no target file at all is still skipped silently, `totalChecked`/`passed` keep counting only pairs actually compared, and a healthy project's output is byte-identical. `deepl sync audit` needed no change — measured on the same fixture, it already excludes such a locale from the comparison and reports it under `missingTargets` at its normal exit code.

- **translate**: **code preservation survives a fenced block overlapping an inline code span.** The preservation passes run in sequence over already-substituted text, so a span preserved later can wrap an earlier pass's token — `` ` ``` ``…``` ` `` makes the inline pass preserve `` ` __CODE_0__ ` `` as `__CODE_1__`, and a brace-shaped span can wrap a code token the same way (`{`x`}`). Both the restore and the loss check walked the map in insertion order, so the inner token was expanded after its own pass had already run — `deepl translate --preserve-code` on that input refused the translation at exit 5 with `The translation lost the placeholder …`, blaming the endpoint for a token the CLI had nested itself, and the round-trip law (`preserve → identity-translate → restore` is the identity) failed under fast-check seed 2139537717 with three lines expected and one received. Restore now expands tokens in reverse insertion order — a stored value can only contain tokens preserved before it, so one pass unfolds every level — and the loss check counts a token as surviving when it sits inside a later span that itself survived, in the sync validator as well as the translate-path assert. The same input now translates at exit 0 with every line restored verbatim, the pinned seed replays green, and four consecutive random-seed property runs stay green.

- **sync**: **a `#, fuzzy` flag on a carried-forward PO entry survives a run that rewrites the file for a sibling key.** The comment replay in the PO writer stripped `fuzzy` from every entry it emitted, and a run is handed every key the file should keep, so any sync with other work to do silently removed a reviewer's "do not ship" marker — after which `sync status` reported the project 100% complete again and `msgfmt` compiled the questioned translation into the catalog. Measured through the CLI: flag one synced key by hand (`sync status`: `50% (1 needs review)`, the behavior the needsReview counting was built on), add one new source key, `deepl sync --yes` — the flag was gone and `status` said `100%`, at exit 0. The flag is now stripped only when the run writes **different content** over the entry — the same test the XLIFF writer applies to its review `state` — comparing the msgstr and every `msgstr[N]` against what this run writes. A carried-forward entry now keeps its comment lines byte-for-byte (a `#, fuzzy, python-format` line is no longer re-joined either), verified with a byte diff across a sync whose only work was a sibling key: the only change in the file is the appended new entry. A re-translation that produces different content still clears the flag, and `msgfmt --statistics` confirms both directions.

- **sync**: **a plural entry a run carries forward keeps its plural forms.** A carried-forward entry was handed to the file writer with the **source** file's plural payloads — empty `msgstr[N]` for gettext, source-language `<item>`s for Android XML — and plural content is rebuilt from exactly those payloads, so any run with other work to do destroyed the target's plural translations at exit 0. Measured through the CLI against a mock engine on three paths. **Translate**: a PO project holding a translated plural entry had `msgstr[0]` / `msgstr[1]` emptied by a sync whose only work was one new sibling key — `msgfmt --statistics` went from `3 translated messages` to `3 translated, 1 untranslated` — with the run misreporting its own destruction as `could not be given 1 translated key … the target file has no element to hold it` and the next sync re-translating and **re-billing** the entry. Android XML was worse: reviewer-corrected items (`Un archivo` / `Muchos archivos`) were silently reverted to the English source (`One file` / `Many files`) with no warning at all, because the reverted values are non-empty and the write-verification saw the key as present. **Validation withholding**: a stale plural entry whose fresh translation failed validation was supposed to keep what the file holds and emptied its forms instead. **Pull**: any `deepl sync pull` that rewrote a PO file emptied plural forms whether or not the export carried the plural key. The carry-forward sites and the pull merge now omit the plural payloads from what they hand the writer, so the parsers keep the file's own forms, and Android's writer keeps a `<plurals>` element verbatim for an entry handed over without per-form translations — a key absent from the entry list is still deleted. A plural entry whose source text actually changed is still re-translated with fresh forms. See docs/SYNC.md "A plural entry carried forward".

- **sync**: **an XLIFF review `state` is no longer counted as a finished translation.** `<target state="needs-review-translation">` in 1.2 and `<segment state="initial">` in 2.0 mean a translation exists but is not approved; every read path took the `<target>` at face value, so a project shipping unapproved strings reported itself done. Measured end to end on a two-unit project through the CLI, in both versions: after flagging one unit with its source unchanged, `deepl sync status` said `100% (0 missing, 0 outdated)`, `--format json` said `needsReview: 0` and `complete: 2`, `sync validate` said `All translations passed validation` and `sync --dry-run` said `2 current`. The same project now reports `50% (0 missing, 0 outdated, 1 needs review)`. `deepl sync push` skips such a unit under the existing `needs_review` reason instead of uploading it as approved. The states are read as an explicit claim only: 1.2's `new` and `needs-*` values and 2.0's `initial` count, `translated` / `signed-off` / `final` / `reviewed` do not, and an **absent** attribute or a value outside those sets counts as complete — which is why an existing project's coverage does not move. In particular 2.0's documented `initial` default is deliberately not applied to a segment that carries no `state`, since that is the shape the CLI itself writes. `state-qualifier` (1.2) and `subState` (2.0) are different attributes and are not read. Nothing is re-translated, rewritten or re-billed; both ways out were measured — changing the state to `translated` returns the key to `complete` with **no API call**, and emptying the `<target>` has the next `deepl sync` translate it afresh.

- **sync**: **a `state` attribute on an XLIFF target the CLI has just written now describes what the CLI wrote.** A source XLIFF exported with `<target state="needs-translation"></target>` placeholders — what most CAT tools produce — yielded a target file whose every unit claimed it still needed translating about a string the CLI had just translated, in both versions (2.0 kept `<segment state="initial">` around a filled-in target). The file contradicted itself, any consumer reading `state` would ignore or re-request work already paid for, and with the counting above every one of those keys would have reported as needing review forever. Such a state now becomes `translated` when reconstruct replaces the target's content, and a `signed-off` state the CLI writes over is downgraded the same way rather than claiming human approval for machine output. An element carrying no `state` still gains none, and a `state` on a unit whose translation is **unchanged** is never touched — which is what keeps a reviewer's `needs-review-translation` alive through a run that translates a sibling key, verified on the real write path.

- **watch**: **two watched files with the same name no longer write one translation on top of the other.** The output path was built from the source's basename alone, so every `doc.md` under the watched tree mapped to one `<output>/doc.es.md` and the last translation to finish silently replaced the ones before it — the whole of the losing file's translated output gone, at exit 0, with no warning and nothing in the summary to notice: the count still read `Translations: 2`. Measured on a watched tree holding `a/doc.md` ("Hello") and `b/doc.md` ("Good morning") with `--to es`: `translateFile` was called twice with the same `out/doc.es.md`, `out/` held one file, and its contents were `b/doc.md`'s translation. The output now carries the source's directory relative to the watched path, so those two write `out/a/doc.es.md` and `out/b/doc.es.md` — both texts, at 2 API calls, unchanged from before. The same flattening ran on **three** paths, not the one: the single-target path built the name itself, and the multi-target path (`--to es,fr`) handed a bare output directory to `FileTranslationService.translateFileToMultiple` for text files and to `StructuredFileTranslationService` for JSON and YAML, each of which then applied the same basename rule. All three now take the per-source directory. Verified end to end through the CLI against a mock API with the **default** output directory (`<watched>/translations`, which sits inside the watched tree): both translations landed under their own subdirectory, `translateCalls` settled at 2 with no further activity, so the loop guard still recognises a nested output as the CLI's own work and does not re-translate it. The layout is what `deepl translate <dir> --output <dir>` already produced — measured on the same fixture, which wrote `out/a/doc.es.md` and `out/b/doc.es.md` — so watch was the one command flattening. See Changed for the paths that move.

- **watch**: **the loop guard no longer warns about the temp file the CLI is writing through.** `atomicWriteFile` renames from a `<target>.tmp.<pid>.<random>` sibling, which has to sit beside its target because a rename is only atomic within one filesystem — so a watcher on the output directory sees it appear and vanish. Its name carries the output file's, so the output-file check matched it and the session printed `Skipping …/doc.es.md.tmp.4242.a1b2c3: it is inside the output directory and named like a translated output … Move it outside …` about a file that this process had already renamed away, telling the user to move something that no longer exists. Such a path is now recognised as an in-flight write and ignored, before the output-file check. A real output-looking file the user put there still gets its one warning.

- **sync**: **`sync status` counts a failed translation as `missing` rather than `outdated`.** `outdated` is documented as "recorded against an older source"; a failed attempt is recorded against the **current** source and produced no translation at all, so the count named the wrong problem — a reader chasing an outdated string would go looking for a source change that never happened. `missing` and `outdated` therefore both move for a project with failed translations in its lockfile. Nothing else changes: `--frozen` computes its own gating from the source diff and is unaffected, and a genuinely stale hash is still `outdated`.

- **sync**: **a gettext `#, fuzzy` translation is no longer counted as complete.** Every read path treated the msgstr of a fuzzy entry as a finished translation, but `fuzzy` is gettext's way of saying "needs review, do not use": `msgfmt` leaves the entry out of the compiled catalog, so the string the CLI called done is one the application does not display. Measured against that oracle on a two-key PO catalog with one entry flagged and its source unchanged — `msgfmt --statistics` said `1 translated message, 1 fuzzy translation` while `deepl sync status` said `100% (0 missing, 0 outdated)`, `complete: 2`, `unwritten: 0`, `sync --dry-run` said `2 current`, `deepl sync` made **0 requests**, and `sync validate` said `All translations passed validation`. So a project shipping an untranslated string reported as finished, indefinitely. Such a key is now its own **`needsReview`** category in `sync status` (text suffix `, 1 needs review` plus a line explaining the flag and both ways out; `needsReview` on each locale in `--format json`), and the same catalog now reports `50%`, agreeing with `msgfmt`. `deepl sync push` skips it under a new **`needs_review`** skip reason instead of uploading a reviewer's draft as an approved translation. **Nothing is re-translated and nothing is rewritten**: the value belongs to whoever flagged it, so reading it as untranslated would have replaced a human's in-progress work with machine output and re-billed every fuzzy entry in the project — the one outcome worse than an overstated percentage. Both documented remedies were measured end to end: removing the flag returns the key to `complete` (`msgfmt`: `2 translated messages`), and clearing the msgstr has the next `deepl sync` translate it afresh. `sync --frozen` deliberately still passes, since a fuzzy entry is a normal transient state in a gettext workflow that only a human review clears. XLIFF's `state="needs-review-translation"` is the same idea in the other bilingual format and is tracked separately: its states differ between 1.2 and 2.0 and no external tool arbitrates which of them mean "will not ship", where `msgfmt` settles it for PO.

- **sync**: **`--dry-run` now previews the run rather than the lockfile, in both directions it was wrong.** The dry-run branch returned before the two target-file checks the real run makes, so the estimate came from the lockfile alone. Measured against a real endpoint on a JSON project with one damaged locale. **Under-reporting:** with a key the lockfile calls translated deleted from the target file, `deepl sync --dry-run` reported `Sync complete: 2 current`, `estimatedCharacters: 0` and no cost line at all, while the very next real run translated it — `✓ es: 1/1 keys`. **Over-reporting:** with a new source key added and the target file left unreadable, dry-run reported `estimatedCharacters: 12` and `ok: true` at exit 0, and said nothing about the file; the real run refused the locale, billed **0**, reported `failed: 3` and exited **12**. So the one command whose job is deciding whether to spend money under-quoted repair work and over-quoted work that was never going to happen. Both halves now come from one `findTargetGaps` call per source file — the machinery `--frozen` already uses, which returns the missing keys and the unreadable reason from the same read: keys the target no longer holds are added to the estimate and reported as `unwrittenKeys`, and a locale whose target file is unreadable is left out of the estimate and named in its own warning ending `It is left out of the estimate below. Fix it before running \`deepl sync\`.` A dry run still writes nothing — no target file, no lockfile, no backup — and still exits 0, since it reports what a run would do rather than standing in for its exit code, which is what `--frozen` is for. Because the summary counts a repair key as `current`, the run now also says `1 key is recorded as translated in the lock file but could not be confirmed in the target file, so a real run would translate it again`, so the character estimate is not a number with nothing behind it. **The bead's suggested cheap option was based on a wrong premise**: warning about an unreadable target "without paying for a full audit" costs exactly the same reads, because a file cannot be known to be unreadable without opening it, and the gap keys fall out of that same read for free. **Cost, measured** on a 20,000-key, 6-locale JSON project (2.83 MiB source, 17.3 MiB of targets, 24 MiB lockfile): `--dry-run` 0.44 s → 0.75 s, against 0.77 s for `sync status` and 0.79 s for `sync --frozen`; peak RSS 283 MiB → 370 MiB. A locale the lockfile claims nothing for is not read at all, so a project mid-first-sync pays nothing.

- **sync**: **the `sync.max_characters` cost cap no longer under-counts the work it is meant to cap.** Its preflight estimate came from the same lockfile-only arithmetic as `--dry-run`, so repair work was invisible to it: on a fixture whose lockfile claimed ten translated keys for a locale with no target file at all, plus a newly added locale, the cap computed **500** characters for a run that bills **1,000** — a cap set at 500 let it through. The cap and `--dry-run` now quote from one function, so a run the preview prices above the cap is a run the cap refuses. This costs one pass over the target files before the cap decides, where it previously decided without reading anything: measured on the fixture above, a translating run went from 1.54 s to 1.91 s against a local mock, where no network latency dilutes the fraction. Projects that do not set `max_characters` are unaffected.

- **sync**: **`--frozen` no longer reads every target file twice.** On a project with no drift the target-versus-lockfile comparison ran once for the drift check and again for the "nothing left to do" check, since each call started a fresh audit. The answer is now computed once per source file and reused, which took `sync --frozen` from 1.13 s to 0.79 s on the 20,000-key, 6-locale fixture above and cut its peak RSS from 469 MiB to 382 MiB. No output changes.

- **watch**: **`--git-staged` now matches its files when the watched path reaches the repository through a symlink.** Two spellings of one path were compared: the staged set is built from `git rev-parse --show-toplevel`, and git always answers with the repository's **real** path, while the watcher compared the path the user typed. Where those differed by a symlinked ancestor, no watched file was ever in the staged set. Measured with the built CLI at e97d835 against a real endpoint, started from the repository root so the working-directory fix above does not apply: `deepl watch /tmp/link/src --to de --git-staged` over a symlink to a repository with one staged file reported `Git-staged files: 1`, printed `Watching for changes...`, and then ignored every edit for the rest of the run — no `Change detected`, **0 translate requests**, empty output directory, **exit 0** — where the same session watching the real path translated the file and wrote `a.de.md`. macOS reaches this with no symlink of the user's own, since `os.tmpdir()` is `/var/folders/…` symlinked to `/private/var/folders/…`, as does any project under a symlinked checkout root. The same two-spellings defect had a **second, independently measured site**: the loop guard's warn-once bookkeeping also compared unresolved paths, so a session whose output directory is reached through a symlink warned `Skipping …/link/src/translations/a.de.md: it is inside the output directory and named like a translated output … Move it outside …/repoA/src/translations to have it translated` about a file **the CLI had just written itself** — a message naming two different spellings of one directory, telling the user to move their own output. Both sites now compare a canonical key with symlinked ancestors resolved and the final path component left alone: a staged file that is itself a symlink is the file git tracks, not its target, so resolving the last component would have broken a case that worked. Messages still show the path as the user spelled it; only the comparison keys are canonical. After the fix the same symlinked session reports `Change detected`, issues 1 translate request and writes `a.de.md`, and the mirror case writes its output with no warning at all.

- **watch**: **`--auto-commit` and `--git-staged` now act on the repository holding the files they name, not on the directory the CLI was started in.** Every git invocation behind both flags ran with no working directory of its own, so watching a path outside the current repository handed one repository's pathspecs to another's index. Measured with the built CLI over two real repositories and a real endpoint. With the terminal in an unrelated repository, every translation failed to commit with `fatal: .../repoA/out/doc.de.md: '.../repoA/out/doc.de.md' is outside repository at '/private/.../repoB'` — one counted auto-commit failure per translated file, the session exiting 12, and the translation left untracked. With the watched repository nested inside the one holding the working directory, `git add` silently did nothing at all, because git does not descend into another repository, and the commit then failed with `error: pathspec '.../out/doc.de.md' did not match any file(s) known to git`. With the working directory in no repository, the session printed `⚠️  Not a git repository, skipping auto-commit` — untrue, the watched path was one — and **exited 0** having committed nothing, which is the silent half. No case committed into the wrong repository's history: git refuses a pathspec outside its own working tree, so the defect was that the flag could never work rather than that it worked somewhere else. **`--git-staged` was the more reachable half, and failed silently inside a single repository with no unusual layout at all.** `git diff --cached --name-only` names its files relative to the repository root, and the result was resolved against the process working directory, so `deepl watch ./docs --git-staged` started from any subdirectory reported `Git-staged files: 1`, printed `Watching for changes...`, and then matched nothing for the rest of the session: every edit to the staged file ignored, no translation, no output, exit 0. Started from another repository it read that repository's index instead and stopped at `No git-staged files found. Nothing to watch.` Both flags now resolve their repository from the path they act on — `git rev-parse --show-toplevel` anchored on the output directory for the commit, and on the watched path for the staged snapshot, with every staged name resolved against that repository's root. Output paths are made absolute before the working directory changes, so a relative `--output` still commits the file it wrote: `deepl watch ../repoA/src --output ../repoA/out --auto-commit` run from a sibling repository now commits `out/doc.de.md` into repoA at exit 0 and leaves the CLI's own repository untouched, as does the same session run with absolute paths, from a non-repository directory, or over a nested repository.

- **sync**: **`sync resolve` no longer warns about possible data loss on every ordinary lockfile merge.** The lockfile's own metadata was the one part of the file where git could produce a conflict region that is not a whole anything. `stats` sits two context lines below `generated_at`, and every write changes both, so git joined them into a single region — which, with `stats` expanded over five lines, opened inside `stats` and closed outside it. That is not a member list, so `JSON.parse('{' + region + '}')` failed, the region fell to the length-heuristic fallback, and the resolver emitted `WARN .deepl-sync.lock:<conflict-region> — parse-error fallback used, JSON.parse failed on ""generate…"` and picked a side by byte length. Measured over a real `git merge` of real serializer output: it fired in every case where both branches had run a sync, including the most common one of all — two branches translating **different** keys, where git merges the entries map perfectly and there is no real conflict at anything — which reported `Resolved 1 conflict (0 theirs, 0 ours, 1 length-heuristic)`. Since the docs tell the reader a `length-heuristic` decision is a data-loss risk to inspect by hand, the one signal that exists to make silent data loss auditable fired spuriously on every single resolve, and a warning about a region that really did carry a translation was indistinguishable from the routine noise. **`stats` is now written on one line**, like a translation and for the neighbouring reason — its counts and `last_sync` describe one sync run — so the region stays a member list and merges normally: the same fixtures now report `generated_at` and `stats.last_sync` as ordinary per-member decisions with no warning at all. Nothing was lost while the fallback was picking sides, as it happens: `total_keys` and `total_translations` are recomputed from `entries` on every read and `generated_at` is overwritten on every write, so the block it was arbitrating carries no information — which is exactly why warning about it was wrong. Upgrading reformats every existing lockfile on the next write; it is formatting only, five lines becoming one, and no entry's content changes.

- **sync**: **`sync resolve` no longer merges a translation field by field when one side is missing `translated_at`, which produced an entry that existed on neither branch.** Measured over a real `git merge` of real serializer output: ours held `{"hash": "human_hash", "review_status": "human_reviewed", "status": "translated"}` and theirs `{"hash": "machine_hash", "review_status": "machine_translated", "translated_at": "2026-08-03T15:00:00.000Z"}`; the resolver wrote `{"hash": "human_hash", "review_status": "human_reviewed", "status": "translated", "translated_at": "2026-08-03T15:00:00.000Z"}` — ours' hash and review status carrying theirs' timestamp — reported as three per-field decisions and exit 0. That is precisely the fabrication the one-line lockfile format exists to prevent, performed by the resolver after git had correctly raised the conflict. The cause was the translation predicate: it recognised a leaf by `translated_at`, or failing that by `source_hash`, which belongs to the *entry* around a translation and not to the translation itself, so a translation whose only remaining identifying field was `hash` was not recognised and fell through to the generic member-by-member merge. Nothing validates `translated_at` on read — the shape survives a lockfile round trip untouched — and `human_reviewed` is only ever set by hand, so a hand-edited entry is the reachable path. A translation leaf is now identified by `hash` as well, and **one side being one is enough**: a pair is arbitrated whole whenever either side looks like a translation, so no field combination can be invented regardless of how degraded the other side is. **Two decision reasons also stated things that were not true.** Equal timestamps reported `kept ours: newer translated_at 2026-08-04T10:00:00.000Z` when neither side was newer — now `kept ours: same translated_at <stamp> on both sides`. And a pair where *ours* had a timestamp and theirs did not fell to the terminal branch and reported `kept ours: neither side had translated_at` — now `kept ours: theirs had no translated_at`, with the mirrored case worded to match. A `translated_at` that is not a string now counts as absent rather than being compared against an ISO timestamp, so a lockfile committed by another tool cannot steer the tie-break with a non-comparable value.

- **sync**: **a TMS that cannot be reached is a network failure (exit 5), not an unclassified one (exit 1).** `fetch` rejects with a bare `TypeError: fetch failed` and puts the errno on `cause`, and the request loop threw that rejection as it stood, so the run ended at `Error: fetch failed` — no host, no port, no code, no remediation — and at the exit code `docs/API.md` tells CI to read as "the CLI crashed, investigate". Measured with the built CLI on three shapes: a refused connection to a port with nothing listening and an unresolvable hostname both exited **1**, while a server that accepted the connection and never answered exited **5** with `TMS request timed out after 1500ms: PUT http://127.0.0.1:60423/…` and a suggestion — the same condition, differently timed, reported two different ways. All three now exit 5 and name the request: `TMS request failed: PUT https://tms.example.com/api/projects/p/keys/greeting: ECONNREFUSED`, plus a line pointing at the `server:` URL in the `tms:` block. Everything the request loop catches is a transport failure by construction — the fetch call is all it awaits, and every response-level outcome is judged after it returns — so the classification needs no code allowlist; an error that is already a `NetworkError` keeps its own message, and a 401, a 500 and a timeout each keep theirs, with a guard apiece. **The replay policy is deliberately unchanged**: retry eligibility is decided before the error is classified, and both counts are asserted — a refusal is still retried to `tms.retry.max_attempts` (3 calls), an unresolvable name still fails on the first (1 call). While measuring this, note that `http://127.0.0.1:1` is not a usable repro: `fetch` refuses port 1 as a blocked port with `cause.message: "bad port"` and no code, before any connection is attempted.

- **sync**: **`TMS server URL must use HTTPS` now says which spellings are waived and how to reach a local TMS.** Plain `http://` is accepted for `http://localhost` and `http://127.0.0.1` only — the same pair the DeepL API base URL waives — so a developer whose `.deepl-sync.yaml` named `http://[::1]:3000` got a one-line refusal at exit 7 with no way to act on it. The rule is unchanged; the error now echoes the URL and points at `http://localhost`, which was measured to reach a server bound to `::1` only (HTTP 200 through the CLI, the `::1`-bound server logging the `PUT`) as well as one bound to `0.0.0.0` or `127.0.0.1`, so it covers every local bind rather than being a partial answer. The waiver was deliberately **not** widened: it would make this rule more permissive than the one for `--api-url`, `0.0.0.0` is not a loopback address, and `127.0.0.2` is not bindable at all without aliasing the loopback interface (`EADDRNOTAVAIL` on macOS). `http://0x7f.0.0.1`, `http://127.1` and `http://2130706433` were already accepted, contrary to the finding: the URL parser normalizes all three to `127.0.0.1`, which four new tests pin so the change cannot widen the gate. The destination-trust gate still does not exempt loopback at all, and answers a different question.

- **sync**: **a target file that cannot be read is left alone instead of being re-translated and overwritten.** The pre-read of each locale's target file swallowed every failure into "this locale has no existing translations", which cannot tell a locale that has never been synced — nothing to lose — from one whose file is on disk and unreadable, which holds the only copy of its translations, since the lock file records hashes rather than translated text. Measured end to end against a mock endpoint, on a healthy two-key JSON project whose `locales/es.json` was then given a flat `"menu.save"` beside a nested `"menu": {"save": …}`, the `.`-separator collision a bad merge produces and the JSON parser refuses: `deepl sync --yes` printed `✓ es: 2/2 keys` and `Sync complete: 2 current` at **exit 0**, made 1 billable translate request where a healthy repeat run makes 0, and rewrote the file as `{"greeting": "Hola", "added": "Traduceme"}` — both hand-reviewed translations replaced by fresh machine output and the file's two other keys deleted — with nothing in the output naming the file. The same happened with the source changed as well (2 requests, exit 0), so this was not an artefact of the `unwritten` repair path added earlier in this release, and the same happened to a file present but unreadable (`chmod 000`), which was rebuilt from the source template and kept its mode, so the damage was not even visible afterwards. The reach is wider than one format: of the parsers that can refuse a file, `json`, `laravel_php` and `android_xml` each have a `reconstruct` that accepts a template its own `extract` rejects and rebuilds it silently, while `po` and a JSON syntax error happened to fail loudly in `reconstruct` — but only after the whole locale had been re-billed. `ENOENT` is now the only read failure that means "absent". Any other errno, and any parse failure, marks that locale unusable for that file **before any translation is requested**: the run prints `Sync failed for locale "es" on "locales/en.json": target file locales/es.json is on disk but could not be read (<reason>) — it holds the only copy of this locale's translations, so it was left as it stands rather than rebuilt from the source. Fix it, then run `deepl sync` again.`, reports `✗ es: 0/2 keys`, exits **12**, bills **0** characters, and leaves the file byte-identical. A key the source has just gained is recorded `failed` rather than `translated`, so the next run retries it once the file is fixed. `deepl sync pull` had the same conflation with a carve-out for one cause (a key collision, added earlier in this release) and now routes every unreadable target to the same outcome: measured on a target file holding git conflict markers, pull printed `Pulled 1 translations` at exit 0 having replaced it with `{"greeting": "TMS-Hola"}`, discarding the local-only key the export does not carry; it now leaves the file byte-identical and records a new `unusable_target` skip reason. `deepl sync push` needed no change — it already propagates every error but `ENOENT`, which is the distinction this fix generalizes. One reader (`readTargetFile`) now answers absent / usable / unusable for all four call sites, and costs no extra I/O: it replaces a read that was already being made.

- **sync**: **`sync status` no longer says the keys of an unreadable target file "are not in the target file", nor tells you to sync again.** Both halves of that sentence are wrong for a file nobody managed to open — its contents are unknown, and `deepl sync` now refuses to rebuild it — so the advice bounced the user between a `status` that said to run `sync` and a `sync` that declined. The count is unchanged, since a file whose contents are unavailable still cannot be shown to hold what the lock file claims; only the reporting is: such a file gets its own sentence naming it and the reason (`2 keys are recorded as translated in the lock file for a target file that could not be read — es: locales/es.json (JSON: 'menu.save' is the key of two different strings. …). Fix the file: \`deepl sync\` will not overwrite it.`), and a project with both kinds of gap gets both sentences rather than one that conflates them. `--format json` carries the reason as a new `unusable` field on the locale's `unwrittenByLocale` entry, absent when the file was read and genuinely lacks the keys. The `--frozen` drift line no longer asserts a cause it has not checked either, and points at `sync status` for the detail.

- **sync**: **a target file that has lost translations the lock file records as translated is no longer reported as 100% complete.** Nothing compared the two: `deepl sync status` and `deepl sync --frozen` both diffed the SOURCE file against `.deepl-sync.lock` and never opened the target file, and `deepl sync` itself returned early whenever the lock file said there was nothing to do. Measured end to end on a healthy two-key project with one key's line deleted from `locales/es.properties` by hand: `sync status` printed `es [####################] 100% (0 missing, 0 outdated)` at exit 0, `sync --frozen` printed `Sync complete: 2 current` at exit 0, and `sync --yes` printed `Sync complete: 2 current` at exit 0 having written nothing — indefinitely, on every run. This is the residual half of the key-dropping finding fixed earlier in this release: the writers no longer drop keys, but a project already damaged by the old behaviour was not repaired by upgrading, and the workaround was to add a string and sync or delete the target file. It is not specific to that, either — a bad merge, a partial checkout, a hand deletion or a `git checkout` of an older locale file all read as complete, and `--frozen` is the CI drift gate whose entire purpose is catching a locale that is not up to date. For every key the lock file records as `translated` against the current source text, the locale's target file is now read and checked. A key it does not hold is counted **`unwritten`** — its own category, distinct from `missing` (absent from the lock file) and `outdated` (recorded against an older source), never counted as complete — so the same project now reports `es [##########..........] 50% (0 missing, 0 outdated, 1 unwritten)` plus a line naming the file and the key, `--frozen` exits **10** naming the count, and `sync` translates the key again and writes it. A target file that cannot be read or cannot be parsed counts all of its claimed keys, which also closes the pre-existing hole where any target-file parse failure read as "no existing translations". Two exemptions, both deliberate: a key whose **source value is empty** is never reported, because an empty source can only produce an empty translation and PO and XLIFF read an empty translation side as untranslated on purpose; and a key already recorded `failed` or against an older hash is not counted twice. `sync` is **not** made to rewrite target files to force agreement — the narrow action is to stop reporting complete and let the existing re-translation path run. **Cost, measured before adopting** on a 2.8 MiB XLIFF source with 20,316 keys across 6 locales (52 MiB of files): `sync status` 410 ms → 660 ms and 207 → ~307 MiB peak RSS; `sync --frozen` 465 ms → 970 ms and 216 → ~365 MiB. The read is skipped entirely for a locale the lock file claims nothing for, and a run that has translating to do never triggers it, since it reads every target file a few lines later anyway. New JSON fields on `sync status`: `unwritten` per locale and a top-level `unwrittenByLocale`; new field `unwrittenKeys` on the sync result.

- **sync**: **a PO catalog written without blank lines between its entries is no longer collapsed into one entry.** The blank-line separator is a gettext convention, not a requirement — `msgfmt -c` exits 0 on every fixture below — but both halves of the PO parser treated it as the only thing that ends an entry, and the damage was total. Measured on a legal five-message catalog with no separators at all: `extract` reported **one** key (`Third`, the last one), so `Hello` and `Bye` were absent from the source key set entirely, and `reconstruct` wrote that single translation into **every** `msgstr` it walked past, the header's included — `msgstr ""` plus `"Content-Type: text/plain; charset=UTF-8\n"` and `"Plural-Forms: nplurals=2; plural=(n != 1);\n"` became `msgstr "[T]Third"`, and `msgfmt -c` on the output then warned `Charset missing in header. Message conversion to user's charset will not work.` Four more shapes were measured, none of them named in the original report: a catalog whose entries carry `#:` comments silently **lost** the whole first entry from the output; an obsolete `#~` run between two messages **deleted the header outright**, at which point `msgfmt -c` failed the output with `PO file header missing or invalid` (exit 1); a plural entry lost its `Plural-Forms` rule and failed `msgfmt -c` with `header entry lacks a "plural=EXPRESSION" attribute`; and `extractTranslations` — the bilingual target read used by `sync`, `push`, `pull`, `validate` and `audit` — reported only the last entry as translated, so every other reviewed `msgstr` looked untranslated and was re-translated and re-billed on every run. An entry now ends where gettext ends it: at the first line that is not a continuation of its translation, i.e. a comment, a `msgctxt`, or the next `msgid`. **Both the reader and the writer needed it** — they scan entry blocks independently, and each was proven to be insufficient alone with its own control: with only the writer fixed the header survives but the key set is still one entry; with only the reader fixed the keys are right but the header is still destroyed. All six catalogs now pass `msgfmt -c` on both input and output, keep their charset and plural rule, and are a fixed point across three successive syncs. Layout is untouched: a catalog that arrived without separators keeps that shape. The blank-line-separated form, multi-line `msgid`/`msgstr` continuations and plural entries are all unchanged.

- **http**: **a response the endpoint cuts off mid-body is reported as a network failure (exit 5), not as invalid input (exit 6).** axios attaches the 200 response to the error it raises for an aborted response stream, and `classifyError` let the mere presence of a response decide: it took the HTTP-status branch and returned `ValidationError('API error: stream has been aborted')`, telling the operator to check input that was never the problem. Reproduced against a stub that declares a `Content-Length`, writes 12 bytes of the body and destroys the socket: `deepl translate "Hello" --to es --max-retries 3` printed `Error: API error: stream has been aborted` at **exit 6**, and `deepl usage` the same. Both now exit **5** with `Network error: the API answered HTTP 200 but its response body did not arrive intact: stream has been aborted`. The test is the status, not the axios code or message: a rejection carrying a 2xx response can only have failed while the body was read, whereas the code varies with how the peer failed (`ERR_BAD_RESPONSE` for an aborted stream, a socket or zlib code otherwise) — both the `Content-Length` and the chunked truncation shapes were measured to confirm it. 3xx, 4xx and 5xx responses keep the classification they had. **The replay policy is deliberately unchanged**, contrary to the finding's framing: the request counts were measured before and after and are identical, 1 for the POST and `--max-retries + 1` for the GET. A 200 means the server accepted — and may have billed — the request, so replaying the billable POST is exactly what must not happen here; the idempotent GET was already being replayed, so the "never retried" half of the report did not hold. The client-side deadline path is untouched: it still restates its own aborts as `ETIMEDOUT` before classification, so both routes end at `NetworkError`.

- **sync**: **the startup stale-backup sweep no longer deletes a crashed run's backup, so recovery is no longer limited to the five minutes after the crash.** `deepl sync` refuses to overwrite an existing `<target>.deepl.bak` (`COPYFILE_EXCL`, warn, leave it alone) precisely because after a `kill -9` that backup holds the only surviving copy of the user's translations — but the sweep runs first, at startup, and unlinked every `.deepl.bak` older than `sync.bak_sweep_max_age_seconds` (default 300) without looking at its content, which left that guard nothing to collide with. Reproduced end to end against a mock endpoint: with `locales/de.json` holding machine output, `locales/de.json.deepl.bak` holding `"HUMAN TRANSLATION"`, no lockfile, and the backup's mtime backdated ten minutes, `deepl sync --yes` reported `✓ de: 1/1 keys`, `Sync complete: 1 new`, **exit 0**, and the human translation existed nowhere in the project afterwards — the same harm the `COPYFILE_EXCL` guard was added to prevent, reached around it. The identical run with the backup dated ten **seconds** earlier kept it and warned, which is what made age the whole of the bug. A stale backup is now deleted only when the file beside it already holds the same bytes: a run that reaches its end unlinks its own backups, so one still on disk is from a run that did not, and there it is the last copy of whatever that run had already overwritten. Size is compared first and the contents only when the sizes agree, so the common case (no backup at all) costs one `readdir` as before. A backup whose target has diverged, or whose target is gone, is kept however old it is and reported once per sweep, naming the file: `Keeping 1 leftover backup file whose content is not in the file beside it: locales/de.json.deepl.bak. It is from a run that did not finish, so it may hold the only copy of translations that run overwrote.` Retention is bounded at one file per target, since the backup's name is derived from the target's, so this cannot accumulate. `bak_sweep_max_age_seconds` keeps its meaning for redundant backups and no longer sets a deadline for recovering a crashed run. The fix is in `sweepStaleBackups`, which every caller shares — `deepl sync`, `sync push`, `sync pull`, `sync export` and `sync --watch`'s startup sweep. Three tests asserted the old policy by giving a stale backup no sibling or a differing one; those fixtures now say which case they mean.

- **sync**: **`sync resolve`'s merge is no longer erased by a concurrent sync, and no longer risks truncating the lockfile.** The process lock was honoured by exactly two call sites — `deepl sync` and `deepl sync pull` — and `sync resolve` took none, while writing the lockfile with a plain `fs.writeFile` rather than the rename every other lockfile writer uses. Measured through the real CLI with a slow sync holding the lock: a second `deepl sync` was correctly refused at exit 7, while `deepl sync resolve` **proceeded**, reported `Resolved 1 conflict` and wrote the merged lockfile at exit 0 — and when the sync finished (also exit 0) the merged entry was gone, because the sync had read the pre-merge lockfile at startup and wrote its whole in-memory copy at the end. Both steps reported success, so the merge-conflict recovery path lost data silently. `sync resolve` now takes the lock — `--dry-run` included, matching `sync pull` — and exits 7 with the same "Another `deepl sync` process is running" message while one is held, leaving the conflict markers in place for after the sync. Its write goes through the atomic rename, so a crash part-way through leaves the previous lockfile instead of a truncated one; a truncated lockfile reads as corrupt and is replaced with an empty one, which costs a full re-translation of the project. And because a hand edit, a `git merge` or another tool takes no lock at all, a run whose lockfile changed on disk between its read and its write now says so and still records what it did — warning rather than refusing, since by that point the target files are written and the translations billed, and declining to record them would bill every one of them again on the next run.

- **watch**: **`--auto-commit` no longer loses most commits under an edit storm.** `WatchService.onTranslate` was typed `=> void` and called without `await`, so the async callback the watch command supplies — the one that awaits `autoCommit` — had its promise discarded. The git work therefore ran outside the translation's concurrency slot, unbounded and untracked, and git holds `.git/index.lock` for the duration of an `add` or a `commit`, so parallel auto-commits knocked each other out. Measured through the real CLI in a real repository, six watched files edited at once with a 300 ms stub delay: **6 translations, 2 commits, 4 auto-commit failures** (three `git add` and one `git commit`, all lock contention), three output files left untracked and a fourth left staged but uncommitted — where an unrelated later commit would have swept it in. The session still exited 0. `onTranslate` may now return a promise and it is awaited, so the callback runs inside the translation's slot and a rejection reaches `onError`; the git work is additionally queued one `add`/`commit` pair at a time. Same harness after the fix: **6 translations, 6 commits, 0 failures**, nothing left untracked or staged. Translations of different files still run in parallel — only the git step is serialized.

- **watch**: **a source file whose name carries a target-language segment is translated instead of being skipped for the whole session.** The loop guard that stops the CLI's own output re-triggering the watcher matched on the *name* alone, anywhere under the watched path, so `pricing.es.md` under `--to es` was silently dropped: measured through the real CLI, no request, no output file, and not even a `📝 Change detected` line, while `plain.md` in the same directory translated normally. Every file the watcher writes lands in the output directory, so the guard now also requires the file to be *inside* it — which leaves the loop protection complete and lets any such file outside it through. Verified on the same harness: `pricing.es.md` now produces `out/pricing.es.es.md`, and pointing `--output` at the watched directory still translates `doc.md` to `doc.es.md` exactly once with no further request. In that same-directory layout a file the CLI did not write is still skipped — the name is genuinely ambiguous there — but now says so once per file instead of doing nothing, naming the file and the output directory to move it out of. The CLI's own writes are skipped in silence, since that is the guard working.

- **watch**: **a slower translation of older content no longer overwrites a newer one, leaving the output permanently stale.** `deepl watch` dropped its debounce bookkeeping when the timer fired rather than when the translation finished, so an edit arriving during an in-flight translation started a *second* translation of the same file; `--concurrency` (default 5) let both run, and both wrote the same output path in API-completion order. Measured through the real CLI against a mock endpoint answering the first request after 6000 ms and the second after 200 ms: request 1 carried `VERSION-A`, request 2 carried `VERSION-B`, the newer translation was written first and the older one then overwrote it, leaving `out/doc.de.md` holding the translation of the **pre-edit** source at exit 0 with two `✓ Translated` lines and no warning. Nothing recovers from that state on its own — the file will not change again, so no further watch event ever fires. A file is now translated one version at a time: an edit arriving while its translation runs queues exactly one re-translation, which starts only after the running one has written, so the last write is always the newest source. Verified on the same harness, where request 2 is now issued after response 1 and the file ends as the translation of `VERSION-B`. Coalescing also collapses an edit storm: six edits during one slow translation cost **7 API calls before and 2 after** (the in-flight one plus one re-translation of the final content), and the final file went from the translation of the *first* edit to the translation of the last. Translations of *different* files still overlap up to `--concurrency`, which is what that option is for.

- **sync**: **the lockfile now records what reached the target file, not what the API returned.** A run marked a key `translated` on the strength of the translation call, so a key `reconstruct` could not place was recorded as done and every gate read that as complete — the mechanism behind the format defect below, and one that would have hidden the next such bug just as completely. Every key is now read back out of the content just written before the lockfile is updated. A key the file does not hold is recorded `failed` instead: the run warns naming the file, the locale and the key, the file line reads `✗ es: 0/1 keys` rather than `✓ es: 1/1 keys`, and the run exits 12. Measured on the two shapes that are still deliberately not written — a new `<string-array>` item and a Laravel key whose parent array is absent from the target — where before this every surface agreed the locale was complete: run 2 now exits **12** with `status: "failed"` in `.deepl-sync.lock`, `deepl sync status` reporting 50% rather than 100%, and `deepl sync --frozen` exiting **10**. Presence is the test, not byte equality, which is the per-parser escaping contract; a translation that is deliberately the empty string is exempt, because PO and XLIFF read an empty translation side as untranslated by design. Content a parser has just produced and cannot read back counts as holding none of the keys.

- **sync**: **a string added to a source file after the first sync is no longer silently dropped from five of the eleven formats.** From the second run onwards `sync` uses the existing target file as the `reconstruct` template — that is how the translations it already holds survive — so a key added to the source since has no slot in it. Six parsers appended such an entry; `properties`, `ios_strings`, `laravel_php`, `android_xml` and `xliff` discarded it, and nothing downstream could tell, because the run recorded success from the translation call rather than from the write. Measured through the real CLI against a mock endpoint, run 2 of 2 on each of the five, with `json` as a control on the same run: exit 0, `OK es: 1/1 keys`, `Sync complete: 1 new, 1 current`, the target file **without** the key, `.deepl-sync.lock` recording `added.translations.es = {status: "translated"}`, `deepl sync status` reporting `es [####] 100% (0 missing, 0 outdated)`, `deepl sync --frozen` — the CI drift gate whose whole purpose is catching a missing translation — exiting 0 with `2 current`, and `deepl sync validate` passing with `Checked 1 translations ... All passed` because it only sees keys the file actually has. The characters were billed on every affected key, and the lockfile's `translated` claim is what stopped any later run correcting it, so the string was permanently absent from the shipped locale. Each of the five now writes the entry in the file's own layout: `.properties` and `.strings` append a line keeping the trailing newline and any dangling comment in place; `laravel_php` splices an array element at the offset of the array that owns it, matching the file's quote style, indentation, one-line-or-many layout and trailing-comma style, and handling `array(...)` as well as `[...]`; `android_xml` writes a `<string>` (or a whole `<plurals>` block) before `</resources>`; XLIFF writes a `<trans-unit>` in 1.2 and a `<unit><segment>` in 2.0, carrying the namespace prefix of the unit it is written beside. **XLIFF 2.0 was affected too** and the finding only measured 1.2. Two cases are deliberately still left out, because writing them would mean inventing structure the source file already defines: a new `<string-array>` item in `android_xml` (its `name.index` key is indistinguishable from a plain resource whose name ends in a dot-integer), and a `laravel_php` key whose parent array does not exist in the target. Verified after the fix with `xmllint --noout` on both XML outputs and `plutil -lint` on the `.strings` output.
- **sync**: **a reviewed PO or XLIFF translation is no longer replaced with source text.** Gettext PO and XLIFF are bilingual — one file carries the source in `msgid` / `<source>` and the translation in `msgstr` / `<target>` — and their `extract().value` is the *source* even when the file being read is a target. Every sync path that needed "the translation this target file already holds" built its map as `key -> extract().value`, so all of them read the source side. Measured through the real CLI against a mock endpoint, on the run that rewrites a file because a **sibling** key is new: `msgstr "REVIEWED-PO"` became `msgstr "Hello"` and `<target>REVIEWED-XLF</target>` became `<target>Hello</target>`, at exit 0, with the lockfile still recording the key as `translated` so no later run corrects it. The identical scenario on a `json` bucket correctly kept its hand-edited value, which is what made this format-specific rather than general. The finding named three call sites; there were **six**, and the two it did not name are the worse ones — see the `sync push` measurement below and the `sync validate` entry under Security. `deepl sync pull` had the same blind spot in its merge base, writing the msgid for a key the TMS export does not carry, and `deepl sync audit` measured terminology consistency across source strings rather than translations. Parsers may now override the target-side read (`FormatParser.extractTranslations`), PO and XLIFF do, and all six call sites go through one helper instead of reaching for `value`. An empty `msgstr`, a missing `<target>` and an empty `<target></target>` now read as *untranslated* rather than as a translation, so such a key is translated instead of having the source pinned into it; this differs deliberately from the monolingual formats, where an empty value is a deliberate translation and is still preserved.

- **sync**: **`deepl sync push` no longer uploads English as a locale's translation.** Push reads each target file and previously sent `entry.value`, which for a PO or XLIFF target is the msgid / `<source>`. Measured against a mock TMS: a `locales/es/app.po` holding `msgstr "Hola amigo"` produced the PUT body `{"locale":"es","value":"Hello {name}"}` and a TMS store of `{"es":{"Hello {name}":"Hello {name}"}}` — the reviewed Spanish never left the machine, and the TMS became the authority for a key whose recorded translation was the English source, so the next `deepl sync pull` would write English back into the target file. `TmsClient.pushEntry` now takes the translation as a required argument rather than reading it off `entry.value`, which is why no caller can reintroduce this by omission.

- **formats**: **a `.properties` value ending in a backslash no longer deletes the entry after it.** `escapeValue` correctly writes a literal trailing backslash as `\\`, but the reader's continuation test was `line.endsWith('\\')` with no parity check, so it read that escape as "this line continues", consumed the following line and appended its raw text to the previous value. Measured: a source of `greeting=Hello` / `api_key=SECRET_VALUE` / `footer=Bye` with `greeting` translated to `Hallo\` was written as `greeting=Hallo\\`, and re-extracted as `[{greeting: "Hallo api_key=SECRET_VALUE"}, {footer: "Bye"}]` — the middle entry **gone**, at exit 0. The finding called this data loss; it is also a disclosure. `sync push` extracts the target file and sends each value to the TMS, so the swallowed line left the machine under an unrelated key's name: measured, the push body for `greeting` was `Hallo api_key=SECRET_VALUE`, and `api_key` itself was never pushed at all — 2 keys sent where the file had 3. The same misread hits a *hand-written* source on its very first read, so a legitimate Windows path such as `path=C:\\` was enough on its own. Both continuation tests (extract and reconstruct) now count the trailing backslash run and continue only on an odd count, which is the rule `escapeValue` was already writing for. Round-trip is now verified for the values `x\`, `\`, `a\b\`, `C:\` and `a\\b`; the first four all previously ate the next entry.

- **translate**: **`deepl translate <file.json|.yaml>` now has a size ceiling, so a huge locale file cannot exhaust memory mid-run.** The structured-file route read and fully parsed whatever it was given, while both sibling routes of the same command were already bounded — text at 100 KiB, documents at 30 MB (`MAX_DOCUMENT_FILE_SIZE`) — and `deepl sync` skips anything over `sync.limits.max_file_bytes`. Measured peak RSS against a dead endpoint, so only parse and extract are counted: 4.7 MB → 129 MB, 19.2 MB → 251 MB, 80.9 MB → 684 MB, 163.8 MB → 1178 MB, linear and unbounded. The finding did not name the multiplier: the multi-target path parses a **fresh copy per target language**, up to `MULTI_TARGET_CONCURRENCY` (5) at once, so the same 19.2 MB file peaked at 252 MB for `--to de` and **483 MB** for `--to de,fr,es,it,nl`. The ceiling is 10 MiB, matching `HARD_MAX_SYNC_LIMITS.max_file_bytes` — the value `sync` refuses to be configured above — so nothing sync can be made to accept is refused here, and the worst case stays a few hundred MB rather than gigabytes. The check is a `fs.stat` before the read, at the one function both entry points funnel through, so an oversize file is never resident: the 163.8 MB fixture now exits 6 in 0.17 s at 86 MB RSS instead of 7.8 s at 1178 MB. The message names the file, its size and the limit, and points at `deepl sync` for anything larger; a directory run fails only that file and keeps its per-file reason in the summary. A document at 25 MB is still accepted, deliberately — it is streamed to the API rather than parsed.

- **sync**: **`sync pull` no longer writes source-language text into a target locale file, and no longer replaces a local translation without saying so.** The merge that applies a pull response read `pulledKeys[key] ?? existingTarget.get(key) ?? entry.value`, so a key the TMS export omits **and** the target file lacks was filled in with the source string. Measured against a mock TMS whose `de` export carried only `greeting`: a source file holding `greeting`/`farewell`/`brand_new` and a `locales/de.json` holding the first two produced a German file containing `"brand_new": "Only in source"` — English, indistinguishable from a translation to anything reading the file — at **exit 0**, with the one-line summary `Pulled 1 translations from TMS`. The final `?? entry.value` is gone; a key with a value on neither side is now omitted from the entry list, which is what `reconstruct` needs to leave it out of the file, and matches what the locale translator already does for a key it could not translate (it pushes nothing rather than the source). An empty string is a translation and is still preserved. The same change fixes the case the finding did not name: when the target file does not exist yet, the source file is used as the reconstruction template, so **every** untranslated key was written into the new locale as English; only the keys the export actually carries are written now. Separately, the pulled value has always won over the local one and always will — neither side of the documented export contract carries a timestamp, so "which is newer" is not a question that can be answered, and pull exists to bring the reviewed copy in — but the overwrite was completely silent. Pull now counts the existing local translations it replaced and names the count (`Replaced 1 existing local translation with the TMS version. Use --dry-run to preview a pull before it overwrites local edits.`), with `--verbose` naming each key and file. See Added for the preview mode.

- **translate**: **the CLI's own internal placeholder tokens can no longer be written into your text.** `restorePlaceholders` substituted every `__VAR_n__` it could find and silently left the rest alone, with nothing checking that the tokens the CLI had injected came back at all. Re-casing and re-spacing an unfamiliar token is ordinary MT behaviour, so `__VAR_0__` returning as `__ Var_0 __` produced, measured against a mock endpoint that does exactly that: `deepl translate "Welcome back, {username}!" --to de` printing `XX Welcome back, __ Var_0 __!` at **exit 0** with no warning; `deepl translate a.txt --output a.de.txt` writing the same to disk at exit 0; and a directory run writing it into every file at `✓ Successful: 2`. Only `sync` caught it, because only `sync` has a placeholder validator. All three paths now check the post-condition: `translate` fails with exit 5 naming the variables it lost (`The translation lost the placeholder {username}. … Nothing was written.`) and a suggestion pointing at the endpoint, and a directory run fails only the affected files — a file with no placeholders in it is unaffected and still translated. The check runs **before** the cache write, so a response that lost a placeholder never becomes a cache entry that reproduces the same output offline; a poisoned entry from an earlier version is refused on read for the same reason. `sync` is deliberately unchanged: its validator already withholds the key, counts it failed and retries it next run, and `validation.check_placeholders: false` stays the documented way to write such a translation anyway.

- **sync**: **every ICU block in a message is protected, not just the first.** `parseIcu` found one block with a single non-global match, then pushed the entire remaining suffix as one ordinary prose segment — so the second and later blocks were submitted to the MT engine as translatable text, which is the exact exposure the module exists to prevent. Measured against a mock endpoint with `You have {n, plural, one {# item} other {# items}} and {m, plural, one {# gift} other {# gifts}} waiting.`, the outbound request was `["You have ", "__VAR_HASH_0__ item", "__VAR_HASH_0__ items", " and {m, plural, one {# gift} other {# gifts}} waiting."]` — the first block's selectors and `#` correctly protected, the second block's full syntax sent as prose. A real engine translating `other` to `andere` yields a message with no `other` branch, which throws at render time. Detection now walks the whole string, emitting each run of prose between blocks as its own segment and each block through the same brace-counting parser, with leaf references reindexed into one combined segment list; the same request is now `["You have ", "__VAR_HASH_0__ item", "__VAR_HASH_0__ items", " and ", "__VAR_HASH_0__ gift", "__VAR_HASH_0__ gifts", " waiting."]`. Adjacent blocks with no prose between them, three or more blocks, and nested ICU are all covered. The documented safe fallback is unchanged and now applies to the whole message: a string holding **any** block that will not parse passes through untouched rather than half-protected.

- **sync**: **the internal ICU marker is no longer submitted and billed as a text.** A string routed to segment-by-segment ICU translation had its slot in the main batch filled with `__ICU_PLACEHOLDER_<n>__`, which went to the API as an ordinary text, was billed, and was cached under its own key — measured as a whole extra request per batch containing an ICU string. The slot now holds nothing to translate, so `translateBatch` skips it (see the empty-value entry above); `reassembleIcu` overwrites every mapped index, so the blank cannot reach a target file.

- **translate/sync**: **an empty string value in an i18n file is no longer mistaken for a failed translation.** `TranslationService.translateBatch` skips a text that is empty — nothing to send, nothing to bill — but left that slot `null`, the same value it uses for a text whose request failed, and declared its return type `TranslationResult[]` so nothing was forced to tell the two apart. Three separate consequences, all measured against a mock endpoint. **`deepl translate` crashed:** `{"title": "Hello world", "placeholder": "", "footer": "Goodbye"}` printed a false `⚠️  Warning: 1 of 3 translations failed` (nothing had failed) then `Error: Cannot read properties of null (reading 'text')`, **exit 1**, and no output file at all — one empty value cost the whole file. **`deepl sync` deleted the key:** the same content wrote a `de.json` containing only `title` and `footer`, recorded `placeholder` as `status: "failed"`, and every later run reported `✗ de: 0/1 keys` and **exit 12 forever**, since the retry could never succeed. It now reports `✓ de: 3/3 keys`, exit 0, writes `"placeholder": ""`, and settles in the lockfile as translated. **An ICU message with an empty plural branch was lost the same way:** `{count, plural, one {} other {# items}}` had its empty branch read as a failed segment, so the entire message was withheld and the key dropped from the target — found by looking for the same defect on a path the report did not name. Empty input now returns an empty translation with `billedCharacters: 0`, `translateBatch` is declared `(TranslationResult | null)[]` so the compiler forces the remaining failure case to be handled at each of the five call sites, and the `N of M translations failed` warning counts only real failures. `BatchTranslationService` records a missing per-index result as that one file's failure instead of dereferencing it.

- **translate**: **a rate limit part-way through a large structured file now exits 3 instead of 1.** `deepl translate <file>` grouped strings for the API by byte size only (128 KB), never by count, so a file of more than 50 strings became several API requests inside one `translateBatch` call; when a later request was rejected, the surviving batches came back with holes and the caller dereferenced one. Measured on a 60-key JSON file with a 429 on the second request: `Error: Cannot read properties of null (reading 'text')` and **exit 1** — `GeneralError` — so a CI wrapper branching on `$? -eq 3` did not retry. Batches are now capped at 50 strings as well as by size, which is what `BatchTranslationService` already did, so each call is a single request and a rejection propagates with its own classified code: the same run reports `Error: Rate limit exceeded: Too many requests`, its retry suggestion, and **exit 3**, with no partial output file written. The unreachable "expected N results but got M" length guards are kept and joined by a per-index check.

- **translate**: `ℹ️  Cache is disabled` and `ℹ️  Cache bypassed for this request (--no-cache)` are announced once per run rather than once per API request. The cache state is a property of the invocation, so a file needing ten requests repeated the same line ten times.

- **sync**: **a translation the engine corrupted is withheld from the target file instead of being written and recorded as done.** The placeholder/ICU validator is the only defence against corrupt machine output, and it ran too late to be one: the write at `sync-locale-translator.ts` happened first, then the lockfile, then the `.deepl.bak` backups were unlinked, and only then was `validation.fail_on_error` consulted. Its results were counted, never acted on. Measured against a mock endpoint that drops the `__VAR_n__` tokens the CLI substitutes for placeholders: `"greeting": "Hello {name}, welcome back"` reported `✓ de: 2/2 keys`, `Sync complete: 2 new`, one line of `1 validation error(s)`, and **exit 0** — with `de.json` holding `"[DE] Hello , welcome back"`, the lockfile recording the key `translated`, and the next run reporting `2 current` and never retrying, so the placeholder was gone permanently. `fail_on_error: true` only changed the exit code to 6 after the same damage was done, and where the target file already existed the previous good translation had been overwritten and its backup deleted on the way out. **The new-locale backfill path was not validated at all**: adding `fr` to `target_locales` translated the already-`current` keys through a second batch that never reached `validateBatch`, so `fr.json` was written corrupt at `✓ fr: 2/2 keys`, exit 0, and **zero validation errors reported** — the bulk-translation case was the silent one. An `error`-severity result (a lost placeholder, an ICU bracket or selector rewritten) is now decided before the write, on both paths: the key is withheld, counted as failed, and recorded `status: "failed"`, so the same run reads `✗ de: 1/2 keys`, `Sync complete: 2 new (1 translations failed)`, exit 12, and the next run retries the key. Warnings still pass through and are still written. Two things the fix cannot do naively: simply leaving the entry out **deletes** the key, because the entry list is the complete desired key set a parser reconstructs from — measured, `de.json` lost `greeting` entirely and a previous `"Hallo {name}, willkommen zurueck"` with it — so a withheld key now carries whatever the target file already held, exactly as an untouched `current` key does; and the plural write-backs, which copy translated text into the metadata the PO and Android parsers reconstruct from, are skipped for withheld entries, or the forms would have gone in corrupt behind a preserved scalar. `validation.fail_on_error` keeps its `false` default rather than being flipped: a withheld key already fails the run, so the protection no longer depends on the setting, and the flag retains its documented meaning of promoting that to a hard `ValidationError`. The backups are still cleaned up on the way out — with the corrupt value never written, there is nothing to roll back to, and keeping them would make the next run report an unfinished earlier run that did not happen.

- **formats**: **an `.arb` key whose name collides with an `Object.prototype` member is no longer dropped from the file it was billed for.** `arb.ts` gated new-key insertion on `key in data`, and `in` reports inherited members — so `toString`, `valueOf`, `constructor`, `hasOwnProperty`, `isPrototypeOf` and `__proto__` all read as already present and their translations were discarded. The sibling `json.ts` documents this exact defect as fixed, with the reason in a comment above the check; same repo, same class, one fixed and one not. Measured at the parser: asked to insert six keys into a target that lacked them, `arb` dropped five and `json` dropped none. **The trigger is a source file gaining a key**, not a first sync — sync seeds a new target from the source, so the keys land on the in-place path; it is the second run, inserting into a target that already exists, that loses them. Reproduced end to end against a mock endpoint: adding `hasOwnProperty` and `constructor` to `app_en.arb` reported `✓ de: 3/3 keys` and `Sync complete: 3 new`, wrote only the third key to `app_de.arb`, and exited 0. The lockfile records all three as translated, so the next run reports `6 current` and **never retries them** — the strings are lost silently and permanently rather than re-billed each run. Insertion now tests `Object.hasOwn` and writes through the shared `setOwnMember`, so a key named `__proto__` becomes an own property instead of reaching the prototype setter. `setOwnMember`/`getOwnMember` moved from `sync/sync-lock.ts` to `utils/own-members.ts` for this: `formats/` cannot import from `sync/` without inverting the dependency, and a third copy of the same `defineProperty` helper was not worth writing. No behaviour change for the five sync modules that use them.


- **logger**: **a short credential value no longer corrupts every diagnostic message.** The redactor's last step substring-replaced the literal credential with `[REDACTED]`, with no length floor and no token boundary, so any message containing the value inside an ordinary word was mangled. With `DEEPL_API_KEY=k` — a mistyped or throwaway value — a single real CLI run against a closed port printed `Warning: sending your DeepL API [REDACTED]ey to …`, `Error: Networ[REDACTED] error: connect ECONNREFUSED`, `Suggestion: Chec[REDACTED] your internet connection and proxy settings`, and a config path rendered as `/Users/[REDACTED]wey/…`: four lines of nonsense at the moment the user most needs to read them, and the mangling was itself how this was noticed, in the harness output of two unrelated findings. A literal value is now only replaced when it is **at least 8 characters**; below that, the auth-header and `token=`/`api_key=` query-parameter patterns still apply, so nothing that is shaped like a credential in transit goes unredacted. A real DeepL key is UUID-shaped with a `:fx` or hyphenated suffix and TMS credentials are longer still, so the floor excludes nothing genuine — the shortest key in this repo's own test suites is 12 characters. The alternative of matching on a token boundary was rejected: it would silently **miss** a real key printed immediately before a word character, which is the more expensive of the two errors, where a floor can only fail to redact a value too short to be a credential.

- **sync**: **the `Sync complete:` summary names how many translations failed**, instead of reading as though every diffed key had landed. The key counts in that line come from the diff, not from what was successfully translated, so a run that translated 50 of 200 keys and rate-limited on the rest printed `✗ de: 50/200 keys` and then `Sync complete: 200 new` directly beneath it — two lines flatly contradicting each other, with the accurate one being the easier to miss in a CI log. It now reads `Sync complete: 200 new (150 translations failed)`. The count totals every locale, and nothing is appended when nothing failed. Exit code 12 on partial failure is unchanged, as are the diff counts themselves, which were accurate about the diff all along.

- **sync**: **the lockfile no longer lets `git merge` invent a translation that existed on neither branch, and `sync resolve` now actually applies its documented `translated_at` tie-break.** One root cause behind both: entries were serialized one field per line, making git's unit of merge a *field* rather than a *translation*. Measured with real `git merge` on real serializer output, against a stashed-old-code control. **The silent case, which never reached `sync resolve` at all:** a branch that changed only `review_status` and a branch that changed only `translated_at` are non-adjacent lines with `status` unchanged between them, so git merged both hunks cleanly and produced `review_status: human_reviewed` from one side carrying `translated_at` from the other — a combination on neither branch, marking machine output as human-approved with a timestamp that makes the staleness invisible to any later timestamp comparison, at exit 0 with no conflict reported. **The `sync resolve` case:** where git *did* conflict, the region was the entry's field list, so it parsed to three scalars and the resolver's entry-level branch was unreachable; every field took the terminal `kept ours: scalar conflict, defaulting to ours` path. Measured discarding a newer `human_reviewed` translation in favour of older machine output, reported as resolved at exit 0 — the exact opposite of the documented rule, and side-dependent, so it silently did the right thing whenever the newer edit happened to be on the local branch. **Each translation is now written on a single line**, which makes the smallest region git can produce a whole entry: the field-level overlap conflicts instead of merging, and the conflict reaches the timestamp comparison, which picks one whole coherent side. Two changes were needed to make that hold, neither of them obvious from the format change alone. A region inside an object carries a trailing comma joining it to the next member, and `JSON.parse('{' + region + '}')` fails on it — so *every* entry but the last locale in its map would have fallen straight back to the length heuristic and kept discarding the newer side; the terminator is now taken off before parsing and put back after. And because resolving rebuilds each region with its own indentation, the resolved file is now written back in canonical form, so committing it cannot leave entries expanded across lines for the next merge to recombine. Where the two sides *disagree* on the terminator — one deleted what the other modified — no terminator is correct for both and the region still falls to the length heuristic rather than risk invalid JSON. **Upgrading reformats every existing lockfile on the next write, producing one large diff; it is formatting only and no entry's content changes.** Keys are sorted within the line, so a changed translation is now a one-line diff rather than three or four.

- **sync**: **`sync export` produces well-formed XLIFF for keys that contain control characters, and no longer changes a key on the way out.** `escapeXml` escaped `&`, `<`, `>` and `"` only, so a key holding a C0 control was written straight into the `id=` and `resname=` attributes — and C0 other than tab, newline and carriage return has no representation at all in XML 1.0, not even as a character reference, so the file was not well-formed and a translator's tool would reject it whole. Those characters are now replaced with `?`, which costs one odd character in one id rather than an unreadable handoff file. Separately, and independent of any hostile input: a tab, newline or carriage return inside a key was emitted literally, and every conforming XML parser **normalizes those to a space inside an attribute value** — so a multi-line key silently came back different from the key that was exported. They are now emitted as `&#9;`, `&#10;` and `&#13;`, which round-trip exactly. C1 (U+0080–U+009F) is deliberately left alone: those are valid XML 1.0 characters that round-trip unchanged, and an export is a data file, so it is mutated no further than validity requires.

- **sync**: **two syncs no longer run concurrently in the same directory, which is the entire purpose of the process lock.** Measured with six processes racing over a planted stale pidfile, 100 rounds: **93 rounds had overlapping lock holders before this change — up to five at once — and 0 do after.** Two independent defects had to be fixed to get there. First, the stale-pidfile reclaim was a read/unlink/create sequence with no atomicity, so a process whose staleness verdict had already been overtaken deleted the *live* pidfile the winner had just written, after which both held what each believed was an exclusive lock; and the create that followed the unlink was the one call not wrapped in the EEXIST handling, so a lost race surfaced as an unhandled `Error: EEXIST: file already exists, open '.deepl-sync.lock.pidfile'` instead of the intended "another sync is running". A stale file is now removed only after taking possession of it with `rename(2)` — atomic, so exactly one of several racers can move a given entry aside — and confirming the captured inode is the one proven stale; a process that captures a different file puts it back rather than deleting someone's lock. Acquisition always goes through the same guarded create, so a lost race reports the running sync, and the retry loop is bounded (5 attempts) with its own error rather than spinning. Second, and the defect that actually accounted for the remaining overlap once the reclaim was atomic: the pidfile was created empty through an `O_EXCL` descriptor and filled afterwards, leaving a window in which a **live** lock read as malformed — and malformed counts as stale, so a concurrent sync deleted it and took over. No identity check downstream can catch that, because the file it inspected really is the file it removed. The payload is now written to a private staging path and `link(2)`ed into place, which publishes the name and the content in one step and doubles as the atomic acquisition. CI relevance: a runner retrying a timed-out job is exactly the double-start trigger.

- **sync**: **a failed backfill for a newly added locale no longer writes the source text in as the translation.** When a current key's translation failed while bootstrapping a new target locale, the backfill path pushed `{ translation: cd.value }` — the English source — and only incremented `failed`. Because any value present in the target file counts as an existing translation, those strings were then skipped on every later run: `sync status` reported `fr 17% (50 missing, 0 outdated)` while `deepl sync` said `60 current` and refused to retranslate them, and `sync validate` rated it a warning at exit 0. The tool reported the strings as missing *and* declined to fix them, permanently, with no error anywhere. The same file's main translation path already handled this correctly, and the guard comment 60 lines up spelled out the reason: "Writing the source value here would record untranslated text as translated, which no later run would correct." The backfill path now pushes nothing, so the key stays out of the target file and the next run picks it up. Nothing is recorded in the lockfile for it either — deliberately, since a `status: 'failed'` entry would make `sync status` count the key as *outdated* when it is genuinely *missing*, and would trip the "lockfile records a translation but the target file has none" path on every retry.

- **sync**: **a run that lost most of its strings no longer exits 0.** A locale counted as failed only when it translated *nothing* (`fr.translated === 0 && fr.failed > 0`), so 10 keys succeeding and 50 failing was not a failed locale: `{"ok": true, "translated": 10, "failed": 50}` at exit 0, with the 50 failed keys absent from `locales/de.json` entirely. The comment directly above the check already cited the documented contract for exit 12 and the code did not implement it. Any failure count above zero now fails the run, so `deepl sync` exits 12 and `--auto-commit` — gated on `result.success` — no longer commits a truncated locale file. A locale that translated nothing *and* failed nothing is still a success: that is a locale which is already up to date. **CI impact**: a pipeline that previously went green on a partially failed sync now sees exit 12, which is the point; branch on `$? -eq 12` and re-run with `--locale` per the retry model in `docs/API.md`. The exit-code table there described 12 as "at least one failed locale" and now says "at least one failed key", matching the prose two sections down that already defined 12 as a mixed result.

- **sync**: **the progress stream no longer reports keys as translated that failed.** All five `key-translated` emission sites fired unconditionally after dispatching a batch, before any result was inspected, so a run in which every key failed still printed `translated: 60, totalKeys: 60` on the way to writing nothing. Each site now emits only when that key's `translateBatch` slot came back non-null, and the running count is a single counter over the successes rather than a loop index, so the number the stream reports agrees with the number the summary reports.

- **sync**: **a backup left behind by a crashed run is no longer overwritten by the run you start to recover from it.** After a `kill -9` mid-sync the lockfile was never written and `locales/de.json.deepl.bak` held the only surviving copy of the user's file — and the natural recovery action, re-running `deepl sync`, destroyed it: the "already backed up" guard is a per-process `Set`, so the run copied the machine-translated target over the existing backup and then unlinked it on success. Reproduced end to end: after the recovery run the human content was gone at exit 0, and the already-completed translations were re-billed. The copy now uses `COPYFILE_EXCL`, and on `EEXIST` the existing backup is left alone with a warning naming it — and deliberately not tracked as this run's, so the success path does not unlink it either. The stale-backup sweep still retires it on age. A run with no pre-existing backup behaves exactly as before: back up, write, unlink on success.

- **sync**: **Ctrl-C during a sync now restores the files it had already overwritten, instead of deleting their backups.** The signal handler ran the same cleanup as a successful run — unlink every `.deepl.bak` taken this run — which is right for a run that finished and catastrophic for one that did not: the backup was the only remaining copy of content the run had already replaced. Reproduced with a delaying endpoint and two locales: at the moment of the interrupt `locales/de.json` held machine output and `locales/de.json.deepl.bak` held the human translations; after `kill -INT` the backup was gone, the machine output stayed, and no lockfile had been written (it is written once at the end), so the human translations were unrecoverable and unrecorded at exit 130. Each backup is now copied back over its target before being removed — that order, so an interrupt during the restore leaves the backup rather than nothing — and the run reports what it undid: `Interrupted — restored 1 file(s) from backup: locales/de.json. No lockfile was written, so nothing was recorded; re-run to translate again.` Verified end to end: `locales/de.json` is byte-identical to its pre-run content. The restore is synchronous because `installSignalExit` defers the exit by one `setImmediate`, so only synchronous handler work is guaranteed to finish. A successful run is unaffected — it still unlinks, from its own path. `sync --watch` is unchanged: it owns its own backup tracker and cleanup.

- **sync**: **a Laravel PHP lang file that overflows `php-parser` is skipped with a warning instead of ending the run.** `php-parser` has no recursion guard, and it throws from inside `parseCode` — before `php-arrays`' own `max_depth` guard, which only walks the AST once a parse has succeeded — so a 100KB file of deeply nested parentheses, well under `max_file_bytes`, arrived at the walker as a bare `RangeError` and was rethrown: `Error: Maximum call stack size exceeded`, exit 1. Verified before and after by removing the new handler and rebuilding: exit 1 with that message, versus exit 0 and `Skipping lang/en.php: nesting depth exhausted the stack while parsing (…)` with it. Covered by the same per-file boundary added for the JSON/YAML depth work below, so any parser that lets a `RangeError` escape now costs one file rather than the run.

- **sync, translate**: **a deeply nested JSON or YAML file no longer ends the whole run with `Error: Maximum call stack size exceeded`.** The JSON and YAML walkers recurse once per nesting level with no depth guard, so a 16KB file of 8,000 nested arrays — far below the 4 MiB `sync.limits.max_file_bytes` default, so the pre-read size check never sees it — killed `deepl sync`, `deepl sync validate` and `deepl translate <file>` alike. In a sync it was worse than a crash: a healthy file earlier in the bucket had already been translated, billed and written, and because the run died before the lockfile was written that work was unrecorded, so the next run paid for it again. `sync.limits.max_depth` (default 32, ceiling 64) existed for exactly this and was wired only to the Laravel PHP parser, which `sync-bucket-walker.ts` documented in a comment rather than fixing. Three changes: `JsonFormatParser` takes a `maxDepth` and rejects past it with a catchable error naming the key path; the walker now applies `sync.limits.max_depth` to **any** parser that accepts one — via a new optional `withMaxDepth` on `FormatParser`, so a future recursive parser opts in rather than needing a new special case — and always, rather than only when the user overrode the default; and one file exceeding the cap is skipped with a warning while the run finishes and records what it did. Verified end to end: a bucket holding one healthy and one 8,000-deep file now completes at exit 0, writes the healthy target, writes the lockfile, and prints `Skipping deep/en.json: JSON: max nesting depth 32 exceeded at 'a.0.0.0…'`. **YAML is bounded differently, because bounding our own recursion could not have helped it:** the `yaml` library builds its tree recursively and reports the blown stack as a parse diagnostic, so it fails inside the library before any walker of ours runs — measured in both flow and block style. That diagnostic is now recognised as a depth rejection and skipped like any other, and a `RangeError` escaping any parser is caught at the same boundary as a backstop. The direct `deepl translate <file>` path has no `.deepl-sync.yaml` and so no configured limit; it gets a fixed ceiling of 100 levels, which clears any realistic i18n file by a wide margin and sits far below the ~2,000 levels at which the stack actually gives out, so its only effect is to turn an opaque stack overflow into a named error.

- **sync**: **two keys whose placeholders protect to the same text no longer receive each other's variables.** `preserveVariables` replaces every variable with a positional token, so `Hello {name}` and `Hello {user}` both become `Hello __VAR_0__` — one text on the wire, and `TranslationService.translateBatch` deduplicates them, which is the point. It then assigned the *same* result object to every index the duplicate covered, and the restore loop in `sync-locale-translator.ts` edited `result.text` **in place**: the first key's restore consumed the token, so the second key found none left and was written with the first key's variable. `{alpha: 'Hello {name}', beta: 'Hello {user}'}` produced `beta: 'XX Hello {name}'`, and the far more common `%s`/`%d` pair — `{delta: 'Deleted %s files', epsilon: 'Deleted %d files'}` — produced `epsilon: 'XX Deleted %s files'`, a format specifier that no longer matches its argument. This needed no hostile input, only two strings that differ solely in their variable. The run reported `5/5 keys` at exit 0, the lockfile recorded the affected key as `translated`, and the next sync reported it `current`, so the corruption was permanent. `translateBatch` now gives each index its own copy of the result — the array is typed as one result per index, and no caller can alias two logical results any more — and both restore loops replace their entry instead of editing it. Verified end to end: every key gets its own placeholder back, and the two validation errors and two warnings the run previously emitted (advisory, exit 0, details not printed) are gone, since they were reporting exactly this. `deepl translate` was never affected; its single-text path already returned a new string.

- **translate**: **`--no-cache` was accepted and silently ignored for every structured i18n format** — JSON, YAML, TOML, PO, XLIFF, Android XML, iOS `.strings`, `.xcstrings`, ARB, `.properties`, and Laravel PHP. In one function thirty lines apart, the plain-text branch passed `skipCache: !options.cache` and the structured branch passed only `{ preserveCode }`, because `TranslationService.translateBatch()` had no service-options parameter at all and consulted persisted `cache.enabled` alone. A wrong translation was therefore permanent: re-running the identical command with `--no-cache` sent **zero** requests and reproduced the previous output byte for byte, defeating the one remedy a user would reach for. `translateBatch` now takes the same `serviceOptions` shape as `translate()` and honours `skipCache` on both the cache read and the cache write, and the flag is threaded through `translateFile`, `translateFileToMultiple`, and `translateStringsInBatches` — the multi-target file path dropped it too, for plain text as well as structured files, so both single- and multi-target now behave alike rather than fixing one sibling and leaving the other bare. Verified end to end against a local stub: two identical runs without the flag make one request (second served from cache); the same pair with `--no-cache` makes two. The bypass message (`ℹ️ Cache bypassed for this request (--no-cache)`) is emitted on the batch path as well now. `sync` and `batch` do not expose `--no-cache` and are unchanged.

- **translate**: **`--output <dir>` failed with `EISDIR` for a single target language, though it worked for two or more.** `--output` is documented as a file path *or* a directory, and the multi-target branch honoured that — `--to ko,ja --output dir/` wrote `dir/t.ko.md` and `dir/t.ja.md` — while the single-target branch used the destination verbatim and let the atomic rename land on the directory: `Error: EISDIR: illegal operation on a directory, rename 'dir/.tmp.59970.vmrlp5' -> 'dir/'`, exit 1. Two branches of the same command disagreed, and the one that contradicted the documentation was the common one. It affected text files, structured files (JSON/YAML) and documents alike, because each branch decided the destination at its own call site. The destination is now resolved once, ahead of every branch, and a directory names the file the way multi-target translation already does: `deepl translate t.md --to ko --output dir/` writes `dir/t.ko.md`, so two locales into one directory cannot collide. `dir` and `dir/` behave identically — the check is `statSync().isDirectory()`, not a trailing-slash test — and a trailing slash additionally creates the directory when it does not exist, matching multi-target. A converted document is named by `--output-format` (`report.pdf --to de --output-format docx --output dir/` writes `dir/report.de.docx`), since that flag decides what the bytes are. `--output -` and a non-existent path such as `--output out/new.md` are unaffected. Pre-existing, not a regression. `examples/03-batch-processing.sh` hit this in five places and hid four of them behind `2>/dev/null`, `|| true` and a `(cached or completed)` message that reported a cache hit for a call that had errored — so `npm run examples` reported 37/37 passed while this was broken; those guards are gone, and section 8's cache comparison now times calls that actually succeed.

- **sync**: **`deepl sync resolve` kept the local side of every merge conflict, silently discarding a teammate's newer translations.** The documented rule — take the newer translation by `translated_at` — never fired on a real `.deepl-sync.lock`. The leaf test treated any object carrying `source_hash` as a translation to compare, and every lockfile entry carries one, so the resolver read `translated_at` on the entry, where it does not exist; the real timestamp lives on each locale inside that entry's `translations` map, and the recursion that would have reached it was never taken. Each conflict was therefore reported as `kept ours: neither side had translated_at` and resolved to ours, at exit code 0 and without the `length-heuristic` tag that exists to mark exactly this kind of unreliable decision — so the per-entry report gave no sign that anything had been dropped. An entry holding a `translations` map is now treated as a container and merged one locale at a time, which is where the timestamps are, and the report names the locale it decided (`greeting.translations.de`) rather than the entry. Fields the two sides agree on are no longer listed as conflicts. The existing tests passed throughout because their fixtures put `translated_at` directly on the entry, a shape `SyncLockManager` does not write; the suite now also drives the shape it does.

- **docs**: Five documentation inaccuracies found in the pre-2.0 audit. `docs/API.md` and `README.md` still said the **last** `--glossary` wins a conflicting term, contradicting the same files, the flag's own help text, and the verified behaviour — which mapping wins is the API's choice and does not follow flag order. `docs/API.md`'s command-group table omitted `correct` while claiming to match `deepl --help`, and the README's table of contents omitted its Spelling and Grammar Correction section. `docs/API.md`'s environment-variable reference omitted `NO_PROXY`, which the HTTP client honours and the README already documented. `docs/TROUBLESHOOTING.md` attributed "Translation cache backend failed to load" to running Node.js < 24, which the startup version check now rejects earlier with its own message, so the stated cause was unreachable; that entry now describes the reachable case (a v24+ runtime with no usable `node:sqlite`) and the version error is documented under exit code 6, where it previously appeared nowhere.

- **watch**: **`deepl watch` debounced at 300 ms while `--help` and every doc said 500, and `watch.debounceMs` did nothing.** The command forwarded a debounce only when `--debounce` was passed, so an omitted flag fell through to `WatchService`'s own 300 ms fallback — a third copy of a value the config schema and the flag's help text both put at 500. The configured key was accepted by `deepl config set` and listed in the documented schema, but nothing ever read it for `watch`. Resolution is now flag, then `watch.debounceMs`, then the documented 500 ms default, and that default is a single exported constant shared with the config schema so the two cannot drift again. `deepl sync --watch` was already correct at 500 and is unchanged.

- **package**: **`import '@deepl/cli'` threw instead of loading.** The package is ESM, so Node requires a full specifier for every relative import, but the entry point re-exported `'./types'` — a directory — which fails with `ERR_UNSUPPORTED_DIR_IMPORT`. The whole programmatic surface was therefore unreachable, and the published typings resolved to nothing for a `nodenext` consumer, so `import type { Language } from '@deepl/cli'` was an error regardless of what the union contained. `deepl --help` never exercised this, because the `bin` entry has its own module graph. Both remaining directory specifiers now carry `/index.js`, and the manifest suite imports the built entry in a real Node ESM process and rejects any extensionless relative specifier in the emitted entry chain.

- **scripts**: **The language generator wrote unescaped API response fields into TypeScript.** `lang` was interpolated into a single-quoted literal with no escaping and `name` escaped only quotes, so a response field containing `' }] as const;` — or merely ending in a backslash — could close the literal and append arbitrary code to `src/data/language-entries.ts`, which the next `npm run build` compiles and the test suite imports. The existing guards checked the shape of the response, never the content of a field. Codes are now validated against the language-tag pattern, display names against a conservative character set, categories against the three tiers, and every value is quoted with escaping; validation runs before grouping, which would otherwise drop an entry with an unrecognized category before it was checked. The generator's main guard also resolves `argv[1]` through `realpathSync`, because Node reports the ESM entry by its real path — under a symlinked checkout both npm scripts exited 0 without doing anything, including the release step that keeps the Write list current.

- **translate**: **A directory run stopped by one request-level rejection now reports that rejection's exit code** instead of the generic `1` for "nothing succeeded". A refused `target_lang` is invalid input and exits 6, an exhausted quota exits 4, a refused key exits 2 — all cases where every file draws the same answer and the run aborts. A run where files failed for their own reasons still exits 1 with no successes, or 12 with some. Text and file modes already exited 6 for this.

- **glossary**: **The language-pair preflight no longer treats two regional variants of one language as interchangeable.** Both sides were compared on their base language, so a `pt-br` dictionary satisfied a request for `pt-pt`. The relaxation is needed in one direction only — dictionaries name base languages while `--to` accepts variants — so a dictionary language now matches the requested one exactly or matches the base it reduces to. `de→en` still covers `--to en-us`, and a dictionary naming `pt-br` still matches `--to pt-br`. Not reachable through the current API, whose glossary language set is entirely base codes.

- **languages**: **A language `GET /v3/languages` describes with no feature matrix is no longer filed as extended.** The tier was derived from the absence of glossary support, and an absent matrix is silence rather than a denial — the same unknown-versus-none conflation already fixed for the `--features` table. Since the extended tier is what refuses formality and glossary before a request is sent, such a language is now tiered by source usability and the API keeps the judgement. An **empty** matrix is still evidence and still means extended. The bundled snapshot is unchanged, since every language the API currently lists carries a matrix.

- **languages**: An absent `usable_as_source` / `usable_as_target` flag is read as "usable" in the language and glossary-pair listings, matching how the language registry has always read it. The two disagreed, so a language whose flag was absent was dropped from `deepl languages` while the snapshot generator recorded it as core.

- **types**: `LanguageEntry`'s fields are `readonly`. The accessors hand out the registry's own objects, so `getTargetLanguages()[0].code = 'x'` changed the registry for the rest of the process — something the generated `as const` snapshot forbids but the widened element type permitted.

- **scripts**: `npm run generate:languages` reports a thrown fetch or an unparseable error body as its own `error:` line and exit 1, rather than as an unhandled rejection with a stack trace.

- **languages**, **voice**: **Strings the API supplies are sanitized before they reach the terminal.** `deepl languages` printed the name, feature keys and feature statuses from `GET /v3/languages` verbatim, and `voice` did the same with transcript text and language labels, so a hostile or intercepted endpoint could move the cursor, clear the screen, or hide text behind a bidi override. Both now go through the same `sanitizeForTerminal` the glossary and style-rule listings already used, replacing control and zero-width characters with `?`. It matters most for `voice`, whose live display clears a fixed number of lines: a newline inside a transcript threw off the whole rendering, not just its own line. `voice --format json` keeps the text byte-for-byte, since JSON escaping already makes it inert and that is the path machines read.

- **watch**: **A direct `WatchCommand.watch()` call rejected `--glossary` without `--from` even when `defaults.sourceLang` was set.** The config-aware resolution every other command uses lived only in watch's CLI registration layer, while the handler kept the older flag-only guard — so the CLI accepted a command a library caller was refused. The handler now settles the source language the same way, from `defaults.sourceLang` when the flag is absent, and `WatchCommand` takes the config service to do it. The requirement itself is unchanged: with neither a flag nor a default, the command still exits 6 before the watcher starts.

- **sync**: **Per-locale glossary overrides skipped the coverage preflight, and `--dry-run` performed no resolution at all.** `locale_overrides.<locale>.glossary` was resolved without the language pair, so an override that did not cover its own locale reached the API — unlike the top-level glossary and the translation-memory override, which were already checked. Both kinds of override now resolve once at startup against their own locale, rather than being re-resolved for every file, so a bad reference fails before anything is translated instead of after earlier files have been written. `sync --dry-run` resolves and checks the same references a real run does: the command already needs an API key to reach that point, and a glossary or translation memory the config names but the account cannot use for the requested pair is exactly what a preview should report. A dry run still sends nothing to `/v2/translate`.

- **voice**: **`--glossary` was resolved before the rest of the command was checked, and without the language pair.** `voice a.ogg --to bogus --glossary my-terms` spent a glossary-list round trip and only then failed locally on the target language; every local check now runs first. Resolution also passes the requested pair, so a glossary whose dictionaries do not cover it fails locally with `Glossary "my-terms" does not support the requested language pair` instead of at the API — the preflight the other commands already had. The pair is the canonical one voice sends, so `--from EN --to zh-hans` is checked as `en→zh-HANS`. Without `--from` there is no pair to check and the API still judges it.

- **translate**: **File, directory and `--dry-run` runs skipped the extended-tier language checks that text runs made.** `translate "Hi" --to af --formality more` exited 6 locally, while the same flags on a file or a directory reached the network and came back as an API rejection; `--dry-run` reported both as runnable, along with `--to 'not!!a!!lang'`, which every real run refuses. Language validation was spread over eight call sites in five files and only three paired the code check with the extended-tier check, which is how the modes drifted apart. There is now one entry point that every input mode calls, so a constrained option fails before anything is sent whichever mode handles the argument. Each mode passes only the flags it actually honours, so nothing is refused over a flag its mode discards: a document run still accepts `--model-type`, which it strips after warning, and a directory run still accepts `--glossary`, which it ignores. **`--from` is validated too** — it never was, so a malformed source language went unremarked until the API answered — and is named as such: `Invalid source language code: "grman"`. The "not in the bundled language list; deferring to the API" note is now said once per code per run instead of once per call site, which had it printing twice for `--to de,ex` and four times for `--to ex,zz` on a directory. An empty repeatable `--glossary` list no longer trips the "do not support glossaries" rejection, and a dry run lowercases `--to`/`--from` the way the real run does.

Since language validation defers unknown codes to the API, a plain `--to` typo took this path: on 1.x it exited 6 locally, and in this release it printed a failure list and exited 0. A run with no successes now exits 1, and a partial failure exits 12, matching what `sync` already does.

The classifier also checks the error class before the message: a 5xx interpolates the upstream body, so a gateway error quoting `target_lang` no longer aborts a run that is otherwise succeeding, while a refused key or an exhausted quota — as request-wide as a bad code — now do.

- **cache**: `write` and `correct` entries cached for the five target codes whose casing changed (`en-GB`, `en-US`, `pt-BR`, `pt-PT`, `zh-Hans`) are no longer reachable, since those keys hash the target language. They are left to expire with their 30-day TTL rather than dropped: the key is a hash, so the affected rows cannot be told apart from the ones for `de`/`en`/`es`/`fr`, which are unaffected and still serve.

- **cache**: **The translation cache keyed on too little and could serve the wrong text.** `translationMemoryId`, `translationMemoryThreshold`, `--ignore-tags`, `--splitting-tags`, `--non-splitting-tags`, `--outline-detection` and `--preserve-formatting` were absent from the key, so `deepl translate "Hello" --to de` and the same command with `--translation-memory my-tm` collided: the second returned the cached non-TM translation, never consulted the memory, and reported `cached: true`. Likewise two runs differing only in `--ignore-tags` returned each other's output. `preserveFormatting` had been excluded on the grounds that it does not affect output, but `preserve_formatting` suppresses the sentence-boundary punctuation and case correction, which shows up in the text. **Every translation entry cached by an earlier version is retired**, not only the ones using these options: the service merges a `preserveFormatting` default, so it is always part of the key. The cache schema version is bumped, so those rows are dropped on first open rather than sitting unreachable until their 30-day TTL — `write` and `correct` entries key the same way they always did and are kept. - **translate**: **A rejected language no longer costs one API round trip per batch.** Because validation defers well-formed unknown codes to the API, a two-letter typo reaches it — and a directory translation asked the same rejected question once per batch, so `deepl translate ./docs --to ex` on 200 files made 200 failing requests to be told the same thing 200 times. An unsupported `target_lang` or `source_lang` is a property of the request, not of one batch, so the remaining batches now fail without being sent; errors specific to a batch (a rate limit, say) still let the run continue. Relatedly, local validation used to be what pointed at `deepl languages`, and deferring left users with a bare `Value for 'target_lang' not supported.` from the server: a code the bundled snapshot does not list now says so up front, before anything is sent or billed.

- **usage**: **Voice usage reported the API key's own consumption as the account total.** Duration-billed products fell back to `apiKeyUnitCount` for the account figure because live `GET /v2/usage` responses omit `unit_count` for them, so `deepl usage` printed the same number in both columns — an account with 100 minutes used and 10 on this key showed 10 for both. The account-wide field the response does carry, `account_unit_count`, was neither typed nor parsed; it is now, and where no account-wide figure exists the row reads `(API key)` instead of inventing a total. This is the only place voice usage appears since the Speech-to-Text section was removed, which is why the wrong number mattered.

- **glossary**: Six smaller defects around the multi-glossary work. Naming one glossary twice — or a name plus its own UUID — sent a duplicate in `glossary_ids`, which flipped the wire parameter away from `glossary_id`, minted a third cache key for an identical request, and spent two of the five slots the API allows; IDs are deduplicated after resolution. `sync` resolved its glossary without the language pair, so a glossary that did not cover it failed once per file instead of at startup, unlike the sibling translation-memory resolution. `translate --dry-run` reported a glossary command as runnable that the real run rejects for a missing `--from`, and `watch --dry-run` did the same. The document path never ran the extended-tier constraint check, newly reachable now that documents accept glossaries, so it uploaded the file and let the API refuse it while the text path said so locally. `glossary info` printed raw dictionary languages beneath a normalized summary, so one glossary could show `EN → DE` under `Source language: en`. And a coverage error listed every dictionary of a multilingual glossary on a single line.

- **glossary**: `--glossary` with a source language set only in config no longer fails. `TranslationService` merges `defaults.sourceLang`, so the request carries `source_lang` whether or not `--from` was typed, but the guard tested the flag alone — so `deepl config set defaults.sourceLang en` followed by `deepl watch ./docs --to es --glossary my-terms` broke a session that had been working. The effective source language is now resolved onto the request, which also gives the document path (which merges no defaults of its own) and the glossary preflight the pair they need. An empty `--glossary` selection is no longer treated as a glossary either: `[]` is truthy, so a caller passing one got a spurious "Source language (--from) is required".

- **languages**: `--features` no longer claims knowledge it does not have. The listing keeps snapshot entries the API response omitted, and every one of them was rendered as the positive claim `none` — with a response covering a handful of languages, `--features` reported over a hundred as supporting nothing. Those rows also made every feature look non-uniform, so features shared by all the described languages became columns of repeated values instead of the single footer note the flag was built around. A feature reported without a `status` rendered as the literal string `undefined` (the enum is open, and an absent status still means the feature is there), and `supportsFormality` was asserted `false` for languages whose features the response never mentioned, turning on the `[F]` legend with no `[F]` anywhere to explain it. `deepl languages` also makes one `GET /v3/languages` request instead of two identical ones — both roles are filtered out of the same payload.

- **languages**: `deepl languages --format json` with no API key answered `{"source":[],"target":[]}` while the text and table formats printed all 125 from the bundled snapshot. Both read the same snapshot, so the JSON path now falls back to it too — listing languages works offline in every format.

- **config**: `deepl config set defaults.sourceLang DE` was rejected while `deepl translate --from DE` works. Every translate path lowercases the flag before validating, but the config validator matched a lowercase-only pattern, so the one casing that is certainly valid was the one class of input still refused. Language values are lowercased before validation and stored normalized. A code the bundled snapshot does not list is still accepted, since the snapshot can lag the API, but now warns at the point of entry — a typo written to config otherwise failed on every later command with nothing pointing back at the config value responsible.

- **translate**: `--tag-handling-version` is honoured for files and directories, not only for text. The shared option mapping carried `--tag-handling` but not the version, so with the CLI now pinning v2 whenever tag handling is on, `deepl translate page.html --tag-handling html --tag-handling-version v1` silently sent v2 — and single-file mode emits no ignored-option warning to say so. The flag is mapped in the shared mapping every handler uses, and its validation moved with it.

- **scripts**: `npm run generate:languages` refuses to write a snapshot that would break the CLI. An empty write list would collapse the `WriteLanguage` union to `never`, rejecting every `--lang` while naming no valid option; a features matrix that stopped reporting `glossary` would retier all 125 languages as extended and make `--formality` and `--glossary` unusable everywhere. Both now fail the run instead. `--check` compares whole blocks rather than quoted codes, so a renamed display name is reported as real drift instead of "formatting only", and the generated file is in `.prettierignore` so `npm run format` cannot make that check fail permanently. Both resources are fetched together and their failures reported together, so a key that cannot read `resource=write` no longer blocks regenerating the translation list it can read.

- **languages**: **Four target languages the API accepts were unusable.** `de-CH` (Swiss German), `de-DE`, `fr-CA` (Canadian French) and `fr-FR` are returned by `GET /v3/languages` and accepted by the translate endpoint, but the CLI's bundled language list did not contain them, so `deepl translate --to de-CH` failed locally with `Invalid target language code` before any request was made — and the `deepl languages` the error suggested did not list them either, because the listing used the bundled list as its row set rather than the API response. Swiss German and Canadian French had no workaround; `de-DE`/`fr-FR` could be spelled `de`/`fr`. The list now contains all 125 languages the API serves (32 core, 11 regional, 82 extended). See the Changed entry below for why this class of divergence can no longer make a language unusable.

- **languages**: `deepl languages --target` marks Portuguese (`pt`) with `[F]`. Formality support is now read from `features.formality` on `GET /v3/languages` instead of a static table in the language registry. The v3 migration had assumed v3 stopped reporting formality, but the capability was only renamed — v2's `supports_formality` boolean became the presence of a `formality` key in the per-language features matrix — so the CLI was answering from an 11-entry snapshot of the final v2 response that had already drifted from the API. The snapshot and the registry's `supportsFormality` field are gone; the registry's `category` tiers are unaffected. Output is otherwise unchanged: the `[F]` set is identical apart from `pt`.

- **watch**: `--glossary` without `--from` now exits 6 before the watcher starts, instead of starting a session that fails on every single file change with a raw server message. The API rejects any translation naming a glossary without a source language ("Use of a glossary requires the source_lang parameter to be specified"), which `translate` already guarded against up front for text, files, and documents; `watch` passed `--from` straight through. A long-running command is the worst place for this, since the operator saw the failure once per edit rather than once at launch. The check runs before the glossary name is resolved, so it costs no API call. `sync` needs no equivalent: it has no `--from` at all, taking the source language from the required `source_locale` field in `.deepl-sync.yaml`, so its requests always carry one.

- **voice**: A session that ends with the audio transcribed but no translation for a requested `--to` language now fails with exit code 9 and names the languages, instead of printing an empty translation line and exiting 0. The failure **carries the transcripts that did arrive**, which the command prints to stderr before exiting: the audio is transcribed and billed before the missing translation is noticed, so with `--to de,fr,es,it,ja` one dropped target must not throw away the source transcript and four good translations and make the user re-stream to see them. Target updates are also matched **case-insensitively**, because the requested spellings include `zh-HANS` and `en-GB`: a server echoing another canonicalization had its translation silently dropped by the existing unmatched-update guard, and this check would then have reported that target as missing — turning a cosmetic mismatch into a failed session. Silent partial output was the worse failure: a script consuming `deepl voice` output saw success with the translation missing. Audio containing no speech transcribes to nothing and translates to nothing, which is legitimate and still exits 0, so the check only applies when a source transcript exists. Whitespace-only and tentative-but-never-concluded translations count as missing, since neither reaches the printed output. Investigated as an intermittent (~1 in 4) empty translated line; the leading hypothesis was disproved with frame-level traces of live sessions — the server sends `end_of_stream` strictly after `end_of_target_transcript`, and the client only tears the socket down on `end_of_stream`, so there is no client-side teardown race. Reconnect was ruled out too: a socket dropped after end-of-source cannot be resumed (the API returns `410 Gone`) and already exited non-zero. The empty line did not reproduce in 64 live runs across pacing, burst, multi-target, and concurrency variations, so the trigger appears to be server-side and transient — which is exactly why the client needs to detect it rather than report success.

- **formats**: TOML reconstruction escapes U+2028/U+2029 (Unicode line/paragraph separators) in double-quoted values, and literal-string values gaining one fall back to double quotes. Written raw, these characters broke the entry-line scan on the *next* sync (JavaScript's `.` excludes line terminators), which re-appended the key as a duplicate and made the third sync fail to parse the file at all — first sync fine, second silently corrupting, third crashing. Found by the property-based round-trip suite.

- **formats**: `.properties` reconstruction escapes leading spaces in values (`\ `), which the value parser otherwise strips on the next read — a translation beginning with a space silently lost it on every subsequent sync. Leading tabs, trailing spaces, and newlines were already escaped correctly. Found by the property-based round-trip suite.

- **sync**: `--auto-commit` now recognises its own translation output rather than only the files a given run wrote, which fixes two related problems. A translation left on disk by an earlier refused run was classed as an unrelated modification, so auto-commit refused forever and the user had to commit it by hand; it is now committed once the genuinely unrelated changes are dealt with. And in `--watch` mode, where the same path runs once per trigger, a trigger that translated nothing skipped the checks entirely and reported success while a commit was still owed. Staging is also driven by what is actually dirty, so a rewrite that produced identical bytes no longer attempts an empty commit. Ownership is derived from the lockfile's tracked source files, with each file matched to its own bucket so one bucket's `target_path_pattern` cannot claim another's output.

- **sync**: Re-running `deepl sync --auto-commit` after a refusal no longer reports success without committing. A refused run still writes its translations to disk, so the retry found nothing to translate; the preflight was skipped in that case and the command exited 0 with no commit made, the translation still uncommitted and the tree still dirty. The repo-state checks now run whenever `--auto-commit` is requested, so the refusal is reported identically on every attempt. Staging and committing are still skipped when there is nothing to commit. Two tests covered this path but could not see the defect: their assertions ran only inside a `catch` the retry never entered, which also hid an assertion that could never have matched (it looked for "detached HEAD" against a message reading "HEAD is detached").

- **write**: `deepl write` now runs from a published install. `diff` is imported at the top of the write command but was declared only under `devDependencies`, which consumers do not install, so every command that loaded the module failed with `Cannot find package 'diff'` before producing output. `--help` did not surface it because the module loads lazily.

- **init/write/sync**: `@inquirer/prompts` is declared as a dependency. It is imported at runtime by `init`, `write --interactive` and `sync init` while only the unused `inquirer` was declared, so it resolved through npm's hoisting: under a strict layout (pnpm, `--install-strategy=nested`) those commands failed with `ERR_MODULE_NOT_FOUND`, and under npm the prompt that reads the API key bound to whatever major another dependent happened to hoist.

- **init**: `deepl init` with stdin at end-of-file now exits 6 with the documented non-interactive message, instead of starting to prompt and then exiting 1 with a Node `unsettled top-level await` warning. Reached by `docker run` without `-it`, CI, and piped invocations. The command checked only `--no-input`, where the sibling guard in `write --interactive` also checks whether stdin is a terminal; the existing test covered only the `--no-input` variant, which already worked.

- **write**: `--lang` and `--to` accept language codes in any casing and normalize them to the API's form. They previously compared against a mixed-case list with an exact match, rejecting the lowercase codes `deepl languages` prints and `translate --to` accepts — so the CLI's own discovery output was unusable with the command documented as consistent with `translate`.

- **translate**: The error raised for an unexpected API response pointed at a bug tracker under an unrelated third-party account rather than this repository's.

- **cli**: Shell completions and the did-you-mean suggester no longer offer hidden internal commands, and the suggester now knows about aliases and prefers a prefix match — `deepl tr` suggests `translate` rather than `tm`. `--version` is also no longer duplicated in the bash and zsh candidate lists.

- **cli**: The remediation for a missing API key survives `--quiet`. It was emitted as a warning, which quiet mode suppresses entirely, leaving only `Error: API key not set`; `docs/API.md` claimed quiet mode still showed such warnings and now describes the actual behaviour.

- **cache**: The size cap is now actually enforced. Size accounting previously lived in a process-local counter that drifted in both directions — downward when an overwrite's eviction deleted the very key being replaced (after which the cap stopped firing and the DB grew without bound), upward when `get()` deleted expired rows without decrementing (evicting entries that didn't need evicting), and negative when a concurrent process's rows were swept (disabling eviction for the process lifetime). The total is now always read from `SELECT SUM(size)`. Eviction now deletes oldest rows in batches until enough space is actually freed, instead of a one-shot estimate from the average row size that under-evicted whenever sizes were skewed. An entry larger than `maxSize` itself is skipped instead of stored — previously it wiped every other entry first (eviction deleted all rows and inserted the oversized one anyway), leaving a cache that re-wiped on every subsequent write. The expired-entry sweep's throttle timer is seeded so the sweep runs on a process's first operation; it was seeded to construction time, so it never ran in any process shorter than 60 seconds — essentially every CLI invocation. Repeated `getInstance()`/`close()` cycles no longer accumulate process signal listeners until Node prints `MaxListenersExceededWarning` to stderr. Docs now describe eviction as oldest-first rather than LRU, which is what the code has always done (`timestamp` is only written on `set()`).

- **cache**: Only genuine corruption (`SQLITE_CORRUPT` / `SQLITE_NOTADB`) now triggers the rename-aside-and-recreate recovery. The constructor previously treated *every* unexpected error as corruption, so transient lock contention (`SQLITE_BUSY` — e.g. two concurrent invocations against a cache on a filesystem where WAL cannot be enabled) renamed a healthy cache aside, recreated it empty, and broke the other process's open transaction; and a DB written by a newer CLI version was destroyed instead of refused, defeating the schema check's stated purpose. Lock waits now go through `PRAGMA busy_timeout` (5s), and everything that isn't corruption propagates so the CLI degrades to an uncached run with a warning. When recovery does run, the backup's WAL/SHM sidecars are copied before the failed handle is closed (SQLite deletes them on close) and named `<backup>-wal` / `<backup>-shm` so SQLite can actually recover the preserved data — the old naming (`<original>-wal<suffix>`) orphaned the WAL, silently losing any rows not yet checkpointed. Rename-aside backups are pruned to the most recent three so repeated corruption cannot fill the disk.

- **sync**: `deepl sync pull` no longer discards existing translations for keys named after `Object.prototype` members. `sanitizePullKeysResponse` built its result on a plain object, and callers test membership with `pulledKeys[key] !== undefined` / `??` — so for a source key called `toString`, `constructor`, `valueOf`, `hasOwnProperty`, or `__proto__`, the lookup returned an inherited *function*, which is neither `undefined` nor nullish. The entry was therefore treated as a freshly approved TMS translation and won over the real one, then vanished from the file when `JSON.stringify` dropped the function value — while the lockfile recorded it as `translated` / `human_reviewed`, so no later sync repaired it. The accumulator now has a null prototype.

- **sync**: ICU plural/select messages with text around the block are now preserved. The detection pattern was anchored to the start of the string, so `You have {count, plural, one {# item} other {# items}} in your cart.` — arguably the most common real shape — was not recognised as ICU at all and the raw syntax went to the engine as prose. Confirmed against the live API: it returned `{count, Plural, ein {…} weiteres {…}}`, translating the format keyword *and* both selectors, leaving a message with no valid format type and no `other` fallback. Detection now matches an ICU block anywhere in the string, and the prose on either side becomes a translatable segment instead of being silently dropped from the reassembled output (trailing text was previously lost outright). Re-verified end to end after the fix: `plural`, `one`, `other`, and the `count` argument all survive while the surrounding prose is translated. Note this affects `deepl sync`, the only path with ICU preservation; `deepl translate` on a raw ICU string is unchanged.

- **sync**: ICU structural damage is now detected instead of reported as passing. `checkIcuBrackets` compared only brace counts and nesting depth, which are identical when the engine translates the keyword, a selector, or the argument name — so `fail_on_error` never tripped on a message that no longer renders. Validation now compares the parsed argument/format-type headers and the selector keyword sets, while tolerating reordered selectors (order is not meaningful in ICU).

- **sync**: A failed ICU segment no longer yields a part-English message reported as a successful translation — the message is marked failed and retried. `reassemble` also throws on a translation-count mismatch rather than filling the gaps with empty strings, which produced empty plural branches that render nothing for that category.

- **sync**: A locale that failed completely now fails the run. The check used `.every()`, so a run was only unsuccessful when *every* locale failed — with two locales where one succeeded and the other failed outright, the run reported success and exited 0, leaving the failed locale's file absent while CI went green. It now matches the documented contract for exit 12 (`docs/API.md`: "completed with at least one failed locale"): a locale that translated nothing and recorded failures fails the run, while a locale that partly succeeded still reports its per-key failures in the summary without failing the run, and a locale with nothing to do is simply up to date. `--auto-commit` additionally now refuses to commit an unsuccessful sync — it previously checked only drift and dry-run, so it would happily commit a state with a missing locale file.

- **sync**: Staleness is now judged per target locale, so `--frozen` can detect a locale that has fallen behind. `computeDiff` compared only the entry-level `source_hash`, so once one locale was re-synced after a source edit, the entry hash matched again and every *other* locale reported `current` **forever** — no API call was ever issued for them, `sync status` showed 100%, and the CI gate whose entire purpose is catching out-of-date translations could not see it. A key is now stale if any configured target locale's stored hash lags the source or its last attempt failed. Relatedly, the failure check was previously unscoped (`Object.values(translations).some(failed)`), so **one** locale's failure marked the key stale for **all** locales and the next run re-translated locales that were already correct — overwriting human-edited files. Locales absent from `target_locales` are ignored, so a leftover entry for a de-configured locale no longer flags a key indefinitely, and a locale with no entry at all is still treated as a new-locale backfill (counted as new keys) rather than as drift. `sync status` computes the same per-locale determination inline instead of inheriting the shared source-level status.

- **BREAKING — sync**: Untranslated source text is never written into a target locale file and recorded as a translation. When a key's source was unchanged, the lockfile claimed the locale already had a translation, and the target file supplied none — because the file had been deleted to force regeneration, or held an empty value — the source string was written through as the "translation" and the lockfile kept its `translated` status, so **no later run ever corrected it**: the locale file silently retained English and the run reported success. Such a key is now re-translated, and a verbose message explains why. A translation that is present but deliberately empty is preserved rather than treated as missing. **Behaviour change to be aware of**: deleting a target locale file now causes its keys to be translated again (billed) instead of being backfilled with English — which is the point, but it does mean a deleted file costs a real re-translation. Two existing tests asserted the old fallback; neither the CHANGELOG nor `docs/SYNC.md` documented it, and both arrived inside a bulk development commit rather than as a deliberate decision, so they have been updated to the corrected contract.

- **api**: A blank `Retry-After` header no longer collapses 429 backoff into a tight retry loop. `Number('')` is `0`, which passed the finite check and returned a 0 ms delay — and because `0` is a real number the jitter-backoff fallback never engaged, so all retries fired back-to-back at an endpoint that was already rate-limiting the client. A blank or whitespace-only header is now treated as absent; an explicit `Retry-After: 0` is still honoured.

- **watch**: A file changed during its own translation is no longer translated twice concurrently. The debounce entry was deleted in the translation's `finally` rather than when the timer fired, so it removed whatever entry was current by then — usually a *newer* pending timer for the same file, which then could not be cancelled. A subsequent change therefore started a second translation racing to write the same output path, doubling API spend with a nondeterministic winner. The entry is now cleared when the timer fires, and only if it is still the entry that timer registered.

- **sync**: An invalid `--concurrency` no longer makes a sync silently do nothing while reporting success. `--concurrency` was parsed with a bare `parseInt`, so `abc` produced `NaN`, which survives `??` defaulting; `Math.min(NaN, n)` is `NaN` and `Array.from({length: NaN})` is empty, so **zero** workers were started and `mapWithConcurrency` returned an empty result having translated nothing and thrown nothing. Verified end-to-end: with a deliberately invalid API key, `deepl sync` correctly failed with exit 2 while `--concurrency 0`, `--concurrency abc`, and `--concurrency -3` each printed `Sync complete` with exit 0 and no output file. The flag (and `--debounce`) now reject non-positive and non-numeric values at the boundary, `sync.concurrency` is validated in the config like `tms.push_concurrency` already was, and `mapWithConcurrency` clamps to at least one worker as defence in depth.

- **cache/cli**: Interrupting a command no longer reports success or leaks the sync process lock. `CacheService`'s `SIGINT` handler called `process.exit(0)`, and because the cache singleton is constructed during service setup that handler ran *before* the sync engine's own — so `deepl sync` interrupted with Ctrl-C exited **0** (so `deepl sync && git commit` would commit a half-finished sync) and left `.deepl-sync.lock.pidfile` behind. The cache handler now only closes the database, and termination belongs to the CLI entry point, which defers the exit so every other listener's cleanup runs first: verified end-to-end as exit 130 with the lock released. Commands that own their shutdown — `sync --watch`, for which SIGTERM is the normal stop signal — opt out and still exit 0.

- **formats**: TOML multi-line (`"""` / `'''`) values survive a sync. Only the opening line was emitted verbatim, so body lines that happened to look like `key = "…"` were parsed as entries and **deleted from the value**, and the multi-line key — never marked as used — was re-appended at end of file, leaving a document that no longer parses (`trying to redefine an already defined table or value`). The whole block is now emitted verbatim and skipped, including the single-line `k = """text"""` form. Multi-line values remain untranslated, which is the existing documented behaviour.

- **formats**: Translating a key in an Xcode String Catalog no longer destroys that key's plural `variations`. Reconstruct replaced the locale's entire localization object with a single `stringUnit`, discarding per-category translations the parser never surfaces as entries — so they could not be recovered. Existing `variations` are now preserved alongside the updated `stringUnit`, and the `Localization` type declares the field so this cannot silently recur.

- **formats**: ARB (Flutter) files with a UTF-8 BOM are readable. `JSON.parse` rejects a leading BOM, so a BOM-prefixed `.arb` file failed outright; the BOM is now stripped on extract and reconstruct, matching the JSON parser's existing behaviour.

- **formats**: A translated Android string can no longer break out of its CDATA section. `escapeForReconstruct` wrapped the translation in `<![CDATA[…]]>` with no escaping, so a value containing `]]>` closed the section early and the remainder was parsed as XML — allowing extra `<string>` elements into a generated resource file. This was reachable without a malicious API response, because on translation failure the source string is written through verbatim and the source file is used as the template when the target locale file does not exist yet. Occurrences of `]]>` are now split across adjacent CDATA sections, which keeps the text literal, and extract concatenates adjacent sections so such values round-trip unchanged.

- **formats**: New TOML keys are written into the section they belong to. They were appended at end of file using the full dotted path while a `[section]` header was still in scope, so `messages.newkey` parsed back as `messages.messages.newkey` — and because the intended key was therefore still missing, it was re-appended on every subsequent run. Keys are now inserted inside their own section block, with a new `[section]` header added only when that section is absent.

- **formats**: Android XML entities no longer compound on every sync run. `extract` never decoded XML entities, and `escapeAndroid` replaced `&` *last* — so it re-escaped its own output. `Terms &amp; Conditions` became `&amp;amp;` after one run and `&amp;amp;amp;` after three, verified. Entities are now decoded on extract via a single-pass decoder (so a literal `&amp;lt;` decodes to `&lt;`, not to `<`), and `&` is escaped before `<`/`>`; a three-run identity sync is now a fixed point.

- **formats**: Emoji and other astral characters survive `.properties` files. `escapeValue` iterated by code point but escaped with `charCodeAt(0)`, emitting only the high surrogate — `Hello 😀 world` was written as `Hello \ud83d world`, which cannot be decoded back. All UTF-16 code units of a character are now emitted, so an emoji round-trips as a complete surrogate pair.

- **formats**: XLIFF files carrying a `state` attribute are no longer mangled. `state` is a standard attribute that every CAT tool writes, but the `<segment>` and `<target>` patterns required bare tags. For XLIFF 2.0 this meant `extract` returned nothing and `reconstruct` then **deleted every `<unit>`**; for XLIFF 1.2 an existing `<target state="…">` was treated as absent, so a second `<target>` was injected, yielding schema-invalid output that retained the stale translation. Both elements now accept attributes and preserve them through a round-trip.

- **formats**: CRLF-authored resource files are no longer invisible to the tool. Line-based parsers split on `'\n'`, leaving a trailing `'\r'` that defeated their `$`-anchored patterns: a Windows-authored `.po` file extracted **zero** entries, so `deepl sync status` reported `totalKeys: 0` and 0% coverage with exit 0, and `sync export` emitted an empty XLIFF. TOML was affected differently — reconstruct failed to match existing keys and appended duplicates, producing a file that no longer parses (`trying to redefine an already defined table or value`). All line-based parsers (PO, TOML, iOS `.strings`, Java `.properties`) now split on `/\r?\n/`; the latter two already tolerated CRLF, and the change makes that explicit rather than incidental.

- **glossary**: A glossary term named after an `Object.prototype` member is no longer silently dropped or misreported. `tsvToEntries` accumulated into a plain object and tested for duplicates with `entries[source] !== undefined`, so `toString` (and friends) triggered a spurious "Duplicate source" warning, and a `__proto__` term was swallowed by the prototype setter instead of being stored. Genuine duplicate detection is unchanged.

- **sync**: A lockfile entry whose i18n key is named `__proto__` no longer vanishes on every write — the key-sorting JSON replacer accumulated into a plain object, where that assignment invokes the prototype setter. Auto-glossary term extraction, which is keyed by untrusted source strings, was fixed the same way.

- **formats**: The JSON parser no longer pollutes `Object.prototype` via a `__proto__` key in a resource file, and now round-trips prototype-named keys as ordinary data. `hasKey` used `part in record`, which reports inherited members, and `setKeyWithParts` assigned with `current[part] = …`, where `current['__proto__'] = {}` invokes the prototype setter instead of creating a property. Membership is now an own-property check, and assignment goes through `Object.defineProperty`, so a key legitimately called `toString` translates like any other.

- **hooks**: Generated git hooks no longer emit a broken install instruction. The `pre-push` hook template told users to globally install the unpublished `deepl-cli` name — which fails with `ENOVERSIONS` — and now points at `@deepl/cli`. Reported by **@maa-xx** in #70, who correctly diagnosed that the documentation instructed readers to install a package that does not resolve; their docs fix was superseded by actually publishing the package, but this source-level occurrence was the one their PR missed and is now guarded by a regression test asserting generated hook output never references an unpublished package name.

- **cache**: A cache backend that fails to load (e.g. `better-sqlite3` ABI mismatch after a Node major upgrade, `ERR_DLOPEN_FAILED`) is no longer misclassified as database corruption. Previously the constructor's catch-all renamed the user's healthy `cache.db` to `cache.db.corrupt-<timestamp>` and recreated an empty database — verified to quarantine a 2,646-entry cache that passed `integrity_check`. Native-module load failures now leave the database and its `-wal`/`-shm` sidecars untouched; genuine corruption still triggers the rename-aside recovery. `deepl translate` and `deepl write` degrade to running without a cache (single warning per process, exit code 0) instead of crashing, since the cache backend is loaded lazily behind a warn-once latch; `deepl cache …` subcommands, which cannot run cacheless, fail with an actionable error suggesting a reinstall or matching Node version.

- **sync**: `deepl sync --frozen` now reports an accurate key count when drift is caused by a newly-added target locale. Previously the message read `Sync drift detected: 0 new, 0 stale keys.` because the frozen branch in `processBucket` short-circuited before promoting current-status keys missing a target-locale translation into `newKeys` — even though `--dry-run` against the same state correctly reported the backfill count. The drift exit code (10) is unchanged. The drift message now also surfaces `deletedKeys` and only mentions nonzero categories, mirroring the success-path summary format.

- **cache**: `deepl cache enable` / `deepl cache disable` now persist `cache.enabled` to the config file. Both reported success but only flipped an in-memory flag in a process that exited immediately, so the state reverted instantly and subsequent translations kept using the cache after it had been disabled. `deepl cache stats` likewise read a process-local flag that always initialized to enabled, so the status line could never show `disabled` — not even after `deepl config set cache.enabled false`; it now reports the persisted state.

- **sync**: Subcommands now honor `--locale`. Commander bound the flag to the parent `sync` command even when it trailed the subcommand name, so `sync status --locale de` listed every configured locale and `sync export --locale de` emitted XLIFF for all of them. Affects `status`, `validate`, and `export`.

- **sync**: Subcommands now honor `--sync-config`. The flag was silently ignored and the auto-detected `.deepl-sync.yaml` used instead, so `sync validate --sync-config /missing.yaml` exited 0. Affects `status`, `validate`, `export`, `audit`, `resolve`, `push`, and `pull`.

- **sync**: A `--locale` value that is not in `target_locales` now exits with a `ConfigError` (exit 7) naming the offending and configured locales, as documented. Previously `sync --locale <typo>` exited 0 reporting success while translating nothing, which made a typo'd locale in CI report green.

- **sync**: `deepl sync init --sync-config <path>` now writes the config at that path and checks the already-exists guard against it, instead of always using the current directory. `.deepl-sync.yaml` is also written atomically, so an interrupted run cannot leave a truncated config behind.

- **formats**: Android XML and XLIFF parsing is now linear in file size. Both parsers matched elements with a lazy `([\s\S]*?)` pattern, so every opening tag without a matching close rescanned the rest of the file; a 4 MiB resource file took minutes to parse. Android reconstruct also rescanned the whole file once per dotted key to identify `<string-array>` members (2.7 s → 63 ms on a 3.6 MiB, 52,000-entry file).

- **formats**: Android XML self-closing elements (`<string name="x"/>`) are no longer deleted together with the element that follows them.

- **formats**: Android XML values whose CDATA body contains `</string>` are no longer truncated on extract, and plural `<item>` attributes are preserved when a translation is written back.

- **formats**: XLIFF files with a CDATA section in a `<note>` between `<source>` and `<target>` are no longer rejected; only CDATA inside `<source>` / `<target>` is unsupported.

- **hooks**: `deepl hooks install` now resolves the hooks directory git actually reads (`git rev-parse --git-path hooks`), so it honours `core.hooksPath` (husky) and works inside linked worktrees and submodules where `.git` is a pointer file. Previously it reported success while writing a hook git never ran, and crashed with a raw `ENOTDIR` on worktrees and submodules.

- **hooks**: `deepl hooks install` no longer overwrites an existing hook backup. A repeat install writes to the next free `.backup` slot, and the install output now prints the hook path and the backup path. `findGitRoot` also no longer loops forever when given a relative start path.

- **sync**: Auto-glossary sync (`translation.glossary: auto`) skips terms whose source or translation is empty or contains a tab, carriage return, or newline. Such terms were uploaded as corrupted or outright wrong glossary entries, which DeepL then applied to live translations. An unchanged dictionary is no longer re-uploaded on every run (entries were compared against a lossy TSV round trip that could never compare equal), and a glossary failure for one locale no longer ends glossary sync for the remaining locales — the warning now names the locale, glossary, and cause.

- **glossary**: `deepl glossary add-entry` / `update-entry` reject terms containing a tab, carriage return, or newline instead of shifting every following column of the uploaded dictionary, and glossary import picks the TSV or CSV dialect once per file, so a quoted CSV field containing a tab is no longer split into garbage columns.

- **sync**: `deepl sync audit` no longer uses the lock file's source hash as a stand-in for a translation. Divergent translations were reported as consistent and identical ones as an inconsistency displaying a hex hash. Targets that cannot be read are now listed separately as missing — a new additive `missingTargets` field in the `sync audit --format json` output.

- **sync**: TMS request URLs are built with the URL API: a trailing slash on `server:` no longer produces a doubled separator, a base path is preserved, and a URL with a query string or fragment is rejected instead of silently truncating the API path. TMS timeouts now exit with the network-error code (5) instead of 1, TMS error messages redact credentials embedded in the server URL, and `deepl sync pull` enforces a 32 MiB cap on the response body while reading it, instead of after the whole payload had been parsed.

- **api**: Non-idempotent POST requests are no longer re-submitted after a client-side timeout. Every failure short of a 4xx reached the retry loop for all HTTP methods, so a batch or document upload that outlived the 30 s timeout was silently re-sent up to three more times — each already accepted and billed server-side (confirmed with server-side request counts: 4 per timed-out translate and upload), with the worst case being duplicate admin API keys whose secret is returned only once. Automatic retry is now restricted to idempotent methods (GET, HEAD, PUT, DELETE); a POST is replayed only on an error that proves the request never reached the server (`ECONNREFUSED`, `ENOTFOUND`, `EAI_AGAIN`). A 429 is still retried for every method, honoring `Retry-After`.

- **api**: A client-side timeout now exits 5 (network error) instead of 6 (invalid input), matching the documented exit-code contract. Error classification substring-matched the message and missed axios's `timeout of 30000ms exceeded` (`ECONNABORTED` and `ERR_CANCELED` were absent entirely), falling through to `ValidationError` — so CI that retries on 5 and hard-fails on 6 did exactly the wrong thing on a flaky network. Classification now branches on `error.code` and the absence of a response. An HTTP 401 is likewise mapped to `AuthError` (exit 2) instead of falling through to exit 6.

- **api**: Retries run under an overall time budget rather than only a per-attempt timeout — twice the request timeout by default — so a never-responding server no longer holds a single command for two minutes (measured 125 s before). Honest `Retry-After` waits are not charged against the budget.

- **api**: The Trace ID quoted in an error message now belongs to the request that failed rather than the client's last-seen response, so concurrent requests no longer cross-quote each other's Trace IDs.

- **api**: Errors already classified by the API client are no longer re-classified when a client wraps its own error handling, which could turn a validation error into a network error and drop its recovery hint. Error messages also no longer print a doubled `Network error: Network error:` prefix.

- **api**: The document translation result endpoint is never retried — the download is effectively single-use, so a retry after a timeout on a large file could permanently lose an already-billed translation — and document transfers get their own larger timeout.

- **voice**: `deepl voice` now actually reconnects after a transport failure. The socket `error` handler marked the stream ended before the `close` event that always follows arrived, so the reconnect path (up to 3 attempts, `--reconnect` on by default) was unreachable for a real network drop — only a clean remote close ever reconnected. A reconnect that exhausts its attempts now closes the audio input instead of leaving the stream generator awaiting forever.

- **formats**: YAML files using merge keys (`<<: *anchor`) or aliases to anchored maps and sequences no longer fail at sync write-back with `Expected YAML collection`. Extraction previously emitted paths through aliases that reconstruction could not apply; aliased collections are now translated at their anchor site and the references round-trip untouched.

- **sync**: ICU plural messages using `offset:N` and messages with single-quote-escaped braces (`'{'`, `'}'`, `''` for a literal apostrophe, `'#'` in plural context) are now recognized and preserved instead of falling back to raw machine translation, which demonstrably corrupts ICU keywords and selectors. `sync validate` placeholder checking is also ICU-aware: plural/select branch braces are treated as structure, eliminating spurious `Extra placeholders in translation` warnings for translated branch bodies.

- **sync**: Template literals containing regex metacharacters in scanned source code (e.g. `` t(`item(${i}`) ``) no longer abort context resolution with a raw `SyntaxError` or silently mismatch keys — all metacharacters are escaped before the scan pattern is compiled.

- **watch**: `filesWatched` statistics now report the actual number of files under watch — seeded from the watcher's inventory once the initial scan completes and tracked live on add/unlink. It was previously never incremented and always reported 0.

- **cli**: The global `--timeout`/`--max-retries` flags now also apply to the API-key validation requests made by `deepl init` and `deepl auth set-key`, which previously always used the 30 s default.

- **utils**: Atomic file writes preserve the target's existing permissions instead of resetting them to the umask default — e.g. `deepl write --fix` on a `0600` secrets file no longer leaves it world-readable at `0644`.

- **docs**: README translate examples no longer show a `Translation (XX):` label the CLI never emits; corrected `--model-type` (no CLI default), `--config` precedence (replaces the config file only; the cache path is unaffected), unknown-command and `deepl detect` sample output, and the nonexistent 10 MB PDF cap (the document limit is 30 MB uniformly). README now covers `deepl sync`, `deepl tm`, and all nine `style-rules` subcommands, with dead in-page anchors repaired and `docs/SYNC.md` listed under Documentation.

- **docs**: TROUBLESHOOTING's exit-code table gains codes 10–12 (SyncDrift, SyncConflict, PartialFailure) and its environment-variable table gains `TMS_API_KEY`, `TMS_TOKEN`, `FORCE_COLOR`, `TERM`; sync JSON-contract stability promises are rescoped from "1.x" to "within a major version"; the GitHub Actions recipes in docs/SYNC.md pin Node 24; CONTRIBUTING no longer cites Zod (validation is commander `Option.choices()` plus hand-written validators); examples/README no longer references a nonexistent `sample-files/` directory.

- **cli**: Subcommand parse errors (unknown subcommand, unknown option, invalid choice, missing argument) exit 6 (invalid input) as documented, instead of 1 ("CLI crashed"). Top-level parse errors already exited 6; the mapping is now uniform across all subcommands, so CI scripts following the documented exit-code table no longer misread a typo as a crash.

- **usage**: Text and table output no longer report duration-billed products (e.g. speech-to-text minutes) as zero characters — duration billing units are recognized, rendered in h/m/s as documented, and product names print in the documented snake_case. `--format json` was already correct and is unchanged.

- **admin**: An entitlement failure (valid key without admin scope) no longer suggests re-running `deepl init` / `auth set-key` — the suggestion now explains that the admin API requires an administrator API key. Exit code and classification are unchanged.

- **cli**: The non-TTY `--format table` fallback notice carries the documented `WARN` prefix at all six call sites, matching `sync resolve`'s existing convention.

- **glossary**: Scoped commands (`show`, `entries`, `delete`) no longer emit an unrelated org glossary's "empty dictionaries" warning during name resolution — the warning appears only when the glossary actually operated on is affected.

- **sync**: `sync resolve` prints each parse-error fallback warning once (relative path) instead of twice.

- **write**: The unsupported-style error links to the published docs URL instead of a `docs/API.md` path npm users don't have.

- **config**: `config delete` and the config read paths can no longer walk or mutate the prototype chain — `__proto__`/`constructor`/`prototype` segments are rejected, completing the `config set` hardening.

- **sync**: `deepl sync pull` no longer reads an inherited `Object.prototype` member as a pulled translation. `sanitizePullKeysResponse` returns a null-prototype object precisely so a source key named `toString`/`constructor`/`valueOf` cannot resolve to a function through `keys[key] !== undefined`, but the pull path had begun spreading it into a plain object literal (`{ ...keys }`), re-exposing the prototype — so on a monolingual bucket a source key with such a name, against a TMS export that omits it, read the inherited function as an approved value, reported `Pulled`/`Replaced`, and deleted the reviewed local translation (on a PO bucket it crashed `value is not iterable`). The spread now preserves the null prototype, and `mergePulledTranslations` tests membership with `Object.hasOwn` so it is immune to the shape of whatever object a caller hands it. All within unreleased work; no tagged release shipped it.

- **perf**: `sync audit` registration no longer loads fast-glob on every CLI invocation (lazy import, matching its sibling subcommands).

### Security

- **sync**: **`deepl sync validate` was inert for PO and XLIFF buckets and reported the opposite of the truth.** The gate compares each target value against its source, but for a bilingual format it read the msgid / `<source>` on both sides, so it was comparing the source against itself. Measured through the real CLI on a `locales/es/app.po` whose `msgstr "Hola amigo"` drops the `{name}` placeholder the msgid carries: `deepl sync validate` **exited 0** reporting `1 warning(s)` — and the warning was `Translation is identical to source text`, which is a false positive raised against every entry in every PO and XLIFF bucket, correct translations included. The genuinely broken translation passed. It now exits 8 with `ERROR es/Hello {name}: Missing placeholders in translation: {name}`. Anything using `deepl sync validate` as a CI gate on a PO or XLIFF project was gating on nothing: the check that was meant to catch a placeholder-dropping translation could not see the translation at all.

- **formats**: **no writer emits a raw C0 control byte into a repo file any more.** Six of the nine writers escaped only their own quoting characters plus `\n`/`\r`/`\t`, so any other control byte in a translation was written through untouched; JSON, YAML and ARB were already clean because they delegate to `JSON.stringify` and the YAML emitter. That put live terminal-control sequences into source-controlled files, where `git diff`, `cat`, `less` and CI log viewers all render them — with no CLI output path involved. **No API call is needed to trigger it.** A contributor commits a *valid* `locales/app.de.toml` holding `greeting = "Hola\u001B[2J"` (TOML basic strings legally carry `\uXXXX`, and smol-toml decodes it to a raw ESC). The key is then `current`, so it is never translated and never validated: the locale translator carries the existing target value forward and the writer put the byte back out raw. Measured through the real CLI: the rewritten file contained `greeting = "Hola␛[2J"`, and `TomlFormatParser.extract` then refuses it — `Invalid TOML document: control characters are not allowed in strings`. The finding said every later run fails; **measured, it is quieter and worse than that.** `deepl sync` exits 0 and says nothing, because the target-file read is inside a catch that treats a parse failure as "no existing translations", so the file's translations simply stop being visible to sync. `deepl sync status` exits 0 reporting **`de [####] 100% (0 missing, 0 outdated)`** for a file it cannot parse. Only `deepl sync validate` fails, at the untyped exit 1. Android XML and XLIFF are worse still: every C0 byte except tab, LF and CR is outside XML 1.0's `Char` production, so there is no escape and no numeric character reference for it — expat rejects both written files as `not well-formed (invalid token)`, which means `aapt2` and every conforming CAT tool reject them too. One shared rule now lives in `src/formats/util/control-chars.ts`, and each writer applies it the way its own format allows: TOML escapes as `\uXXXX` (and forces the double-quoted form for a value a literal string could not escape, plus U+007F, which smol-toml also rejects raw — verified against the library); `.properties` extends its existing `\uXXXX` rule below U+0020; iOS Strings emits `\UXXXX`, which its own reader already decodes; PO gains the missing `\r` escape and refuses the rest with a `ValidationError` naming the entry, since its escape set cannot spell them and `unquote` could not read them back; Android XML and XLIFF refuse with a `ValidationError` naming the resource or trans-unit, matching the stance both already take on CDATA. Each message names the codepoint (`U+001B`) rather than quoting a byte that prints as nothing.

- **sync**: **a source catalog can no longer smuggle one string into another string's key.** Five parsers encode hierarchical key identity in-band with no escaping: PO joins `msgctxt` and `msgid` with U+0004, YAML joins path segments with U+0000, and JSON, Laravel PHP and Android XML join with `.`. A key component holding the separator therefore resolved to the same key as an unrelated entry, and the two control bytes **print as nothing**, so the source diff showed an ordinary string. Measured: a PO catalog carrying `msgid "menu␄Save"` beside a normal `msgctxt "menu" / msgid "Save"` pair extracted two entries with the identical key `menu␄Save`, and reconstruct wrote the smuggled entry's translation into the legitimate pair's `msgstr` — the attacker picks the source text, DeepL translates it, and the result lands in the victim key's slot in **every** locale. **The stronger case needs no collision at all**: one smuggled `msgid "menu␄Save"` in a catalog with no `msgctxt` anywhere produced `msgctxt "menu"` / `msgid "Save"` / `msgstr "ATTACKER-TEXT"` in every target `.po`, forging a context-qualified entry the source never had — so a duplicate-key check alone would have missed it. YAML behaves the same way: a source key `"a\0b"` became a genuine nested `a: { b: ATTACKER-TEXT }` via `doc.setIn`. For the `.` formats the damage is a lost or corrupt file rather than a forgery: `{"a.b":"FLAT","a":{"b":"NESTED"}}` rewrote both slots to one translation and dropped the flat key's own; the Android `<string name="items.0">` colliding with `<string-array name="items">` was **deleted** from the output; and the Laravel case emitted PHP the CLI's own parser then refuses — the repo's `11-dot-key-vs-nested.php` fixture reconstructs to `'b' => 'PWNED<NESTED>'LAT>',`, failing to re-read with `syntax error, unexpected 'LAT' (T_STRING), expecting ']'`, because `collectStringLocs` maps a key to one source offset and the two replacements splice over each other. Each parser now refuses the file: PO and YAML reject the reserved byte at both key-construction sites (extract and the target-file read inside reconstruct), quoting it back escaped as `\u0004` / `\u0000` rather than echoing a byte that prints as nothing; JSON, Laravel PHP and Android XML assert their extract output has distinct keys, which for those three is exactly equivalent to detecting a separator collision because their containers already guarantee distinct sibling keys. `sync` skips the one file with a warning naming the colliding key and finishes the rest of the run at exit 0, following the existing `FormatDepthExceededError` and `max_entries_per_file` convention — one hostile file must not discard the lockfile for work already translated, billed and written. `.properties` and XLIFF are deliberately excluded: a literally repeated key is legal in both (Java `Properties.load` is last-wins), so a blanket duplicate check would have rejected files that work today. `sync pull` reading a **target** file whose keys collide leaves it untouched and records a `key_collision` skip, rather than falling through to the source template — measured, that fallback would have rebuilt `locales/de.json` from source down to the single key the export carried, discarding a hand-written translation.

- **translate**: **a document upload response can no longer choose where this client sends its own follow-up requests.** The `document_id` from `POST /v2/document` was interpolated into `POST /v2/document/{id}` and `POST /v2/document/{id}/result` with no encoding and no format check, and the endpoint supplying it is redirectable via `--api-url`, `api.baseUrl` or a proxy. Measured against a stub answering `document_id: '../../v3/glossaries%3fpwned=1'`, the client's next two request lines arrived as `POST /v3/glossaries%3fpwned=1` and `POST /v3/glossaries%3fpwned=1/result` — the traversal collapsed exactly as crafted, on a completely different route from `/v2/document/{id}` — and the run finished at **exit 0** reporting `Translated report.pdf -> out.pdf` after writing the stub's JSON body into the output file as if it were a translated PDF. `document_id` is now checked against `[A-Za-z0-9_-]+` at both interpolation sites, so a redirected first response stops the workflow at exit 5 (`NetworkError`, since nothing the user typed is wrong) with the ID quoted back, nothing further sent, and no output file written. A response with no `document_id` at all was reaching the wire as the literal path `/v2/document/undefined`; that is refused by the same check. This was the last unguarded interpolation of an untrusted value into a URL path in the API layer — `GlossaryClient` validates its ID at all 7 sites and `StyleRulesClient` encodes at all 8, and the document client was the one exception among the ten clients. The polling loop was also checked: it re-sends the original handle rather than the `document_id` echoed by each status response, so a clean first response cannot be followed by a poisoned second one.

- **sync**: **`sync pull` no longer records `review_status: human_reviewed` for content it never verified was reviewed.** Every key a pull applied was stamped `human_reviewed` in `.deepl-sync.lock`, unconditionally. The documented export contract is `GET /keys/export` returning `{ "key": "translated value", … }` — a flat map with no per-entry review flag — so there was nothing in the response to base that claim on, and a TMS that exports machine-translation drafts had them recorded in a committed file as human-reviewed. Where the `tms.server` in a checkout is not one the operator chose, the endpoint controls the strings *and* the review label attached to them. Measured: a mock export returning `{"greeting":"Hallo vom TMS"}` produced `"de": {"hash":"185f8db32271","review_status":"human_reviewed","status":"translated","translated_at":"…"}`. Pulled entries now record `status: translated` with **no** `review_status`, which is the type's way of saying "unknown"; `human_reviewed` is still honoured when a person or another tool writes it, and `--flag-for-review` still writes `machine_translated`, so nothing else in the lockfile changes. Nothing in the CLI reads `review_status` today, which is exactly why a false value could sit there unnoticed until something did — including the `tms.require_review` gate the config schema advertised.

- **sync**: **`--force` is refused when there is no terminal to confirm it on, instead of treating "nobody can answer" as yes.** The guard threw for `CI=true` and prompted on a TTY, and had no third branch — so in a git hook, cron job, `make` target, container entrypoint, Jenkins agent, or plain `deepl sync --force < /dev/null`, the prompt was skipped and the run **proceeded**. This inverted the convention `confirm()` exists to enforce: it returns `false` for a non-TTY, deliberately fail-closed, and the seven other destructive sites (`cache clear`, `admin`, `config`, two in `glossary`, two in `style-rules`) all inherit that auto-NO. This one site turned it into auto-YES, for the single most destructive operation the CLI has. Measured on a fully synced project whose `locales/de.json` had been hand-edited to stand in for human review: `env -u CI deepl sync --force < /dev/null` printed no prompt and no warning, reported `✓ de: 3/3 keys`, `Sync complete: 3 new`, **exit 0**, and replaced all three reviewed strings with machine output — with no `.deepl.bak` surviving, so the edits were unrecoverable. **`--no-input` was ignored on the same path**, though it documents itself as "abort instead of prompting": `deepl --no-input sync --force` destroyed the same edits at exit 0. Both now exit 6 with a message naming `--yes` as the only way to run `--force` unattended, and `--yes` still works everywhere it did. Refusing rather than aborting quietly, matching the existing `CI=true` branch and the TMS destination-trust gate: unlike `cache clear`, declining here abandons the whole sync, so exit 0 would report an up-to-date project for a run that did nothing. An interactive decline is unchanged at exit 0, and now prints `Aborted.` like its seven siblings. Verified on a real terminal through a pty: the prompt appears, `n` aborts with the edits intact, `y` proceeds. The gate is a single `canPrompt()` in `utils/confirm.ts`, which `confirm()` itself now uses, so the two cannot drift apart.

- **sync**: **a lockfile is now checked member by member before sync uses it, instead of being version-checked and then cast.** `SyncLockManager.read()` validated `version` and that `entries` was an object, then cast the rest of the repository's JSON to `SyncLockFile` — so `stats`, each per-file map, each entry and each translation were dereferenced unguarded. Four shapes reproduced by execution against a mock endpoint, all from a lockfile a hostile or merge-mangled repository ships: **a missing `stats`** crashed with `Error: Cannot set properties of undefined (setting 'total_keys')` and exit 1 **after the endpoint had been hit and `de.json` written**, leaving the lockfile as the attacker's stub so the next run re-billed everything; **an entry with no `translations` container** crashed with `Cannot read properties of undefined (reading 'de')`, and the same lockfile took `sync status` — a read-only command — down with `Cannot convert undefined or null to object`; **a per-file map that is a string** crashed with `Cannot delete property '0' of [object String]`; and **`entries` as an array** was accepted silently, exit 0, with the run's results written onto named properties of that array and then discarded by the serializer, so the lockfile recorded `"entries": []` beside `total_keys: 2` and every later run re-billed the project in silence, forever. Two more shapes found while probing: **a null translation** crashed with `Cannot read properties of null (reading 'status')` — one level deeper than the shape check the finding proposed — and **`stats` as a string** crashed with `Cannot create property 'total_keys' on string`. Every one of them now exits 0 with a well-formed lockfile. **Malformed members are dropped individually, not by discarding the file**: a key that loses its entry is translated and billed again, so resetting a whole lockfile over one bad member would hand whoever wrote it a full re-translation of the project. The count is reported at WARN level and the original is copied to `.deepl-sync.lock.bak-v1-malformed-<timestamp>`. `entries` that is not a map at all has nothing to salvage and takes the existing full-sync path with its own `-entries-not-a-map` tag. **`stats` is no longer trusted at all**: it is derived from `entries` and recomputed on every write that follows a mutation, and nothing reads the on-disk values for their own sake, so read() recomputes the counts from the surviving entries rather than validating what the file claims — which also means the counts can no longer disagree with the entries they describe. The repaired `entries` is rebuilt with `setOwnMember`, so a source path or i18n key named `__proto__` is carried across as an own property. In-repo precedent for the shape of the fix: `sync/tms-client.ts` already validated an untrusted map this way for pulled keys.

- **hooks**: **`deepl hooks list` no longer reports attacker-authored content as an installed DeepL hook, and the integrity check it already had is now on a path a user can reach.** Two halves of one false-assurance defect. `isDeepLHook()` was `MARKER_PATTERN.test(content) || content.includes('# DeepL CLI Hook')`, and that second test is a **bare substring match**: a file mentioning the marker anywhere, on any line, in any context, passed as a hook this CLI installed. And `verifyIntegrity()` — which parses the `# DeepL CLI Hook v1 [sha256:...]` marker, rehashes the body and compares — was referenced by nothing but its own definition and its unit tests, so no command ever called it and the recorded hash was never checked outside the test suite. Reproduced by execution: a repository shipping a tracked `.githooks/pre-commit` that carries a forged marker with an all-zero hash plus a payload, wired up with `git config core.hooksPath .githooks` (the husky pattern, commonly set by a `prepare` script), and a second file whose only claim to the marker was the sentence `# borrowed from a # DeepL CLI Hook someone posted`. Before: `✓ pre-commit installed`, `✓ pre-push installed`, and `--format json` reporting `{"pre-commit": true, "pre-push": true}` for two files this CLI had never touched. **`list` now reports one of four states per hook** rather than a boolean — `installed` (versioned marker present and the body hashes to what it records), `modified` (marker present, body does not hash to it), `unverified` (legacy pre-1.0 marker, no hash to check), `not-installed` (no file, or no marker) — so the forged hook reads `! pre-commit installed, content does not match its recorded hash` and the quoted-marker file reads `not installed`. The legacy marker is now anchored to a whole line the way the versioned one always was, which is safe because it was only ever emitted as a line of its own. **The output states plainly what the hash is and is not worth**: it detects a change made after the marker was written, and it **cannot establish authorship**, because it is unkeyed — anyone who can write the hook can compute a marker that agrees with their content. That limit is why the fix is honest reporting rather than a stronger claim, and why the marker should be read as change detection, not provenance. A mismatch also has an innocent reading the CLI cannot distinguish — the README invites customizing an installed hook by editing it — so `modified` renders in yellow and the note gives both readings instead of accusing: expected if you edited it yourself, otherwise reinstall. Tightening `isDeepLHook` also tightens two paths that consult it, both fail-safe: `uninstall` refuses to delete a file whose marker is only quoted (it would previously have removed it), and `install` backs such a file up instead of overwriting it.

- **hooks**: **`deepl hooks install` no longer writes an executable outside the repository because the repository told it to.** `resolveHooksDir` asks `git rev-parse --git-path hooks`, which faithfully honours `core.hooksPath` — including an absolute path anywhere on the filesystem — and the install then did an unconditional `writeFileSync` plus `chmod 0755` with no containment check. `core.hooksPath` is repository-local git config, so it travels with a checkout rather than coming from the person running the command. Reproduced by execution: `git config core.hooksPath /outside/dir` followed by `deepl hooks install pre-commit` printed `✓ Installed pre-commit hook`, exited `0`, and left an `0755` script in `/outside/dir`, with nothing on any channel to say the write had left the project. The content written is the CLI's own static template, so this was a wrong-destination defect rather than an arbitrary-code one — but the destination was the checkout's choice. An install whose hooks directory falls outside the working tree now names the configured value and the resolved directory and asks first: declining, or having no terminal to ask on, **exits 6 and writes nothing**, and `-y, --yes` accepts it while still printing the notice to stderr so a scripted install records where the executable went. The refusal lives in `GitHooksService.install`, which needs an explicit `allowExternal` to proceed, so the gate cannot be skipped by a caller that forgets to prompt. Three scoping decisions. Only the **repository-local** setting is consulted: a global `core.hooksPath` is the user's own machine-wide choice, and reading `--local` also means a repository that sets nothing is never reported — which is what keeps **linked worktrees and submodules** quiet, since there `--git-path hooks` legitimately answers with the hooks directory of the repository that owns them, outside this working tree by design. Containment is checked **through symlinks**, so a relative `core.hooksPath` pointing at a symlink that leaves the tree is caught rather than passing a lexical check. And **`uninstall` is left alone**: it already refuses to remove anything that is not a DeepL hook, so the worst it can do at a redirected path is clean up a file this CLI wrote. The containment predicate is now `isWithinDirectory` in `src/utils/paths.ts`, extracted from the copy that was private to `sync-utils.ts` along with `realpathOrAncestor`, so `assertPathWithinRoot` and the hooks check compare paths the same way.

- **config**: **the `0600` mode on the file holding the plaintext API key is now enforced on every load, not just asserted at creation.** `config.json` is created `0600` and its directory `0700`, and neither was ever checked again — so a file restored from a tar or dotfiles backup, copied by `rsync`, or written by hand kept whatever mode it arrived with, forever, and `load()` read it with no `stat`, no repair and no warning while README promised `0600`. Reproduced by execution: a `0777` config directory was still `0777` after `auth set-key`, and a `config.json` chmod'd to `0644` was read by `config list` at exit 0 and left `0644`. A group- or world-reachable config file is now tightened back to `0600` on load, and the run says what it found — `… was mode 0644, which other users on this machine can read. Tightened to 0600. Your API key may already have been read; consider rotating it with: deepl auth set-key` — because a repair says nothing about who read the file before it. The warning is self-extinguishing: the next run finds `0600` and is silent. **The directory is deliberately reported rather than repaired**, which is where the filed remediation had to be rejected after probing it: it proposed `chmod(path.dirname(configPath), 0o700)`, and that dirname is not always a directory the CLI owns — `deepl -c ~/deepl.json` would have chmod'd the user's home directory to `0700`, and this repo's own `ConfigService` unit tests would have chmod'd `/tmp`. A directory that already existed was created by someone else for reasons the CLI cannot know, so it names the mode and the `chmod 700` that would close it and changes nothing. Only the **write** bits are reported (`0o022`): a merely traversable `0755` directory does not let anyone replace the file inside it, and warning about it on every run would be noise nobody reads. **Sticky directories are exempt**, which execution also forced — the first implementation told the user to `chmod 700 /tmp`, advice that would break a shared temp directory, when mode `1777` is exactly the arrangement that makes it safe: only a file's owner can rename or remove it. The cache directory gets the same report, and `cache.db` needed nothing, as it is already `chmod 0600` on every open. Both `mkdir` sites are now unconditional recursive calls rather than `existsSync`-then-create, closing the window where a directory could appear between the two. Nothing refuses to run over a permission: the mode of the file is not a reason to reject the settings in it.

- **logger**: **the credential redactor no longer has two holes that between them defeat its own documented invariant.** It promised that "a dumped axios error (config.headers.Authorization etc.) cannot leak credentials via util.inspect", and neither half of that held. **Hole one: any object that was not a plain object, an array or an `Error` was returned live.** Reproduced by execution — an `Error` whose `config.headers` is an `AxiosHeaders` instance printed `headers: AxiosHeaders { Authorization: 'DeepL-Auth-Key SUPER-SECRET-KEY-FROM-CONFIG' }` verbatim, while the sibling plain-object field on the same error was redacted correctly. `Map` and `Set` leaked the same way and worse, since their contents are not own properties at all: `util.inspect` prints `Map(1) { 'Authorization' => 'DeepL-Auth-Key SECRET' }` and the redactor never saw a string. Every object is now **rebuilt property by property on its own prototype**, so `util.inspect` still names the class (`AxiosHeaders { Authorization: 'DeepL-Auth-Key [REDACTED]' }`) but never receives the original instance, and `Map`/`Set` are rebuilt with their keys and members mapped. Returning a foreign instance untouched was the wrong default for a redactor; the fail-closed one is to copy. Four types are still passed through deliberately — `Date`, `RegExp`, `ArrayBuffer` and its views — because their payload is not in string-keyed own properties, so a rebuilt copy would either lose it (`Date {}` instead of the timestamp) or, for a `Buffer`, enumerate one own property per byte; none of them renders a credential as readable text, since `util.inspect` prints a buffer as hex. Properties are `defineProperty`'d rather than assigned, so an own key named `__proto__` — which `JSON.parse` can produce — lands on the copy instead of reaching the prototype setter. **Hole two: the literal-value backstop read only `process.env`, and the config-file key wins precedence over it.** `src/cli/index.ts` resolves `apiKey ?? envKey`, so with a key in `config.json` and a different one in `DEEPL_API_KEY`, the value on the wire is precisely the one the redactor could not see. Reproduced against a loopback stub: the captured header was `authorization: DeepL-Auth-Key CONFIG-FILE-KEY-WINS:fx` while `Logger.error` redacted only `ENV-KEY-LOSES:fx` and printed the config key in full. A new `Logger.registerSecret()` closes it, called from the **`HttpClient` constructor** — the one place that sees whichever key won precedence, because it is where the key is attached to every request — and from the **`TmsClient` constructor**, which covers a `tms.api_key` or `tms.token` inlined in `.deepl-sync.yaml`. That chokepoint was chosen over the CLI's key-resolution seams because five call sites read `auth.apiKey` and a per-seam fix would go stale on the sixth. Stated honestly, hole one was a protection-mechanism failure rather than a live leak: no current call site hands a raw axios error to the logger. Hole two is reachable today — a server that echoes the key back in its own error body surfaces as `API error: <key>`, which is the path the new E2E test drives, asserting on the bare value rather than the whole `Authorization` header so the pre-existing header pattern cannot mask a missing registration. The env-versus-config precedence itself is left alone: registration makes redaction independent of which side wins. One existing unit test was replaced rather than kept — `should pass non-plain objects through unchanged` asserted the hole, down to a `token=class-secret` inside the instance it expected to pass through.

- **api**: **a `/v2/translate` or `/v2/write` response body of the wrong shape is now refused instead of being carried into output.** The bodies were typed by a TypeScript interface, which asserts nothing at runtime, and checked only for truthiness and a length match. Reproduced by execution, one stub body per case, all at **exit 0** before this change: `{"translations":"notarray"}` printed the literal text **`undefined`** — a string has a truthy `.length`, so the guard and the length comparison both passed and `[0]` yielded nothing, meaning `deepl translate ... > out.txt` wrote the word "undefined" while reporting success; `{"translations":[{"text":12345}]}` printed `12345`; `{"translations":[{"text":{"a":1,"b":[2,3]}}]}` printed `{ a: 1, b: [ 2, 3 ] }`; `{"translations":{"0":{"text":"x"}}}` printed `x`. A body of `null` crashed on a raw `Cannot read properties of null` at exit 1. All six now exit 5 naming the field and the offending type — `Unexpected API response: "translations[0].text" must be a string, got number.` — and the `--output` path can no longer reach `fs.writeFile` with a non-string and die on `ERR_INVALID_ARG_TYPE`. The checks live in a new `src/api/response-shape.ts` following the contract `sanitizePullKeysResponse` already sets for the TMS: reject rather than coerce, and name the type so the endpoint is diagnosable. **The finding scoped this to the translation client; `write`/`correct` had the identical hole** — `mapImprovements` did the same truthiness-and-length check and passed `improvement.text` through unvalidated — so both are fixed together as one defect class, and the response bodies are now requested as `unknown` rather than as an interface that was never enforced. Three deliberate distinctions. **An absent or null `translations`/`improvements` field is not a type error**: it means nothing came back, which the callers' own messages already describe better ("No translation returned from DeepL API"), so it becomes an empty array and falls through to their existing length check — this is why three pre-existing tests that assert those messages still pass unchanged. **In a batch, every element is validated before any is used**, so a bad element late in the array cannot leave earlier translations already written. And the optional metadata fields — `billed_characters`, `detected_source_language`, `model_type_used` — are **dropped when wrong-typed rather than rejecting the response**, because they are not the translation: a bogus `billed_characters` must not be summed into a cost report or written to a lockfile, but it is no reason to discard a translation that has already been billed.

- **cli**: **pointing the CLI at a non-DeepL endpoint is now announced, so the API key no longer travels to an unexpected host in silence.** `isStandardDeepLUrl()` existed solely to detect this case and was consumed by nothing — `grep` returned the definition and one internal precedence test, no warning path. Reproduced against a loopback stub with `DEEPL_API_KEY=SECRET-KEY-1234`: **the key arrived as `authorization: DeepL-Auth-Key SECRET-KEY-1234` and the run printed only the translation, at exit 0.** Adding `-v` did not help — the verbose line was `[verbose] HTTP POST /v2/translate completed in 12ms (status 200)`, method and path only, never the host. The worst of the three cases needed no flag at all: a `config.json` holding `api.baseUrl` redirected every request with nothing on any channel to say so, and the CLI never reported which config file it had loaded either. Now the resolved endpoint is checked and, when it is neither `api.deepl.com` nor `api-free.deepl.com`, an unconditional `Logger.warn` names the **origin** the key is going to and where the redirect came from: `set by --api-url`, or `set by api.baseUrl in /path/to/config.json` — the real path, resolved from the several locations searched and any `-c` override, which is what makes a substituted config visible. Only the origin is rendered, never the path or query, because those are chosen by whatever did the redirecting and echoing them would put attacker-picked text in front of the user; it is terminal-sanitized on the way out. Four scoping decisions. The notice is **not** gated behind `--verbose`, since a user who does not already know their key is being redirected has no reason to pass it; `--quiet` still suppresses it, matching every other warning. It goes to **stderr**, so `deepl translate ... > out.txt` and `$(deepl translate ...)` keep capturing only translation output. **Loopback is not exempt**, consistent with the TMS destination-trust gate — a co-tenant process on `127.0.0.1` receives the key exactly as a remote host does, and that is the shape the reproduction used. And it fires **once per run rather than once per client**, because a single command may build several (translation, usage, glossary) from the same endpoint and the notice is about the destination, not the client. Regional endpoints such as `api-jp.deepl.com` are included: they are not one of the two hosts the key is issued for. Separately, the verbose request line now names the resolved origin (`[verbose] HTTP POST http://127.0.0.1:56295/v2/translate completed in 12ms (status 200)`), and `ConfigService` gained a `configFilePath` accessor so any message about a setting can name the file that supplied it.

- **sync**: **a sync target path can no longer begin with `-`**, closing the defense-in-depth half of the `git add`/`git commit` option-injection fix. The argv side was already fixed — both call sites pass `--` before the pathspec — but `.deepl-sync.yaml` could still name a target that *looks* like an option, and validation accepted it: `target_path_pattern: --pathspec-from-file={locale}` satisfies all four existing checks (a string, contains `{locale}`, no `..`, no `.git`/`.github` segment) and `resolveTargetPath` rendered it verbatim to `--pathspec-from-file=de`. Reproduced by execution, and the finding named only one of **three** routes to a dash-leading target: the literal pattern, a `{basename}` taken from a source file the glob discovered whose own name begins with `-` (`--pathspec-from-file=x.json` + `{basename}.{locale}.json` → `--pathspec-from-file=x.json.de.json`), and the default locale-substitution branch running over a dash-leading source directory (`-o/en.json` → `-o/de.json`), which involves no pattern at all. Rejecting the pattern alone would therefore have left two thirds of the class open. Two tiers, mirroring how `FORBIDDEN_TARGET_SEGMENTS` is already enforced twice: a literal pattern beginning with `-` fails at config load with `ConfigError` (exit 7), and every path `resolveTargetPath` renders is checked again and fails with `ValidationError` (exit 6), which is the only tier the `{basename}` and locale-substitution routes pass through. **Only the first segment** is checked, because the rendered path is one argv entry and a dash later in it is never option-like — `res/values-{locale}/strings.xml`, `locales/zh-Hans.json` and `locales/-legacy/{locale}.json` all still resolve, verified alongside the three refusals.

- **sync**: **a `tms.server` value in the checkout can no longer redirect the operator's environment-held `TMS_API_KEY` to a host of its choosing.** `.deepl-sync.yaml` picks the destination, `TMS_API_KEY`/`TMS_TOKEN` come from the operator's environment, and `createTmsClient` wired the two together with the only destination guard being **scheme, not identity** — `buildUrl` requires `https:` (waived for `localhost`/`127.0.0.1`) and nothing checked *who* was on the other end. Nothing secret had to be in the repo. Reproduced end to end: a hostile checkout with `tms: {enabled: true, server: http://127.0.0.1:<port>, project_id: victim-project}`, an operator with `TMS_API_KEY` exported (normal for cross-project use), `deepl sync push` → **`Pushed 1 translations to TMS`, exit 0**, while the listener captured `PUT /api/projects/victim-project/keys/greeting` with `authorization: ApiKey TMS-SECRET-CREDENTIAL-1234` and the translated string in the body. `resolveTmsCredentials` did warn — but only about credentials *inlined in the YAML*, never about the YAML choosing the *destination*, and the success line named a count and no host. Now a **hybrid allowlist plus trust-on-first-use** gates it, in `createTmsClient` so both `sync push` and `sync pull` are covered by one choke point: the hostname must appear in a new user-level `tms.allowedServers` list, or be approved once at a prompt that names the host and states that the credential and every translated string would go to it. An accepted answer is recorded in **user** config (`~/.config/deepl-cli/config.json`), never in the repository, so it survives a fresh clone and does not travel with the repo. Under `--no-input` or on a non-TTY the run **fails closed with exit 7** naming the host and the exact `deepl config set tms.allowedServers <hosts>` command, with the already-approved hosts preserved in the suggested value so following it is not destructive. Verified under a real pty: declining exits 7 with nothing sent and nothing recorded; accepting exits 0, writes `allowedServers: ['localhost']` to the isolated config dir, and a later non-TTY run proceeds without prompting. Four scoping decisions the finding did not settle. The gate keys on **credential provenance**, not merely on a repo-supplied host: a credential inlined as `tms.api_key`/`tms.token` is not gated, because it belongs to the same file that chose the destination and nothing of the operator's leaks — and provenance is computed for the credential `getAuthHeader` will *actually* attach, which prefers `api_key`, so an env-held token sitting behind a config-held key does not trigger a prompt it could never leak through. Allowlist-only was rejected as it breaks every existing TMS user with no migration path, and TOFU-only was rejected as it leaves `--no-input` CI with no way to pre-approve. Matching is **exact and case-insensitive on the parsed hostname**, ignoring scheme, port and path, so a listed `example.com` does not approve `tms.example.com` and `tms.example.com` does not approve `evil-tms.example.com`; there are no wildcards, and entries carrying a scheme, port, path or `*` are **rejected at `deepl config set`** rather than stored as approval that could never match. And **loopback is not exempt**, unlike in `buildUrl`'s HTTPS check: a co-tenant process listening on `127.0.0.1` is as much an exfiltration sink as a remote host, which is exactly the shape the reproduction used. Independently and unconditionally, both commands now **print the resolved destination origin** on success in text and JSON output (`Pushed 3 translations to TMS at https://tms.example.com`; `"server": "https://tms.example.com"`), so a redirected destination is visible in logs even when the host was already approved — the origin only, never a repo-controlled path or query, and terminal-sanitized.

- **sync**: **an i18n key named `__proto__` is now recorded in the lockfile instead of vanishing from it, so it is no longer re-translated and re-billed on every run, forever.** Every write into the lockfile's entry maps was a plain assignment — `fileEntryMap[diff.key] = {...}` in `sync-process-bucket.ts` and `sync-tms.ts`, `lockFile.entries[filePath][key] = entry` in `sync-lock.ts` — and for that one key name the assignment reaches the prototype setter rather than creating a property. With `locales/en.json` holding `{greeting, __proto__, normal}`, `deepl sync` reported `3/3 keys` and wrote all three translations into `de.json`, but the lockfile came back with two entries and `"total_keys": 2`; each subsequent run diffed the missing key as new, sent it to the API, and was billed for it again, with no run ever converging. The hazard was already documented one file over — `sync-lock.ts` carries a null-prototype comment about exactly this — but only the **serialization** side had been fixed, and by the time serialization runs the key is already gone. The same shape applied to a **source path** named `__proto__`, which fell out of `lockFile.entries` wholesale, taking every key in that file with it. Fixed with three shared accessors in `sync-lock.ts` (`setOwnMember` / `getOwnMember` / `ensureFileEntries`) applied at all fourteen access sites across six files, following the `setOwn` pattern `formats/json.ts` already uses for this hazard on the translation side. The read side needed the same treatment and for a **different** reason the finding did not cover: plain indexing hands back inherited `Object.prototype` members, so keys named `constructor`, `toString`, `valueOf` or `hasOwnProperty` read as an existing lock entry that is missing every field it should have — `computeDiff` classified all four as **stale** rather than new on a first sync (`newKeys: 0, staleKeys: 4` where both should have been 4/0), and one code path would have dereferenced `.translations` on `Object` itself had a hash ever matched. Two sites beyond the fourteen the finding listed also needed it, in `sync-status.ts` and `sync-locale-translator.ts`. Verified end to end against a recording stub: the key is translated once, the lockfile round-trips all three entries with `total_keys: 3`, `de.json` holds the translated value as an own property, and a second sync sends **no** request and reports 3 current keys.

- **api**: **an endpoint that keeps sending is now bounded in both bytes and wall-clock time.** The shared axios instance set `baseURL`, `timeout` and agents but never `maxContentLength` or `maxBodyLength`, which axios defaults to `-1` — unbounded — so a response body was buffered into memory until the process died; all ten API clients inherited that. Worse, `--timeout` did not save the run, because axios delivers it to the socket as an *inactivity* timeout and this client goes out over the follow-redirects transport, where that is the only timeout armed: every arriving chunk reset it, so it never fired. Measured against a stub streaming 1 MiB chunks forever with `timeout: 5000`: **peak RSS 8572 MB and still running, un-aborted, at 20 s — four times past the configured deadline. After: rejected in 24 ms with RSS flat.** A second, nastier shape proves a size cap alone would not have been enough: a stub trickling **one byte per second** stays under any byte cap indefinitely while pinning the process, and also ran past 20 s untouched; it now aborts at 5005 ms, the configured timeout. With retries enabled the whole call is bounded too — 10093 ms for `--max-retries 3`, matching the twice-`--timeout` budget that was already documented but that only held for an endpoint which said nothing at all. Two changes, and the second is the load-bearing one. **A finite response cap of 32 MiB and body cap of 128 MiB on the shared instance**, verified to be enforced by axios on the buffered and `arraybuffer` paths alike, which is every path this repo uses. **An `AbortController` deadline armed per attempt inside the retry loop**, wall-clock and therefore not resettable by the peer. The caps are deliberately **not** the single 32 MiB used by `sync`'s TMS client, which the finding suggested reusing: DeepL accepts documents up to 30 MB and a translated result can exceed its source — `output_format` converts between types — so a 32 MiB response cap would have rejected a legitimate translated document on `deepl translate report.pdf --to de`, at the one endpoint whose result is single-use and deliberately never retried. Rejecting there destroys an already-billed translation permanently, so the cap would have caused the very data loss it was meant to prevent; the document download therefore raises its response cap to 128 MiB per request, riding the same `RequestPolicy` mechanism it already uses to widen `timeout`, while status polling and the other nine clients keep the tighter default. Two smaller consequences of the same work: a deadline abort is restated as the socket timeout it stands in for, because axios surfaces a mid-body cancellation as a `CanceledError` that still carries the 200 response and classification would have reported that as `API error: canceled` rather than a timeout; and a size-cap rejection is **not** retried, since the verdict is deterministic and replaying it only re-downloads bytes that will be discarded again — three extra attempts on a 32 MiB body were 128 MiB of pointless transfer. Both bounds surface as `NetworkError` (exit 5), the size cap naming the limit it hit rather than axios's internal `maxContentLength size of 33554432 exceeded`.

- **cli, sync**: **text the CLI did not author can no longer drive the terminal that renders it.** Translation text went from the API to stdout raw, and i18n keys went from a checkout to stdout raw, so both could carry terminal control sequences. Measured against a stub endpoint with a real pty on stdout: the run emitted **4 raw ESC and 1 BEL before this change — setting the window title via OSC 0 and erasing the line via CSI 2K — and 2 ESC and 0 BEL after, both of them SGR colour**. The key sink needs no API key and no network: an evil checkout plus `deepl sync validate` exits 8 with an OSC 52 clipboard write and a CSI 2J screen erase verbatim in its output, and `hooks install` puts that command in the pre-commit hook, so it fires on every commit. `sanitizeForTerminal` already existed and was applied in ten other files, just not on the primary render paths. Two layers close it. **Untrusted values interpolated into report lines are sanitized at the call site, unconditionally**: the locale, key and message in `sync validate`, and the choice labels in `write --interactive` / `correct --interactive`, where the value handed back to the caller stays raw so only the display is affected. **The logger neutralizes control sequences centrally**, which covers all 111 `Logger.output` call sites, every stderr sink, and future ones by construction — including error paths that echo a hostile value, such as the JSON parser's duplicate-key report. stderr is sanitized whether or not it is a TTY, because a redirected stderr is still rendered by CI log viewers that interpret ANSI. **stdout is sanitized only when it is a terminal**, because redirected stdout is data: `deepl translate ... > out.txt` and `$(deepl translate ...)` must reproduce the API's bytes exactly, and a control sequence can only act on a terminal that interprets one — the same rule `ls` and `git` apply to nonprintables. Colour (SGR) sequences survive, since chalk-formatted strings are passed to the logger already rendered and stripping them would drop all colour; that concedes only text attributes, while the primitives that let injected text take over a session — OSC title and clipboard writes, CSI erase and cursor moves, and the status queries whose reply is typed back on the shell's stdin — are all neutralized. The stream filter is a **separate, narrower function** from `sanitizeForTerminal`, which cannot be used on a whole stream: it replaces newlines and tabs, and replaces U+200B–U+200F, so applying it to translation output would have turned every multi-line result into `?`-separated text and corrupted the ZWNJ, ZWJ and bidi marks that are legitimate content in Persian, Arabic, Devanagari and emoji sequences — silent corruption of the main command's output, in place of the bug being fixed.

- **api**: a batch translation response that returns the submitted texts themselves, rearranged, is now refused instead of written out. `POST /v2/translate` correlates a translation to its request item by position and by nothing else, and the only check on the response was that it had the same number of entries — so an endpoint returning the request's own texts rotated by one wrote each translation under the wrong i18n key at exit 0, reporting full success. `{confirm_delete: 'Delete account permanently', cancel: 'Cancel', save: 'Save changes'}` came back as `{confirm_delete: 'Cancel', cancel: 'Save changes', save: 'Delete account permanently'}`, hiding a destructive action behind the cancel label; the placeholder validator cannot see it, because plain UI strings carry no placeholders to compare. Verified end to end against a rotating stub: exit 5 and no file written, where the same run previously exited 0 with the keys transposed, and an honest endpoint on the same fixture is unaffected. The check requires **both** that the returned texts are a multiset match for the submitted ones and that at least one has moved position, so it cannot fire on a legitimate identity translation (source language equal to target, where nothing moves) or on one item whose translation happens to equal another item's source text, which a partially translated file produces. It is deliberately narrow: this catches the one reordering that is provable from the response alone, and an endpoint returning plausible **translations** in the wrong order remains undetectable, because the protocol carries no per-item identity to verify. It applies to every batch caller — `translate` on all 11 structured i18n formats, plain-text batches, and `sync` — since it sits in the one client method they share.

- **sync, watch**: auto-commit passes staged paths after a `--` separator and commits with `--only`, so a translation target path can no longer be read by git as an option, and the commit can no longer carry anything else the user had staged. `execFile` prevents shell injection but not git's own option parsing: a `target_path_pattern` rendering a leading dash — `--pathspec-from-file={locale}` passes every existing pattern check, since none rejects a leading dash — reached `git add` as a flag and staged files of the pattern author's choosing, defeating the auto-commit preflight that exists to bound the staged set. `git commit` then ran with no pathspec, so it committed the whole index: a separately staged `.env.local` or unfinished work landed in a `chore(i18n)` commit whose message described only the translation. Both `sync --auto-commit` and `watch --auto-commit` are affected; `sync` was partly shielded by its unrelated-modifications preflight, `watch` was not.

- **cache**: the resolved API base URL is now part of every translation, `write`, and `correct` cache key. One `cache.db` is shared by every endpoint a config directory has ever talked to, and the key hashed 20 request parameters but not who was going to answer them — so a single `deepl translate "hello" --to DE --api-url http://127.0.0.1:18111` served that endpoint's answer back for `api.deepl.com` for the full 30-day TTL, with no network reachable at all. Custom endpoints are a supported feature (proxies, regional endpoints), so this needed nothing the tool discourages: pointing the CLI at a local stub once was enough to make its output the cached truth everywhere. Verified end to end against two stub endpoints returning different text for the same request: each now gets its own row, and neither can answer for the other or for the real API. The endpoint is derived from the same expression the HTTP transport uses (`resolveClientBaseUrl`) rather than a second copy that could drift, and the free and Pro endpoints are keyed apart too. `CACHE_SCHEMA_VERSION` moves to 3, so opening an existing DB drops its `translation:`, `write:`, and `correct:` rows — every one of those keys changed, and retiring them is also what clears any entry a custom endpoint already poisoned. Other namespaces are untouched. Cache **writes** are deliberately still allowed for non-standard endpoints: with the endpoint in the key there is nothing left to cross-contaminate, and disabling them would cost proxy and regional-endpoint users their cache for no gain.

- **sync**: the startup stale-backup sweep no longer writes anything, and no longer takes the whole project as its scope. It restored any **zero-length** file from a `<file>.deepl.bak` sibling, with no check that the sibling was a translation target, was matched by a bucket glob, was tracked, or that the backup came from this tool. A hostile checkout shipping an empty tracked file plus a `.deepl.bak` alongside it — any clone older than five minutes qualifies, since checkout stamps mtimes at clone time — therefore got bytes of its choosing written into that file during sync **startup**, before any translation, at exit 0, with a single `Logger.warn` as the only trace and the `.bak` unlinked immediately after. Because every target write goes through `atomicWriteFile`, which renames a fully-written temp file into place, a crash cannot leave a zero-length target: the restore branch had no legitimate trigger left and is removed, so the sweep only ever unlinks. Separately, a bucket glob beginning with a wildcard (`**/en.json`, `*.json`) has no literal prefix, and the old `path.dirname('')` fallback handed the sweep the entire project root to walk recursively — defeating the scoping the function exists to provide. Such a glob now contributes no sweep root, which means a bucket configured that way gets no stale-backup cleanup and may accumulate inert `.deepl.bak` files; run with `--verbose` to see when this is skipped.

- **sync**: no sync path may resolve into `.git/` or `.github/` any more, closing a gap where the guard that exists to prevent exactly that was enforced on one branch only. `FORBIDDEN_TARGET_SEGMENTS` was checked against a literal `target_path_pattern`, so a bucket that simply omitted the pattern reached the default locale-substitution path unguarded: `buckets.yaml.include: ['.github/workflows/en.yml']` made `deepl sync` write `.github/workflows/de.yml` whose `run:` body was whatever the translation endpoint returned — CI workflow code under the influence of a hostile checkout or a hostile endpoint, at exit 0. The containment check on the project root accepted it, because the path never leaves the root. The check now sits on the resolved path inside `assertPathWithinRoot`, the one boundary every read and write in the pipeline passes through, so both the substitution branch and the multi-locale branch — which writes back to the source path and never calls `resolveTargetPath` at all — inherit it, and a future call site cannot forget it. A bucket rooted in `.github/` now fails at the source-file walk with exit 6 and a message naming the directory, before any translation request is made; the pattern-level check is kept as well, so a bad `target_path_pattern` is still reported at config load. Segments are compared relative to the project root, so a checkout living under a `.github` directory is unaffected, and `.gitlab/`, `.gitignore`, and paths merely containing `github` as a substring are untouched.

- **sync**: glob patterns from `.deepl-sync.yaml` are bounded before they reach fast-glob, so a hostile checkout can no longer end the process with an uncatchable out-of-memory abort. fast-glob expands brace groups through `braces`, a different package from `brace-expansion` despite the name, and `braces` caps only its input length — the expansion it produces is a product with no bound at all. A 1007-byte `include` pattern of 200 `{a,b}` groups therefore killed `deepl sync` and `deepl sync validate` with `FATAL ERROR: Ineffective mark-compacts near heap limit` (SIGABRT, exit 134). An abort is not a JavaScript exception, so the per-bucket error handling could not contain it, and the tool's own generated pre-commit hook and documented CI step were killed the same way. Brace expansion is a product rather than a sum, so this needs very little input: 20 groups is 107 characters and already wedges the run. Every pattern-bearing field is now checked at config load — `buckets.*.include`, `buckets.*.exclude`, top-level `ignore`, and `context.scan_paths` — rejecting anything that expands past 1000 paths or exceeds 4096 characters with a `ConfigError` (exit 7) naming the field. The bound is a conservative over-approximation computed without expanding anything, it counts numeric and alpha ranges (`{1..9}`, `{a..e}`) by cardinality, and it folds unbalanced groups in as if closed so an unclosed `{` cannot smuggle a bomb past it. Neither cap is configurable, since the attacker in this scenario supplies the config; both sit below the point where `braces` itself throws, so its `RangeError` and `SyntaxError` paths are unreachable too. Realistic patterns are nowhere near the cap — `{en,de,fr}/**/*.{json,yaml,yml}` expands to 9.

- **deps**: `brace-expansion` is pinned to `>=5.0.9` through an `overrides` entry, resolving GHSA-rgw5-rvv9-x895 (unbounded intermediate arrays) in the copy reached via `minimatch`. `npm audit --audit-level=moderate --omit=dev` — the gate `security.yml` runs on every push and nightly — was failing. It is an `overrides` entry rather than a dependency because the CLI does not import the package, and declaring it would fail `check-deps`.

- **config**: `ConfigService.save()` writes through an unpredictably named temp file created with an exclusive flag, instead of a fixed `config.json.tmp`. A symlink planted at the predictable path redirected the config — which holds the API key in plaintext — to a path of the planter's choosing, and the subsequent rename left `config.json` as that symlink, so every later write followed it too. The mode is also applied with `chmod` after creation, which the umask cannot widen.

- **tests**: The test suite no longer inherits real credentials or the real config directory. Suites that spawn the bare `deepl` command cannot be intercepted by nock, so they reached the live DeepL API with whatever key was exported and read and wrote the developer's cache database; cached responses matching this suite's fixtures were recovered from a real cache, confirming it had happened. `globalSetup` now clears `DEEPL_API_KEY`, `TMS_API_KEY` and `TMS_TOKEN` and points `DEEPL_CONFIG_DIR` at a temporary directory before workers fork.

- **formats**: The prototype-pollution guard in the JSON parser is now pinned by tests. Replacing `Object.defineProperty` with plain assignment previously left the whole suite green: on a fresh object `obj['__proto__'] = value` retargets that object's prototype rather than `Object.prototype`, so the translation was silently dropped while the negative pollution assertion still passed.

- **ci**: The release workflow refuses to create a GitHub Release when the pushed tag does not match `package.json`. A tag can be pushed at any commit, so without the check a mislabelled tag would mint a Release whose title disagrees with the version it contains.

- **translate/sync**: Placeholder restoration no longer hangs the CLI with unbounded memory growth. `restorePlaceholders` looped `while (restored.includes(placeholder))`, replacing one occurrence per pass — so when the preserved original itself contained the placeholder token, every pass re-inserted it and the guard never went false. Measured before the fix: the input `{__VAR_0__}` grew from 9 to 400,009 bytes across 200,000 iterations without converging, and the real function had to be killed. It needed no attacker and no network: `preserveVariables`' pattern matches `{__VAR_0__}` (underscores and digits are in its character class), variable preservation runs unconditionally, and restoration also runs on **cached** results — so a locale value of that shape hung the process with no API call. Each placeholder is now restored in a single pass, using the function form of the replacement so `$&`/`$1` inside a preserved value stay literal.

- **sync**: Bucket `include` globs can no longer escape the project root, and `--dry-run` no longer modifies the working tree. `include` entries were validated only as non-empty strings, while `target_path_pattern` a few lines later already rejected `..`. The unvalidated glob's literal prefix was resolved and handed to the stale-`.bak` sweep, which recursed with **no containment check** — deleting every old `*.bak` it found and *re-creating* any file whose `.bak` existed while the live file was missing or empty. Verified: `include: "../../../../../../**/*.json"` produced a sweep root of `/var`, an out-of-root `.bak` was deleted and its sibling resurrected with the backup's contents. Two things made it worse: the sweep was gated only on watch runs, so it ran under `--dry-run` — the flag a cautious user reaches for to avoid side effects — and its errors were swallowed entirely, so it was silent. `include` entries are now rejected at config load for traversal segments and absolute paths (the check the `sync init` wizard already applied, which simply did not exist on the load path), the sweep independently refuses any root outside the project and logs the attempt, the sweep is skipped under `--dry-run`, and its failures are reported instead of discarded.

- **deps**: Resolved four production-dependency advisories flagged by `npm audit --omit=dev` via lockfile-only transitive bumps (no `package.json` ranges changed): `brace-expansion` 5.0.5 → 5.0.6 (GHSA-jxxr-4gwj-5jf2, ReDoS), `form-data` → 4.0.6 (GHSA-hmw2-7cc7-3qxx, CRLF injection), and `ws` 8.20.0 → 8.21.0 (GHSA-58qx-3vcg-4xpx and GHSA-96hv-2xvq-fx4p, uninitialized-memory disclosure and memory-exhaustion DoS). Production `npm audit` is back to zero vulnerabilities, unblocking the CI audit gate.

- **deps**: Resolved two further `brace-expansion` denial-of-service advisories disclosed after the bump above: `brace-expansion` 5.0.6 → 5.0.8 (GHSA-3jxr-9vmj-r5cp, exponential-time expansion of consecutive non-expanding `{}` groups; GHSA-mh99-v99m-4gvg, unbounded expansion length causing an out-of-memory crash). Reached in production through `minimatch`, which accepts `^5.0.5`, so this is again a lockfile-only bump with no `package.json` range changes. Dev-tree instances of the same advisories are intentionally left in place: npm's proposed remediation downgrades `jest` 30 → 25 and `ts-jest` 29 → 27, `devDependencies` are not installed by consumers, and the CI audit gate is production-only.

- **formats**: The YAML i18n parser no longer expands aliases at all, structurally removing the denial-of-service vector where documents with exponentially-expanding anchors ("alias bombs") or self-referential anchors hung `deepl sync` indefinitely. Aliased content is extracted and translated only at its anchor site and every alias — including merge keys — round-trips as a reference, so alias bombs now parse in milliseconds as plain references instead of being rejected by the interim expansion budget.

- **formats**: Android XML translations containing `]]>` are refused instead of being written into a CDATA section, where they closed the section and had their remainder parsed as XML — injecting elements into generated resource files. This was reachable without a malicious API response, since a failed translation is written through verbatim and the source file is used as the template for a missing target locale.

- **sync**: Target-path containment is enforced *before* any target file is read or backed up. The check previously ran after the read and the `.bak` copy, so a committed symlink directory plus a crafted `target_path_pattern` could read an out-of-root file into memory and clobber an out-of-root `.bak` sibling before the write was blocked — and the swallowed error made it repeat per locale × file. A containment violation now also aborts the sync instead of being absorbed, and the bucket pre-read loop (which had no containment check at all) now asserts it too.

- **sync**: `source_locale` and `target_locales` are validated against a BCP-47 whitelist at config load (previously a three-substring denylist), and `target_path_pattern` may not contain a `.git` or `.github` path segment — closing a write primitive where a "locale" like `config` plus a pattern like `.git/{locale}` wrote inside `.git/`. **Migration**: underscore-style locale codes (`pt_BR`) are now rejected; use hyphenated BCP-47 (`pt-BR`).

- **sync**: `.deepl-sync.yaml` discovery stops at the repository boundary (the first directory containing `.git`) instead of walking to the filesystem root, so a config planted in an ancestor directory outside the repo is no longer silently adopted as project root.

- **init**: `deepl init` masks the API-key prompt instead of echoing the key in cleartext into terminal scrollback.

- **logger**: Credential redaction now recurses through objects, arrays, and `Error` values (with cycle protection) instead of applying only to strings, so a dumped error object can no longer print an `Authorization` header or API key verbatim.

- **glossary**: Server-supplied glossary names are sanitized before terminal display, blocking ANSI escape injection via glossaries shared within a team account. Style-rule names were already sanitized; the two sites now match.

- **config**: `deepl config set` rejects `__proto__`, `constructor`, and `prototype` path segments and resolves keys with `Object.hasOwn`, so crafted paths can no longer pollute `Object.prototype`.

- **batch**: `translate --pattern` values containing `..` can no longer write translated output outside `--output-dir` (the default output branch now enforces the same containment as `--output-pattern`), and directory batch translation no longer follows symlinks out of the input directory.

- **ci**: `ci.yml` and `security.yml` explicitly request `contents: read` instead of inheriting the repository default token permissions.

- **sync cost cap**: When a brand-new target locale is added to an existing project, `sync.max_characters` now correctly includes the character cost of translating all current keys into the new locale in its preflight estimate. Previously, `toTranslate` was empty (no new/stale diffs) so the cap check passed with 0 estimated characters while the actual sync translated the entire key set — a silent cost surprise. The live-path preflight now mirrors the dry-run math (`currentChars × newLocaleCount`) so `--dry-run` and the live run always report the same estimated character count for the same workload.
- **sync perf**: Stale-lock entry cleanup now issues a single `fg` call with all stale-basename patterns instead of one call per stale entry. A reorg renaming 50 files previously triggered 50 sequential full-tree scans before sync completed; it now completes in one pass regardless of stale-entry count.
- **sync perf**: Startup `.bak` sweep (`sweepStaleBackups`) is now scoped to the directories implied by each bucket's `include` globs instead of walking the entire project tree. On large monorepos the sweep cost is now proportional to the number of bucket-matched directories rather than total project size. Callers without bucket config fall back to the previous full-tree walk with a one-time warning.

The accumulator in `extractAllKeyContexts` pushed one `TemplatePatternMatch` per template-literal match per source file with no dedup; a 2K-file repo with 20 template literals per file produced 40K entries × 10K keys = 400M `.test()` calls (~8s/sync). A `Set`-based dedup before the resolve loop collapses all per-file duplicates to at most one entry per distinct pattern string; `MAX_LOCATIONS=3` downstream is unaffected since the first-seen `filePath`/`line` is sufficient context.

Three call sites that tested `batchIndices.includes(slot.diffIndex)` — one in Path A (plain batch), one in Path C (element-instruction batch), one in Path B1 (section-batched context) — now precompute a `Set` before the `pluralSlots` loop and use `Set.has`. ### Security

- **`deepl sync --force` billing defense**: `--watch --force` is now rejected at startup with `ValidationError` (exit 6) — the combination would silently retranslate every key on every file change, creating an unbounded billing loop. Additionally, `--force` now requires confirmation in interactive mode ("Retranslate all keys and bypass cost cap? [y/N]"); add `--yes` (`-y`) to skip the prompt in scripts. In CI environments (`CI=true`), `--force` requires `--yes` explicitly — the process exits 6 with an actionable hint rather than proceeding silently.
- Updated `minimatch` from `^9.0.5` to `^10.2.1` to fix ReDoS vulnerability (GHSA-3ppc-4f35-3m26)
- **sync**: `deepl sync pull` now acquires the pidfile process lock (`acquireSyncProcessLock`) before writing any target files. Previously, a concurrent `deepl sync` (which holds the lock while writing target files) and `deepl sync pull` could race across multiple files — `atomicWriteFile` prevents torn individual writes but the multi-file read-modify-write cycle was unguarded. `deepl sync push` is read-only toward local files and does not need the guard.
- **sync**: `sanitizePullKeysResponse` now enforces a hard cap of 50,000 keys (`MAX_PULL_KEY_COUNT`) on TMS pull responses. A response exceeding this limit is rejected with a `ValidationError` before any data is written to disk, preventing OOM conditions on large TMS inventories (e.g. 100K keys × 20 locales). Remediation: partition the TMS export by locale or paginate the pull.
- **sync**: TMS error responses are now sanitized through `sanitizeForTerminal` before appearing in thrown `Error` messages. Both the response body (capped at 1024 bytes) and `response.statusText` are stripped of ANSI escape sequences, bidi override codepoints (U+202A–U+202F), and other terminal-unsafe control characters. Previously a malicious or compromised TMS server could inject sequences such as `\x1b[2J` (screen clear) or U+202E (right-to-left override) into the operator's terminal via a crafted 4xx/5xx HTTP response.
- **sync**: TMS `sync pull` now validates response payloads at the TmsClient boundary before writing to source trees. Non-string values, keys with path separators or control chars, and values >64KiB are rejected with ValidationError; control chars are stripped from accepted values. Previously a compromised or misconfigured TMS could write arbitrary bytes — including format-breaking XML or terminal-corrupting control sequences — into the user's working tree.
- **security**: Validate `context.scan_paths` against project root with symlink protection
- **security**: Use URL hostname check for `tms.server` (prevents `localhost.evil.com` bypass)
- **security**: Encode `tms.project_id` in URL path
- **sync**: `sync push`, `sync pull`, `sync export`, and `sync validate` now refuse to follow symbolic links when scanning source files, matching the policy already enforced by `sync` itself and `sync-context`. Previously a symlink inside a bucket's `include` pattern would be silently followed, potentially reading and transmitting files outside the project root (e.g., `/etc/passwd`, SSH keys).
- **sync**: `Logger.sanitize()` now redacts TMS credentials (`TMS_API_KEY`, `TMS_TOKEN` env values, and `Authorization: ApiKey/Bearer <value>` headers). Previously only `DEEPL_API_KEY` and `DeepL-Auth-Key` were covered, so TMS credentials could leak into logs via error messages, Headers dumps, or stringified fetch error bodies.
- **sync**: Harden `sync resolve` conflict-fragment merge against prototype pollution. JSON-parsed fragments can carry `__proto__`/`constructor`/`prototype` as own properties; the merge now skips those keys and uses `Object.create(null)` accumulators so `deepl sync resolve` on a hostile `.deepl-sync.lock` cannot mutate `Object.prototype`.
- **sync**: `deepl sync export` now rejects source-side paths that resolve outside the project root with a ValidationError, matching the `--output` destination guard. Previously a `.deepl-sync.yaml` with absolute source paths or symlinks pre-dating the fast-glob hardening could read files outside the configured scan root during export.
- **sync**: `scan_paths` config entries are validated against path traversal using a proper glob-literal prefix extractor rather than a regex strip. Previously crafted patterns using brace-expansion (`{..,src}/**`), extglobs (`@(..)/**`), or escaped wildcards could bypass the prior `assertPathWithinRoot` guard. No change to valid configurations; rejected configurations now produce a ConfigError with the offending pattern shown.
- **deps**: `npm audit fix` — resolves `axios` GHSA-3p68-rc4w-qgx5 (SSRF via NO_PROXY normalization), `axios` GHSA-fvcv-3m26-pcqx (cloud-metadata exfil via header injection), and `follow-redirects` GHSA-r4q5-vmmm-2653 (auth-header leak on redirect). Not reachable from the CLI (baseUrl hardcoded to `api.deepl.com`; TMS uses native `fetch`); transitive advisories are now quiet.
- **sync**: `.deepl-sync.yaml` and auto-detect-path reads (`package.json`, the first-match i18n file for key counting) now route through `safeReadFileSync`, which rejects symbolic links with a `ValidationError`. A hostile repo could previously ship a `.deepl-sync.yaml` symlinked to `~/.ssh/id_rsa` (or another dotfile outside the project root) and surface the target's contents in YAML parser errors on stderr. Affected sites: `src/sync/sync-config.ts:566`, `src/sync/sync-init.ts:239`, `src/sync/sync-init.ts:271`. Runtime file reads during `deepl sync` itself are unchanged — the bucket walker already refuses symlinks via `fast-glob`'s `followSymbolicLinks: false`.
- **http**: When `HTTP_PROXY` / `HTTPS_PROXY` is configured with an `http://` proxy and the target endpoint is `https://`, the CLI now emits a startup warning naming the proxy host and noting the TLS-termination MITM risk. TLS is still tunneled end-to-end via CONNECT, so this is a visibility fix rather than a behavior change — a malicious proxy that terminates TLS with a trusted cert would see the Authorization header, and the user should be aware. Users with legitimate corporate http-only proxies see the warning but the connection proceeds (no forced abort; the CLI can't tell corporate infra apart from attacker infra).
- **log redaction**: `Logger`'s sanitizer now redacts `X-Api-Key` and `X-Auth-Token` headers, plus `?api_key=` / `?apikey=` query parameters. Previously only `DeepL-Auth-Key`, `Authorization: ApiKey|Bearer`, `?token=` / `&token=`, and the `DEEPL_API_KEY` / `TMS_API_KEY` / `TMS_TOKEN` env-var exact values were covered. axios error dumps that include `config.headers` on TMS-style third-party backends (e.g., Phrase, Lokalise, custom REST endpoints) no longer leak these credentials via verbose logs.
